SONTU DOMAIN & SYSTEM BEHAVIOR

Authority role  
This document is the Gate 1 source of truth for authoritative product states, state transitions, permissions, invariants, concurrency behavior and failure semantics. It defines what the system is allowed to believe and how consequential objects change. It does not prescribe database schema, API shape, component implementation or visual design.

Upstream authorities: 02.01.01 Event Model & Capabilities; 02.01.02 Event Categories & Requirements; 02.01.03 Beta, MVP & Future Scope; 02.01.04 User Journeys & Acceptance Criteria; 02.01.05 Functions & Features; 02.02.01 Experience Architecture & UX Requirements. Technical implementation remains owned by 03.01.

1 — SYSTEM-WIDE BEHAVIOR PRINCIPLES  
B01 Server-authoritative consequential truth. Permissions, capacity, eligibility, payment, admission validity, credential use and check-in cannot be decided solely by client UI state.  
B02 Explicit state over inference. Consequential state is represented directly rather than inferred from labels, page location or absence of data.  
B03 Historical truth is preserved. Material changes, cancellations, refunds, credential invalidations, check-ins and operator exceptions produce auditable history rather than destructive rewriting.  
B04 Idempotent consequential actions. Repeated requests caused by retries, double taps or network uncertainty must not create duplicate registrations, charges, credentials, refunds or check-ins.  
B05 Fail closed for authority, not for comprehension. When authority cannot be established, Joy must not fabricate success; it should preserve the user’s work where safe and communicate pending/unknown/retry states.  
B06 Contextual complexity. Specialized state machines activate only when their capability is enabled; simple events do not inherit irrelevant operational states.  
B07 Gamification is downstream of truth. Progress/achievement state may react to authoritative events but never creates or overrides event, payment, eligibility, admission or attendance truth.  
B08 Time is explicit. Event and operational timestamps retain timezone context; server timestamps provide ordering/audit authority.  
B09 Ownership and acting context are explicit for consequential host actions.  
B10 External provider state and Joy state are reconciled deliberately; provider callbacks/webhooks are not assumed to arrive once, in order or immediately.

2 — CORE DOMAIN OBJECTS & RELATIONSHIPS  
Identity: durable authenticated person/account reference for protected actions.  
Organization: durable hosting entity separate from individual members.  
Organization Membership: relationship granting scoped authority to act for an organization.  
Event: durable event record with ownership, lifecycle, configuration and history.  
Event Capability Configuration: activated optional behavior such as paid admission, restriction, physical check-in or virtual access.  
Participant Relationship: person/guest relationship to an event; distinct from payment, credential and attendance.  
Registration/RSVP: commitment record for a free or registration-based participation model.  
Order: commercial purchase intent/result for paid participation.  
Payment: provider-backed monetary state associated with an order.  
Admission: authoritative entitlement to enter/join under defined conditions.  
Credential: presentation mechanism referencing an admission; never the source of entitlement truth by itself.  
Check-in: event-day assertion that an eligible admission/participant was admitted at a point in time.  
Invitation: host-authorized distribution/access artifact; does not itself guarantee eligibility, capacity or admission unless explicitly configured as entitlement.  
Communication: event-related message/notification with reason, audience and delivery state.  
Event Discussion: event-scoped participant/host message-board content and moderation state; never a general direct-message graph.  
Ask Host Conversation: event-scoped user↔assistant support thread used to answer bounded event questions and triage concerns; may escalate to a host-contact case without exposing private host contact information by default.  
Audit Event: append-oriented record of consequential change, actor/context and result.  
Gamification Event: derived recognition of a qualifying authoritative action.

3 — OWNERSHIP, MEMBERSHIP & PERMISSIONS  
O1 Every event has exactly one authoritative owner context: an individual identity or an organization.  
O2 Organization-owned event data survives membership changes and is not owned by the employee/member who created it.  
O3 Acting context must be resolved before create/publish/material-change/cancel/refund/operator-management actions when the identity can act in multiple contexts.  
O4 Losing organization permission removes future authority; it does not erase historical attribution.  
O5 A user may be both participant and authorized host/operator for the same event when legitimately configured. Permissions are additive by relationship, not permanent account type.  
O6 Basic Beta organization permissions may collapse to owner/admin-equivalent authority. MVP may introduce scoped management/operator roles, but every permission must map to explicit actions.  
O7 Client-hidden controls are not authorization. Every consequential action is re-authorized server-side.  
O8 Admin/support intervention uses separate privileged authority, requires reason/context where consequential and is audited.

4 — EVENT LIFECYCLE  
Authoritative event lifecycle states:  
DRAFT — editable, not publicly committed as a published event.  
PUBLISHED — available through its configured visibility/access rules before active occurrence.  
IN\_PROGRESS — the event occurrence/operational window is active where the event requires an explicit operational lifecycle state.  
CANCELLED — event will not occur under the active event instance; historical event remains.  
COMPLETED — event occurrence has ended and is retained for history/continuation.

Postponement/rescheduling is a material-change condition on a published event, not a destructive replacement. The event retains its identity unless product policy explicitly requires a successor occurrence.

Allowed primary transitions:  
DRAFT → PUBLISHED when required readiness invariants pass and actor is authorized.  
DRAFT → abandoned/deleted only under retention/deletion policy; draft disappearance is not equivalent to cancellation.  
PUBLISHED → PUBLISHED through non-material edits or completed material-change workflow.  
PUBLISHED → IN\_PROGRESS when the event occurrence begins or an approved operational transition activates the event.  
PUBLISHED → CANCELLED through explicit authorized cancellation.  
PUBLISHED → COMPLETED when an explicit In Progress state is unnecessary and the event occurrence/end permits direct completion.  
IN\_PROGRESS → COMPLETED after event occurrence/end and required operational settlement rules permit completion.  
IN\_PROGRESS → CANCELLED only where cancellation during active operation is a legitimate event outcome and its consequences are explicitly handled.  
CANCELLED and COMPLETED are terminal for the original occurrence except narrowly authorized administrative correction. Repeating/duplicating creates a new draft.

Event invariants:  
E1 Published event has valid owner, title, format, start/end semantics, visibility/access model and at least one valid participation path or explicit information-only disposition if that is later approved.  
E2 End cannot precede start. Multi-day/series exceptions must be modeled explicitly rather than violating this invariant.  
E3 Public presentation never exposes protected private/restricted fields.  
E4 Material changes after participant commitment must evaluate notification and affected participation/admission/payment obligations before finalization.  
E5 Cancellation invalidates future operational admission to the cancelled occurrence and triggers applicable participant/payment handling; it does not erase prior transactions/history.  
E6 Event completion does not silently delete participant/order/admission/audit history.

5 — VISIBILITY, ACCESS & ELIGIBILITY  
Visibility states: PUBLIC; UNLISTED; PRIVATE. Visibility controls findability/presentation, not authorization by itself.  
Access policy may additionally require invitation/access token, authentication, eligibility or a combination.

A private/unlisted URL is not proof of authorization. Protected event details are returned only after applicable access rules pass.

Eligibility states when activated: NOT\_REQUIRED; UNKNOWN; PENDING; ELIGIBLE; INELIGIBLE; EXPIRED/REVALIDATION\_REQUIRED where assurance expires.

Eligibility invariants:  
A1 Unrestricted public evaluation does not require an account.  
A2 Restricted protected content/actions are unavailable until the required assurance threshold is met.  
A3 Eligibility success does not imply capacity, payment or admission success.  
A4 Eligibility denial does not reveal unnecessary sensitive verification detail.  
A5 Eligibility method and retained evidence must follow Legal/Safety and minimization requirements.

6 — CAPACITY & PARTICIPATION  
Capacity applies to the authoritative participation/admission unit defined for the event. Capacity checks are atomic at commitment time.

Free registration/RSVP states: STARTED/DRAFT where partial capture is intentionally retained; CONFIRMED; WITHDRAWN/CANCELLED; WAITLISTED when waitlist is activated; REJECTED/UNAVAILABLE where commitment cannot be accepted.

Participation invariants:  
P1 A user retry cannot create multiple active registrations for the same intended participant/event relationship unless the event explicitly supports multiple distinct admissions/guests.  
P2 Capacity cannot be oversold by concurrent requests. The final capacity claim and confirmation occur atomically or through an equivalent reservation mechanism.  
P3 A displayed available spot is informational until authoritative commitment succeeds.  
P4 Withdrawal releases capacity only when policy says that participation consumed capacity and no non-releasable entitlement remains.  
P5 Waitlist status is not confirmed admission. Promotion requires explicit transition behavior and notification; silent UI reinterpretation is prohibited.  
P6 Guest/plus-one records must remain attributable to the controlling registration/order without pretending each guest has an authenticated identity.

7 — PAID ORDER & PAYMENT BEHAVIOR  
Order states: CREATED; PAYMENT\_PENDING; PAID; PAYMENT\_FAILED; CANCELLED; PARTIALLY\_REFUNDED where supported; REFUNDED; DISPUTED/CHARGEBACK where provider/payment model requires it.

Payment attempt state may be more granular internally, but user-visible success requires authoritative provider-confirmed success or an approved equivalent.

Payment invariants:  
M1 Unknown/pending payment is never shown as paid.  
M2 Retry/idempotency prevents duplicate charge creation for one intended purchase.  
M3 Capacity and payment are coordinated so Joy does not knowingly issue more valid paid admissions than capacity. Exact hold/authorization sequence is implementation-owned but must define expiry and recovery.  
M4 Paid admission is created/activated only after required payment success, except explicit complimentary/zero-value paths.  
M5 Refund changes monetary state and may change admission validity according to policy; both changes are auditable.  
M6 Provider webhook/event replay is idempotent. Out-of-order provider events cannot regress settled truth without explicit reconciliation rules.  
M7 Joy does not claim refund completion until provider/merchant-of-record state supports it.  
M8 Transfer, if activated, cannot create two simultaneously valid owners/credentials for one non-duplicable admission.

8 — ADMISSION & CREDENTIALS  
Admission states: PENDING where prerequisite remains; VALID; USED where single-entry semantics apply; REVOKED; REFUNDED\_INVALID; CANCELLED\_EVENT\_INVALID; TRANSFER\_PENDING where supported; TRANSFERRED/INVALIDATED; EXPIRED where time-bound.

Credential states: ACTIVE; ROTATED/REPLACED; REVOKED; EXPIRED. A QR/token is a reference/presentation mechanism and can be rotated without changing the underlying admission unless policy requires it.

Admission invariants:  
AD1 Credential possession alone is insufficient when server/degraded authoritative rules say admission is invalid.  
AD2 Refunded/revoked/cancelled-event admissions cannot successfully check in.  
AD3 Duplicate credential presentation must resolve against admission/check-in truth, not merely QR uniqueness.  
AD4 Credential rotation invalidates prior presentation artifacts as appropriate without creating duplicate entitlement.  
AD5 Entitlements such as VIP/staff/vendor access are explicit attributes/relationships and do not emerge from gamification status.

9 — CHECK-IN & ATTENDANCE  
Check-in result states include SUCCESS; ALREADY\_USED/DUPLICATE; INVALID; WRONG\_EVENT; NOT\_YET\_VALID/EXPIRED; ELIGIBILITY\_REQUIRED; MANUAL\_REVIEW/EXCEPTION; UNKNOWN\_OFFLINE where degraded mode cannot safely resolve immediately.

Check-in invariants:  
C1 Successful check-in is idempotent for the same intended entry operation.  
C2 A duplicate scan never creates duplicate attendance.  
C3 Operator override requires authorized role and an audit reason/context appropriate to risk.  
C4 Re-entry, when activated, is a policy separate from initial admission and must not be approximated by clearing check-in history.  
C5 Multiple lanes/devices reconcile to one authoritative admission/check-in history.  
C6 Degraded-connectivity operation must define which decisions can be made locally, which must wait, conflict resolution and later reconciliation. Before external physical-event testing, this behavior must be tested against duplicate-use and stale-roster scenarios.  
C7 Printed/manual fallback does not erase the requirement to reconcile resulting attendance/exception state.

10 — INVITATIONS, DISTRIBUTION & COMMUNICATIONS  
Invitation states: CREATED; SENT/SHARED where delivery is known; OPENED/VISITED only where privacy-appropriate attribution exists; ACCEPTED/CONVERTED where linked commitment succeeds; REVOKED/EXPIRED where configured.

Invitation invariants:  
I1 Invitation delivery is not registration/admission success.  
I2 Revoking an invitation does not automatically revoke an already-created legitimate registration/admission unless policy explicitly couples them.  
I3 Direct invitation/audience reuse must respect consent and communication rules.  
I4 Share/Feed attribution may record acquisition source without creating a person-centered social graph.  
I5 Feed presentation is downstream of authoritative event/access state. Feed content or promotion cannot make a private, restricted, cancelled, unavailable or ineligible event actionable beyond its actual rules.  
I6 Home presentation preference (Participant-forward, Host-forward or Mixed) changes information hierarchy only; it never grants/revokes hosting, organization, event or participant authority.

Communication states: QUEUED; SENT\_TO\_PROVIDER; DELIVERED where provider confirms; FAILED; SUPPRESSED/NOT\_SENT where policy/preferences prevent delivery. Provider acceptance is not necessarily end-recipient delivery.

Material-change and cancellation communications are generated from authoritative event/affected-participant state, with retry/idempotency and auditability.  
Discussion invariants: event discussion is scoped to one event; access follows event/relationship policy; removing or moderating discussion content cannot rewrite event, admission, payment or attendance truth; no participant-to-participant DM entitlement is implied.  
Ask Host invariants: host controls whether the assistant is enabled for an event; automated responses must be grounded in permitted authoritative event information and identify automation appropriately; the assistant cannot create/change registration, admission, refund, eligibility, access, event policy or other consequential state through conversational assertion; insufficient confidence, host-judgment questions, safety/trust concerns, or explicit human-contact requests must offer/escalate to a permitted host-contact workflow. Escalation records status and preserves only permitted useful context.

11 — VIRTUAL/HYBRID ACCESS  
Protected virtual join data is separate from public event content and is released only when access/admission/time policy permits.

Virtual access invariants:  
V1 Public page rendering never leaks protected join credentials.  
V2 Changed/revoked join information invalidates obsolete protected presentation as practical.  
V3 Virtual access success does not imply physical check-in and vice versa unless a hybrid policy explicitly links them.  
V4 External video-platform availability is not treated as Joy transactional success; Joy must represent unavailable/changed access without fabricating control over the provider.

12 — MATERIAL CHANGE, RESCHEDULING & CANCELLATION  
A material change is a published-event change that can reasonably affect a participant’s decision, eligibility, admission, payment obligation or ability to attend. Candidate triggers include date/time, venue, format, material access restrictions, material scope, cancellation/postponement and other policy-defined changes.

Material-change workflow:  
1\. Authorized host proposes change.  
2\. System classifies or asks for confirmation where materiality cannot be safely inferred.  
3\. System identifies affected participant/admission/order obligations.  
4\. Required consequence policy is resolved: notify, re-confirm, preserve, invalidate, offer transfer/refund or block change pending resolution.  
5\. Change commits atomically with historical record and downstream work intent.  
6\. Delivery/provider failures do not roll back authoritative event truth but remain visible operational failures requiring retry/escalation.

R1 Rescheduling preserves original event relationship/history.  
R2 Existing admissions/orders are never silently reinterpreted when the material change alters what was purchased/accepted.  
R3 Cancellation is explicit and irreversible by ordinary host edit; a new/replacement event is a new occurrence relationship.  
R4 Refund entitlement policy is not invented by the UI. Product/business/legal policy determines eligibility and system enforces it consistently.

13 — FAILURE, RETRY & RECOVERY SEMANTICS  
Consequential commands resolve to SUCCESS, REJECTED, PENDING/UNKNOWN, or SAFE\_FAILURE with retained user input where practical.

F1 Network timeout after command submission is not proof the command failed. Client must reconcile by stable operation/object identity before retrying consequential creation.  
F2 Retried create/purchase/refund/check-in commands carry idempotency identity or equivalent duplicate protection.  
F3 Stale client data cannot overwrite newer consequential state without conflict detection/merge policy.  
F4 Optimistic UI may be used only for reversible/non-authoritative interactions. Payment, eligibility, publish, cancellation, refund and check-in success require authoritative confirmation.  
F5 Provider outage preserves distinguishable pending/failed state and a recovery path.  
F6 Partial workflow completion is explicit. Example: event change committed but some notifications failed; do not pretend either that the change failed or that all notices succeeded.  
F7 User-entered draft/configuration data should survive recoverable errors and navigation where safe.  
F8 Error messages expose actionable state without leaking protected internals.

14 — CONCURRENCY & CONFLICT RULES  
CC1 Capacity claims serialize/atomically validate against the same authoritative capacity pool.  
CC2 Concurrent host edits to consequential fields use version/conflict detection; last-write-wins is not acceptable when it can silently overwrite material event truth.  
CC3 Check-in uses atomic compare/update or equivalent protection against simultaneous duplicate admission.  
CC4 Payment/refund provider events reconcile using provider event identity and monotonic business rules, not arrival order alone.  
CC5 Membership/permission changes take effect for subsequent commands immediately enough to prevent a removed actor from continuing consequential operations from stale UI.  
CC6 Credential rotation/revocation propagates to validation authority; cached/degraded behavior must define staleness bounds and conflict handling.  
CC7 Duplicate event creation caused by retry is prevented where the same creation intent can be identified; intentional duplication remains an explicit user action.

15 — GAMIFICATION SYSTEM BEHAVIOR  
Gamification events are derived from qualifying authoritative transitions. Examples: first legitimate publish; first confirmed participation; first completed hosted event; first valid check-in/attendance where attendance is known; repeat hosting.

G1 No award on optimistic intent alone for consequential milestones.  
G2 Reversal/correction behavior must be defined. Fraudulent, corrected or invalidated source actions cannot leave misleading achievements where integrity requires revocation.  
G3 Points/XP, if activated, are non-monetary and cannot grant admission, eligibility, refund priority or organization authority.  
G4 Achievement processing is idempotent; replayed source events do not duplicate rewards.  
G5 Progression may span host and participant activity under one identity but does not collapse contextual permissions.  
G6 Reputation/trust remains separate from gamification. Achievement badges cannot masquerade as verification or host-quality assurance.  
G7 A Verified marker, when activated, represents only a specifically defined assurance actually completed; it does not imply safety, quality or endorsement beyond that assurance.  
G8 A Super Host or equivalent quality designation remains inactive until sufficient operating history and approved evidence criteria exist; it must be derived from defensible hosting evidence rather than points/XP or popularity alone.

16 — DELETION, RETENTION & CORRECTION  
Ordinary deletion must not be used to conceal or repair consequential historical state.

T1 Draft deletion/abandonment follows retention policy and may be hard/soft deletion according to Technical/Legal requirements.  
T2 Published event, order, payment, refund, admission, check-in and material-change records require retention/audit treatment appropriate to legal/operational needs.  
T3 User correction is represented as correction/version/audit where changing historical consequential truth would otherwise destroy evidence.  
T4 Privacy deletion requests may require de-identification, deletion or legal retention exceptions; Legal/Privacy authority governs exact behavior.

17 — ADMIN, SUPPORT & TRUST INTERVENTION  
Admin actions are explicit privileged commands, not direct invisible data editing in normal operations.

A01 Inspect only information required for authorized support/testing/trust purpose.  
A02 Disable/restrict user/event/access only under approved operating policy and audit actor, reason, time and affected object.  
A03 Manual payment/admission/check-in correction distinguishes correction from original event and preserves history.  
A04 Support tooling must not bypass organization ownership or participant privacy merely because the UI exposes an admin surface.

18 — STATE DERIVATION & DISPLAY RULES  
The UI may derive friendly summaries such as “Ready to publish,” “Sold out,” “Starts soon,” “Checked in,” or “Needs attention,” but the underlying authoritative states remain separately inspectable by the system.

D1 A summary label cannot create a new hidden business state unless formally added here.  
D2 “Ready” is derived from readiness invariants and does not equal PUBLISHED.  
D3 “Sold out” derives from capacity availability; it does not change event lifecycle.  
D4 “Attended” requires a valid attendance basis defined by the event model; registration alone is not attendance.  
D5 “Completed” event status is distinct from every participant having attended or every commercial dispute being resolved.

19 — DOMAIN EVENTS / DOWNSTREAM INTEGRATION CONTRACT  
Implementation may use domain events or equivalent transactional signals. At minimum, downstream architecture must be able to react reliably to consequential transitions including:  
EventDraftCreated; EventPublished; EventStarted/InProgress where activated; EventMateriallyChanged; EventRescheduled; EventCancelled; EventCompleted; RegistrationConfirmed; RegistrationWithdrawn; WaitlistEntered/Promoted where activated; PaymentSucceeded; PaymentFailed; RefundSucceeded/Failed; AdmissionIssued; AdmissionRevoked/Transferred where activated; CheckInSucceeded/Rejected/Overridden; InvitationCreated/Sent/Revoked; CommunicationFailed; OrganizationPermissionChanged; EligibilityChanged; GamificationMilestoneQualified. Feed ranking/presentation may consume approved event/content signals but does not become authoritative domain truth.

Names are conceptual, not API contracts. Delivery must be idempotent/replay-safe where side effects depend on them.

20 — PROTOTYPE VERSUS WORKING SYSTEM  
Gate 2 may represent states and transitions interactively without production persistence/providers. It must not simplify away distinctions that would force product invention later: paid success versus pending/failure; eligibility pass versus pending/fail; registration versus admission; credential versus entitlement; event cancellation versus deletion; material change versus ordinary edit; host versus organization acting context.

Gate 3 Working Beta must persist and enforce the Beta-active subset of these rules. Gate 4 external testing activates only domains whose operational/legal dependencies are satisfied. Gate 5 Working MVP must enforce the complete MVP-active subset.

21 — DOMAIN/SYSTEM BEHAVIOR EXIT  
The core domain now has explicit ownership, event, access, participation, payment, admission, credential, check-in, communication, virtual-access, material-change, failure, concurrency, gamification, retention and admin semantics sufficient to constrain implementation.

Remaining decisions are implementation or launch-policy decisions rather than missing domain architecture: exact DB schema/constraints; API contracts; provider-specific payment orchestration; exact eligibility assurance provider/method; exact degraded-connectivity cache/reconciliation implementation; exact communication provider/channel mechanics; legal retention durations; and final promotion/removal of features explicitly marked as candidates.

Authority boundary  
02.01.01 Sontu Event Model & Capability Catalog owns shared domain meaning during Stage 0\. This document owns detailed candidate invariants, transition semantics, concurrency, recovery and failure behavior only where consistent with upstream Sontu authorities. It does not authorize implementation, schema/API design, or gate movement.

Sontu invariant corrections  
S1 — One governed event state. Participant, standard-host, advanced Control Center, operational-role and future AI/agent surfaces read and act on the same authoritative event state. A surface-specific convenience state must not become a parallel source of truth.  
S2 — Actor, person, account and party are distinct. An account is an authentication/access mechanism, not the universal human primitive. Accountless low-consequence participation is valid when policy permits.  
S3 — Commitment is polymorphic. Invitation, interest, application, approval, registration, reservation, payment and other commitment forms remain distinct and may compose. No universal RSVP state machine is canonical.  
S4 — Entitlement is first-class truth. Payment, order, registration, credential, QR and check-in are not entitlement. A credential presents or references authority; it does not create authority.  
S5 — Party-aware capacity. Capacity/inventory may be consumed by a person, party, seat, slot, resource, admission unit, activity or other configured unit. Atomic allocation protects the authoritative pool.  
S6 — Composite events inherit deliberately. Activities/sub-events may inherit owner, visibility, access, time, capacity, program, communication or other policy from a parent and may override only where the domain explicitly permits. Parent changes must evaluate affected descendants and commitments.  
S7 — Roles are scoped relationships. Host, staff, volunteer, speaker, exhibitor/vendor, door/check-in operator and other operational roles grant only the capabilities required for their scope. Role labels never substitute for explicit permission checks.  
S8 — Change propagation is a domain operation. Material changes determine affected parties, descendants, entitlements, commitments, payments, assignments and required communication/reconfirmation/refund/cancellation actions before consequences are considered settled.  
S9 — Closure is deliberate. Closed/Completed means the event has reached its stable post-event disposition under applicable policy, not merely that wall-clock end time passed. Higher-consequence events may require a Reconciling state before closure. Archived is a presentation/record-management condition, not event lifecycle truth.  
S10 — Attendance is evidence-based. Registration, entitlement or lack of check-in does not alone prove attendance or no-show. Attendance evidence can remain unknown/unverified and should record event/host/platform-caused exceptions where material.  
S11 — Check-in is contextual. Events that do not need physical/virtual admission operations do not inherit check-in machinery. Where check-in exists, duplicate/re-entry/degraded-mode behavior reconciles to one attendance/admission history.  
S12 — Event-scoped media and interaction remain event state. Visibility, contribution, moderation and retention are governed by event/role policy and do not create a general social graph or platform engagement system.  
S13 — Sensitive contextual state is purpose-bound. Accessibility/accommodation, eligibility and similar sensitive information receives least-privilege access and expiry/de-identification treatment when its event purpose ends unless retention is justified.  
S14 — Event-specific game mechanics may exist when they improve the event. Generic platform XP, streaks, levels, popularity progression or reputation-linked gamification are not Sontu domain primitives and cannot confer entitlement, trust, eligibility or authority.  
S15 — AI/agent actions are attributable governed commands. An agent acts under an identified authorizer, scoped permission and confirmation policy; conversational assertion never mutates consequential truth by itself.  
S16 — External providers are subordinate integrations. Payment, messaging, maps, calendar, media, identity/assurance or other providers may contribute authoritative evidence within their domain, but Sontu explicitly reconciles that evidence into governed event state and represents provider uncertainty/failure honestly.

Lifecycle direction  
Candidate canonical lifecycle semantics for later Gate 1 detailed design are: DRAFT; PUBLISHED/SCHEDULED; LIVE/IN\_PROGRESS only where operationally meaningful; RECONCILING only where unresolved consequence requires it; CLOSED/COMPLETED; CANCELLED; plus governed postponement/rescheduling and publication withdrawal where required. Failure and concurrency doctrine

N88-G2 MINIMUM AUTHORITATIVE COORDINATION STATE — 2026-09-07

Purpose and boundary  
This section pressure-tests the progressive H-A→H-H / P-A→P-G journey against the smallest state Sontu must own to preserve Form B coordination value. “Own” means Sontu requires governed authoritative state for the coordination consequence; it does not imply Sontu must implement the specialist workflow, store every provider detail, or become the external domain’s system of record. This is domain/requirements reasoning only. It does not select schema, APIs, providers, UI architecture, persistence technology, prototype scope or N88-G3 implementation architecture.

MINIMUM CORE STATE — MUST BE SONTU-GOVERNED

C1 — UNDERTAKING IDENTITY. A durable Event Instance identity is required so rename, reschedule, postponement, material change and closure modify/reconcile the same undertaking rather than producing disconnected records. Where recurrence exists, Series/Program identity is separately durable and instances retain independent identity/history.

C2 — OWNER / ACTING AUTHORITY. Sontu must know the authoritative owner context and enough scoped actor/delegation/role state to determine who may create, activate, materially change, cancel, close or perform other consequential coordination actions. External identity/organization providers may supply evidence; they do not replace Sontu’s event-scoped authority interpretation.

C3 — CURRENT SHARED EVENT TRUTH. Sontu must own the coordination-relevant current facts required for affected parties to understand the undertaking: purpose/identity, relevant time, place/access/format, lifecycle, and the configured visibility/access/distribution context. Specialist detail that does not alter cross-party coordination remains external.

C4 — CONSEQUENCE-RELEVANT RELATIONSHIPS / PARTIES. Sontu must represent the people/parties/organizations whose commitments, roles, preparation, entitlements or required actions materially affect coordination. This does not require a universal participant account or full CRM/contact profile.

C5 — COORDINATION COMMITMENT STATE. When Sontu is responsible for knowing whether a party is expected, accepted, declined, registered, reserved, waitlisted, approved, reconfirmed, released or otherwise committed, it must hold the minimum authoritative commitment state and provenance necessary to act on it. Commitment remains polymorphic; Sontu does not force every event into RSVP semantics.

C6 — ENTITLEMENT / REQUIRED-ACTION INTERPRETATION. Where a participant’s right or obligation materially affects event coordination, Sontu must know the coordination-relevant entitlement or required-action state. The underlying payment, ticketing, eligibility or specialist provider may remain authoritative for its own transaction/evidence. Sontu must distinguish known, pending, stale, failed and unresolved provider-derived evidence rather than fabricate settled truth.

C7 — MATERIAL CHANGE / CONSEQUENCE STATE. Sontu must preserve what consequential event truth changed, when, under whose authority, which governed relationships are affected, and what follow-up state is required: notice, reconfirmation, release, cancellation, refund/transfer handling, provider reconciliation or another explicit consequence. This is a primary Form B ownership candidate because without it Sontu cannot maintain cross-party continuity.

C8 — READINESS / UNRESOLVED COORDINATION STATE. Sontu must be able to derive or record the unresolved conditions that prevent credible activation, operation or closure: missing required truth, unresolved consequential commitments, capacity conflict where Sontu owns/reconciles it, provider uncertainty, permission failure, required participant action, failed material-change delivery/reconciliation, or other configured blocker. “Needs attention” is derived presentation, not a parallel business state.

C9 — LIFECYCLE / CLOSURE STATE. Sontu must know whether the Event Instance is Draft, Published/Scheduled, Live/In Progress where meaningful, Reconciling where consequence requires it, Closed/Completed, Cancelled or under a governed postponement/rescheduling/publication-withdrawal condition. Closure preserves history and unresolved commercial/provider evidence as appropriate rather than deleting it.

C10 — PROVENANCE / CONSEQUENTIAL HISTORY. Sontu must retain enough actor, time, source/provider, previous/current state and outcome provenance to reconstruct material event truth and explain consequential changes. This is not a requirement for indiscriminate telemetry or permanent retention of all event content.

CONDITIONAL STATE — SONTU OWNS ONLY WHEN THE EVENT/JOURNEY ACTIVATES THE CONSEQUENCE

K1 Capacity/inventory allocation: native when Sontu accepts/controls the relevant commitment pool; otherwise reference/reconcile specialist availability where reliable.  
K2 Eligibility/assurance: Sontu owns the event-policy interpretation and resulting coordination status when needed; verification evidence/provider workflow may remain external and minimized.  
K3 Payment/order/refund: Sontu owns only the coordination consequence and reconciled status necessary for event truth unless commercial validation later justifies native merchant/order ownership.  
K4 Admission/credential/check-in: activate only where access operations materially require them. Entitlement remains distinct. Credential/check-in mechanics are not universal event primitives.  
K5 Organization/team operations: activate scoped roles/delegation only where multiple actors require differentiated authority.  
K6 Assignments/tasks/resources/program/space: activate only where their state materially changes cross-party readiness, responsibility, handoff or outcome. Specialist planning/project tools remain external otherwise.  
K7 Event-scoped media/interaction: native only when event context, contribution rights, moderation or closure materially benefit from Sontu ownership; never a general social graph.  
K8 Sensitive preparation/accommodation state: native only for a defined event purpose, with least privilege and expiry/de-identification treatment.  
K9 Attendance evidence: native/reconciled only where the event outcome or follow-up depends on credible attendance evidence. No scan does not equal no-show.  
K10 Intelligence/agent state: derived/advisory. Intelligence may interpret C/K state and propose actions but does not become a separate source of consequential truth.

EXTERNAL BY DEFAULT — DO NOT OWN WITHOUT NEW EVIDENCE

General CRM/contact history; general-purpose calendar; full payment processing/merchant ledger; specialist ticketing inventory where Sontu does not control admission; payroll/workforce management; general project/task management; conferencing/video infrastructure; media editing/storage infrastructure beyond justified event-scoped needs; CAD/floorplanning/venue-production suites; general LMS; sports scoring; fundraising platforms; advertising marketplace; general messaging/social feed/network; provider-specific operational internals. Sontu may integrate or retain coordination-relevant references/evidence without reproducing these systems.

N88-G2 FORM B ↔ FORM C STATE-OWNERSHIP CHALLENGE — 2026-09-07

Question  
Which elements of the C1–C10 minimum coordination core genuinely require Sontu-governed authoritative state, and which could instead be reconstructed/orchestrated from external systems under Form C? This is an internal falsification exercise. Form C receives the benefit of the doubt wherever orchestration can preserve consequence integrity with materially lower burden. No external validation, implementation architecture or N88-G3+ work is authorized.

Decision rule  
A state belongs natively in Sontu only when at least one of the following is true: (1) no dependable external authority exists for the cross-party coordination fact; (2) Sontu must decide a consequence that spans multiple external authorities; (3) reconstructing the fact on demand would be ambiguous, stale or unable to preserve material history; or (4) Sontu itself creates the governed relationship/commitment and therefore cannot truthfully delegate its authority elsewhere. Otherwise Form C may reference, derive or reconcile the state without owning a duplicate authoritative copy.

C1 — UNDERTAKING IDENTITY  
Form C challenge: derive an event context from calendar/ticketing/venue/project/event-suite identifiers and maintain a mapping layer.  
Result: NATIVE MINIMUM SURVIVES, but narrower than a full event record. No external system is guaranteed to represent the same undertaking across calendar, invitation, payment, venue, participant and operational systems. Sontu therefore needs a stable coordination-context identity if it promises cross-system continuity. External identifiers attach to that context rather than replace it. If Sontu supports only one upstream event system in a bounded integration mode, the upstream ID could temporarily anchor identity; that would be a Form C implementation path, not a universal product invariant.

C2 — OWNER / ACTING AUTHORITY  
Form C challenge: rely entirely on upstream account/organization permissions.  
Result: HYBRID; SONTU-GOVERNED CONSEQUENCE AUTHORITY SURVIVES. Identity proof and organization membership may be external, but Sontu cannot safely execute its own material-change, closure, participant-notice or cross-provider reconciliation actions without knowing who is authorized for the Sontu coordination context. Sontu needs scoped authority interpretation and provenance, not a general IAM/organization directory.

C3 — CURRENT SHARED EVENT TRUTH  
Form C challenge: compute the current event view dynamically from calendar, ticketing, venue, conferencing and other systems.  
Result: CONDITIONAL SURVIVAL. Pure reconstruction is viable only when one upstream source clearly owns each consequential fact, freshness is sufficient, conflicts are resolvable and historical meaning is not lost. Once multiple providers can disagree—or Sontu allows a host to make a coordination-level change not owned by one provider—Sontu requires a governed canonical interpretation of the minimum shared truth. This may consist of authoritative values plus external references/evidence rather than copying all provider fields.

C4 — CONSEQUENCE-RELEVANT RELATIONSHIPS / PARTIES  
Form C challenge: query attendee/contact/ticket/CRM systems when needed.  
Result: CONDITIONAL / MINIMIZE. Sontu does not need a native universal participant directory. It does need a stable event-scoped party reference when Sontu must track a commitment, entitlement consequence, required action, material-change acknowledgement or closure consequence across provider boundaries. If no Sontu-owned consequence persists for a party, external reference or ephemeral resolution is sufficient.

C5 — COORDINATION COMMITMENT STATE  
Form C challenge: treat ticketing/RSVP/registration systems as commitment authorities and aggregate their results.  
Result: HYBRID. Provider-owned commitments should remain provider-authoritative. Native Sontu commitment state is justified only for commitment mechanisms Sontu itself offers or for a cross-provider coordination interpretation that no single provider can represent. Therefore C5 is not universally native. Canonical requirement becomes: Sontu must know the authoritative commitment result and provenance; it owns the commitment only when Sontu creates/governs it.

C6 — ENTITLEMENT / REQUIRED-ACTION INTERPRETATION  
Form C challenge: derive rights/obligations directly from ticket/payment/eligibility/task providers.  
Result: COORDINATION INTERPRETATION SURVIVES; SOURCE STATE EXTERNAL BY DEFAULT. Sontu should not duplicate merchant/ticket/verification ledgers. It needs only the consequence-relevant interpretation required to decide what the event coordination flow may do, together with freshness/provenance/uncertainty. This is strongest as a reconciled projection rather than a second transaction authority.

C7 — MATERIAL CHANGE / CONSEQUENCE STATE  
Form C challenge: detect changed fields in upstream systems and send automation from integrations.  
Result: STRONGEST NATIVE SURVIVOR. A material change can affect commitments, entitlements, payments, access, preparation, communications, assignments and multiple providers simultaneously. No specialist source reliably owns the cross-domain consequence graph. If Sontu’s distinctive promise includes maintaining continuity when event truth changes, it needs governed change identity, affected-state determination, required consequences, resolution status and history. A Form C integration layer could technically implement this, but the moment it persists/decides those consequences it has become an authoritative coordination state layer in substance. This is the clearest boundary where Form C converges toward Form B.

C8 — READINESS / UNRESOLVED COORDINATION STATE  
Form C challenge: calculate readiness on demand from external status checks.  
Result: DERIVED, NOT INDEPENDENT AUTHORITY. Readiness should normally be computed from authoritative/reconciled C/K state. Persistent unresolved-work records are justified where an issue must survive sessions, be assigned/resolved or block a consequential transition. A generic native readiness status is unnecessary and risks becoming hidden duplicate state.

C9 — LIFECYCLE / CLOSURE STATE  
Form C challenge: infer lifecycle from time/calendar/upstream event status.  
Result: NATIVE COORDINATION LIFECYCLE SURVIVES IF SONTU OWNS CROSS-PARTY CONSEQUENCES. Calendar time cannot establish deliberate closure, reconciliation or cancellation consequences. If Sontu only observes an upstream event system whose lifecycle is sufficient, Form C may reference it. If Sontu governs C7 or any unresolved cross-provider consequence, it requires a coordination lifecycle/closure disposition independent of provider lifecycle labels.

C10 — PROVENANCE / CONSEQUENTIAL HISTORY  
Form C challenge: rely on provider histories/logs and query them when explanation is needed.  
Result: MINIMUM NATIVE PROVENANCE SURVIVES. External histories are fragmented, have different retention/semantics and may not record Sontu’s cross-provider interpretation or action. Sontu needs provenance for the consequential decisions/actions it makes and the evidence it relied on. It does not need to mirror complete provider histories.

REVISED OWNERSHIP CLASSIFICATION  
Hard native coordination core: C1 coordination-context identity; C2 Sontu consequence authority; C7 material-change/consequence state; C9 coordination lifecycle/closure when Sontu governs consequences; C10 provenance for Sontu decisions/actions.  
Hybrid/reconciled core: C3 current shared truth; C4 event-scoped parties; C5 commitments; C6 entitlement/required-action interpretation. These should remain external-authoritative wherever a dependable specialist authority exists and become Sontu-native only for Sontu-created relationships or cross-provider interpretations that cannot be delegated coherently.  
Derived/operational projection: C8 readiness/unresolved summary, with persistent issue/work records only where consequence requires durable resolution.

FORM C CONVERGENCE TEST  
A genuine Form C remains possible if Sontu can map an upstream event identity, rely on upstream authority/lifecycle, read provider-owned commitments/entitlements, and offer useful intelligence/automation without becoming responsible for cross-provider material-change consequences. In that case C1/C2/C9 may be mostly references and C7 may be simple automation history.

However, if Sontu promises that a host can change event truth once and have affected parties, commitments, entitlements, providers and unresolved consequences remain coherently reconciled, then Form C must persist C7 plus enough C1/C2/C9/C10 to govern it. At that point the distinction is not “integration versus state”: the integration layer has become a small coordination system of record. This supports Form B’s conceptual architecture while still allowing most specialist source state to remain external.

FORM B NARROWING  
Form B should therefore not be interpreted as “Sontu owns C1–C10.” The stronger provisional definition is: Sontu owns the minimum cross-party coordination consequences that no specialist system can coherently own, and reconciles specialist-authoritative evidence around them. The irreducible candidate nucleus is Event/Series coordination identity \+ scoped acting authority \+ material-change/consequence ledger \+ coordination lifecycle/closure \+ consequential provenance. Participant, commercial, admission, provider and operational state remains reference/reconciled or conditional unless Sontu itself creates the relationship.

EARLY VALUE IMPLICATION  
This exposes a major requirement for later validation: the product cannot justify Form B merely by storing event data. Early value must come from coordination consequences—especially change propagation, unresolved-action visibility, cross-party continuity and reliable closure—or Form C is preferable. Generic event creation, reminders, RSVP aggregation, dashboards or AI summaries do not justify native coordination authority by themselves.

Five state families survive as the candidate irreducible coordination nucleus; four become hybrid/reconciled rather than universally native; one becomes primarily derived. The strongest reason for Sontu to own state is not event-data centralization but cross-provider consequence governance, particularly material change and deliberate closure.

N88-G2 NARROWED COORDINATION NUCLEUS — FAILURE-SCENARIO PRESSURE TEST — 2026-09-07

Purpose  
Pressure-test whether the narrowed Form B nucleus actually removes consequential coordination failures or merely introduces another synchronization layer. Candidate nucleus under test: coordination-context identity; Sontu-scoped acting authority; material-change/consequence state; coordination lifecycle/closure where Sontu governs consequences; and consequential provenance. Hybrid specialist state remains external-authoritative by default. This is internal requirements reasoning only; no implementation architecture, provider selection, prototype/build work, external respondent work or N88-G3+ movement is authorized.

Decision rule  
For each scenario, Form B earns native authority only if the failure crosses systems/parties, no single specialist authority can resolve the whole consequence, and durable coordination state materially improves correct resolution. If an existing source plus stateless/read-only automation can resolve the scenario safely and with less burden, Form C wins that scenario.

S1 — EVENT RESCHEDULE  
Scenario: a published event moves from Saturday to Sunday. Calendar, invitation/registration, venue, vendor, ticket/payment and participant-preparation systems may hold different representations of the old date.  
Failure without coordination authority: changing one source does not prove which commitments remain valid, who must reconfirm, which provider changes succeeded, whether venue/vendor obligations still align, or whether unresolved parties may be treated as attending. A sequence of integrations can send updates but has no durable cross-provider definition of settled versus unresolved consequence unless one system owns it.  
Form B contribution: C1 preserves the same undertaking; C2 establishes authorized change; C7 records the material change, affected relationships and required consequences; C9 prevents treating the event as settled/closed while required reconciliation remains; C10 records evidence/results. Provider-owned reservations, payments and commitments remain external.  
Verdict: STRONG FORM B CASE when multiple consequential parties/systems exist. FORM C SUFFICIENT for a simple event with one authoritative calendar/registration source and no material cross-system obligation.

S2 — EVENT CANCELLATION  
Scenario: host cancels after participants have committed and some have paid, booked related services or received access entitlements.  
Failure without coordination authority: an event status can become Cancelled while refunds, entitlement invalidation, participant acknowledgement, vendor obligations or replacement arrangements remain unresolved. No payment/ticketing/calendar system necessarily owns all consequences.  
Form B contribution: C7 owns the cancellation consequence set and resolution status, while specialist systems continue to own refunds, transactions and provider-specific cancellation. C9 distinguishes cancelled event truth from completed reconciliation; C10 prevents provider success/failure from becoming invisible.  
Verdict: STRONG FORM B CASE for consequential cancellation. This is one of the clearest reasons to separate event lifecycle from commercial/provider state. Form C wins only where one upstream event platform already coordinates all material cancellation consequences reliably.

S3 — VENUE / ACCESS CHANGE  
Scenario: venue changes after commitments; some participants need travel/accessibility changes, a vendor delivery address changes, and virtual/hybrid access may also change.  
Failure without coordination authority: ordinary notification can announce the new venue but cannot establish that consequence-bearing parties/providers are ready under the new conditions. A participant may be informed while a vendor still targets the old location or an accommodation becomes invalid.  
Form B contribution: C7 can distinguish notification from resolved consequence and preserve affected-party/provider work. C3 remains hybrid: location/access truth may originate externally, but Sontu needs the coordination interpretation when conflicting sources exist.  
Verdict: MODERATE-TO-STRONG FORM B CASE when the change creates obligations beyond awareness. If the only consequence is telling attendees a new address, Form C automation is preferable.

S4 — PARTICIPANT WITHDRAWAL  
Scenario: a participant withdraws after registration/reservation; their place may affect capacity, waitlist, seating, payment/refund, assigned role, guest group or required preparation.  
Failure without coordination authority: broad native participant state would duplicate registration/ticketing systems. Conversely, treating withdrawal as a single upstream status can miss cross-domain consequences.  
Form B contribution: Sontu should not own withdrawal merely because it occurs. If Sontu created the commitment, it owns it; otherwise it reconciles provider authority. C7 becomes native only when withdrawal triggers cross-provider/event consequences that Sontu is responsible for resolving.  
Verdict: HYBRID; NOT AN INDEPENDENT FORM B JUSTIFICATION. This scenario narrows the nucleus: participant commitment/withdrawal is external by default, with native consequence state only when coordination crosses authorities.

S5 — SPECIALIST PROVIDER OUTAGE OR STALE STATE  
Scenario: ticketing, payment, messaging, venue or another provider is unavailable or returns stale/unknown evidence during a consequential event operation.  
Failure without coordination authority: an integration layer may either block everything, optimistically assume success, or lose the distinction between event truth and provider uncertainty. However, persisting a full duplicate provider state creates reconciliation burden.  
Form B contribution: C7/C10 preserve that a required consequence is pending/unknown and what evidence was last known; C9 can block deliberate closure where unresolved consequence warrants it. Sontu does not manufacture provider truth or mirror the provider ledger.  
Verdict: MODERATE FORM B CASE for durable unresolved consequence; NOT justification for duplicating specialist state. Form C remains sufficient when temporary failure has no durable cross-party consequence and safe retry is enough.

S6 — PAYMENT / REFUND MISMATCH  
Scenario: event is cancelled or a participant is released; Sontu expects a refund consequence, but payment provider reports pending, failed, partial, disputed or contradictory status.  
Failure without coordination authority: making Sontu a payment authority would be wrong; relying only on the provider also cannot express whether the event-side obligation has been resolved for the participant.  
Form B contribution: payment/refund truth remains provider-authoritative. Sontu may own only the coordination obligation—e.g. refund required, evidence pending, resolved, exception/escalation—plus provenance. It must never relabel provider uncertainty as monetary success.  
Verdict: STRONG HYBRID BOUNDARY; MODERATE FORM B CASE for obligation reconciliation, ZERO case for native merchant ledger. This validates the narrowed C6 interpretation.

S7 — RECURRING SERIES CHANGE  
Scenario: organizer changes the default venue/time/policy for a recurring program after several future instances already exist, some with commitments or local exceptions.

C7 records which future instances are affected and which require separate consequence handling. C10 preserves divergence/provenance. Existing instance commitments remain their own authoritative/hybrid state.  
Verdict: STRONG DOMAIN CASE for durable series/instance coordination identity and explicit propagation. It supports Form B only if Sontu actually provides cross-instance coordination value; a specialist recurring-event system can satisfy Form C where it already owns these semantics.

S8 — ORGANIZATION REPRESENTATIVE HANDOFF  
Scenario: an employee/volunteer who created or coordinated an organization event leaves or loses authority while the event remains active. Another representative must continue work.  
Failure without coordination authority: tying event authority to creator identity can orphan the event; copying permissions from a general organization directory can overgrant or erase historical responsibility.

External IAM/org membership can provide identity evidence, but Sontu interprets authority for its own consequential coordination actions. C10 preserves who acted under what authority.

CROSS-SCENARIO RESULT  
The narrowed nucleus survives, but not uniformly. The strongest native justification appears when a material change creates a durable cross-provider consequence that must be resolved rather than merely announced. Reschedule, consequential cancellation, recurring-series propagation and organization handoff support the nucleus most strongly. Venue change supports it only when obligations change. Provider outage and payment/refund mismatch support a durable unresolved-consequence/provenance layer but explicitly argue against duplicating specialist truth. Participant withdrawal is primarily hybrid and does not independently justify Form B.

MINIMUM FAILURE-RESOLUTION PRIMITIVE  
Across the scenarios, the common native object is conceptually a governed Consequence Case rather than a broad copy of every domain state. A Consequence Case needs only: coordination context/instance; triggering material fact/change; authorized actor/source; affected event-scoped parties/relationships; required consequence(s); external authority/reference where applicable; status such as unresolved/pending/resolved/exception; evidence freshness/uncertainty; and consequential history. This is a domain primitive, not a schema or UI commitment. It may represent one or multiple linked consequences depending on later architecture.

IMPORTANT NARROWING  
Sontu does not earn authority merely because it can detect a change or send a notification. The native case exists only where Sontu assumes responsibility for knowing whether the cross-party consequence is settled. “Message sent” is not “coordination resolved.” Likewise, a provider transaction succeeding does not prove the event-side obligation is resolved if another affected consequence remains.

FORM C WIN CONDITIONS  
Form C should replace/narrow Form B wherever representative events have one upstream system that already owns the consequential lifecycle; changes are mostly informational; cross-provider obligations are rare; stateless automation plus provider retry is sufficient; or maintaining Consequence Cases forces hosts to manually reconcile Sontu with systems that already know the answer.

This is the clearest internally coherent Form B nucleus found so far. It remains an unvalidated product hypothesis, not a market conclusion.

N88-G2 CONSEQUENCE CASE BOUNDARY TEST — 2026-09-07

Purpose  
Test whether the newly identified Consequence Case can remain a minimal coordination primitive or inevitably expands into a generic workflow/task engine. This is an internal N88-G2 domain test only. It does not define schema, APIs, UI, automation architecture, implementation backlog, prototype scope or N88-G3+ readiness.

Primitive definition under test  
A Consequence Case exists only when a material event fact/change creates a cross-party or cross-authority consequence for which Sontu assumes responsibility for knowing whether the coordination obligation is settled. Minimum semantics: coordination context/instance; trigger; authorized source/actor; affected event-scoped relationship(s); required coordination consequence; external authority/reference where relevant; resolution status; evidence freshness/uncertainty; consequential history.

ANTI-WORKFLOW INVARIANTS  
CW1 — A case is consequence-bound, not work-bound. It represents an obligation/result that must become known as settled, not an arbitrary task someone would like performed.  
CW2 — A case must trace to a governed event fact, material change, closure requirement or Sontu-governed commitment/authority condition. Free-standing to-dos are outside the primitive.  
CW3 — The case records the required outcome and evidence of resolution. It does not require Sontu to model every intermediate step used by a human or specialist system to achieve that outcome.  
CW4 — Assignment is optional and consequence-scoped. A responsible party may be identified where necessary, but Sontu does not thereby become a workforce/project-management system.  
CW5 — Due/urgency semantics exist only when timing changes the event consequence. General deadlines, priorities, kanban stages, estimates, dependencies, subtasks and productivity metadata are not native case semantics by default.  
CW6 — External specialist workflows remain external. A case may reference their object/status/evidence, but Sontu does not reproduce the provider workflow merely to monitor resolution.  
CW7 — A case closes only when its coordination obligation reaches a policy-permitted resolved, waived, superseded, impossible/exception or other explicit terminal disposition. Sending a message, creating a task or invoking a provider is not itself resolution unless that action is the actual required consequence.  
CW8 — Cases are event/series-contextual and do not create a general organization-wide task graph, CRM pipeline or issue tracker.  
CW9 — Case creation must be consequence-proportional. Informational changes that need no durable resolution should produce notification/history only, not cases.  
CW10 — Intelligence may detect/propose/classify cases but cannot invent obligations or mark consequential resolution without governed evidence/authority.

SCENARIO REDUCTION TEST  
1\. Reschedule — Required consequences may include participant reconfirmation, venue/vendor acknowledgement or specialist-state reconciliation. Sontu needs only the obligation and settled/unsettled evidence. It does not need to model phone calls, negotiation steps, vendor task lists or calendar-edit workflows. PASS.  
2\. Cancellation — Cases can represent refund-required, entitlement-invalidated, participant-acknowledgement or vendor-obligation outcomes. Refund execution remains with the payment/provider system; contractual/vendor workflow remains external. PASS.  
3\. Venue/access change — A case is justified only for consequences such as accessibility accommodation invalidated, delivery location requiring acknowledgement or protected access needing replacement. Merely broadcasting a new address creates no case. PASS WITH PROPORTIONALITY.  
4\. Participant withdrawal — A case appears only if withdrawal creates another unresolved coordination obligation such as waitlist promotion, refund handling or assigned-role replacement. Withdrawal itself remains provider/Sontu commitment state according to authority. PASS; confirms the case is not a universal participant workflow.  
5\. Provider outage/stale state — A case may persist an unresolved consequential provider dependency only when the event cannot safely treat the result as irrelevant. Generic integration-health incidents belong to technical operations, not Consequence Cases. PASS WITH DOMAIN SEPARATION.  
6\. Payment/refund mismatch — The case states the event-side obligation and provider evidence uncertainty; it does not model payment operations. PASS.  
7\. Series propagation — A series-level change may create instance-scoped cases where propagation has material consequences. The case does not become a recurrence scheduler or bulk-edit workflow. PASS.  
8\. Organization handoff — A case may represent unresolved Sontu event authority only when the handoff blocks/affects consequential action. General employee onboarding/offboarding remains external IAM/HR. PASS.

TASK-ENGINE RED-LINE TEST  
The primitive fails its boundary and should be redesigned or removed if Sontu needs any of the following merely to make ordinary cases useful: arbitrary user-created tasks unrelated to governed consequences; nested subtasks/checklists as a universal pattern; general project dependencies; organization-wide assignment queues; time tracking; workload/capacity planning for staff; generic comments/collaboration threads; arbitrary custom workflow builders; general SLA/help-desk machinery; sales/CRM stages; broad document approval routing; or specialist operational process modeling. These may exist elsewhere only if independently justified by a future event-specific capability; they are not inherited from Consequence Case.

MINIMUM CASE STATE MACHINE  
Candidate semantic states are deliberately small:  
OPEN/UNRESOLVED — a governed consequence exists and is not yet settled.  
PENDING\_EXTERNAL — resolution depends on external evidence/action whose outcome is not yet authoritative to Sontu.  
RESOLVED — governed evidence establishes the required coordination outcome.  
EXCEPTION — ordinary resolution failed or cannot be established and explicit handling/escalation is required.  
WAIVED/SUPERSEDED — an authorized policy/action removes or replaces the original obligation while preserving history.  
These labels are conceptual and not implementation commitments. More granular provider/task statuses remain external unless later evidence proves they are necessary to distinguish coordination truth.

CASE COMPOSITION RULE  
One material change may create several independently resolvable Consequence Cases when different obligations have different authorities or outcomes. Conversely, multiple affected parties may share one case only when their consequence genuinely resolves as one governed unit. This prevents a single giant workflow object while also preventing meaningless one-case-per-notification proliferation.

RELATION TO C7/C8/C9  
C7 material-change/consequence state is the source/trigger context; Consequence Cases are the durable unresolved/resolved obligations produced where consequence requires persistence. C8 readiness remains derived from open consequential cases plus other authoritative blockers; a case is not a generic readiness task. C9 lifecycle/closure may require selected cases to reach permitted terminal dispositions before stable closure, but not every open informational issue must block event closure.

FORM C CHALLENGE  
Form C still wins when a provider already exposes the needed consequence outcome and Sontu can safely read it without assuming cross-party responsibility. A read-only alert such as “refund pending in provider” does not automatically require a native case. Native Consequence Case authority is justified only when Sontu itself promises to determine whether the event-side obligation across parties/authorities is settled.

INTERNAL DISPOSITION  
The Consequence Case survives the anti-workflow pressure test if kept outcome-oriented, event-scoped, consequence-proportional and deliberately ignorant of intermediate specialist work. It should be treated as a coordination exception/obligation ledger, not a task manager. The boundary is strongest when Sontu records WHAT coordination consequence must become true and WHETHER evidence establishes it, while external systems/people retain HOW the work is performed.

This further narrows provisional Form B: the native value proposition is not “manage all event work.” It is “preserve and resolve the consequential gaps between event truth and the specialist systems/parties affected by it.” Whether hosts value this enough remains external evidence debt and is not validated internally.

N88-G2 FORM-C-FIRST DOMAIN RECONCILIATION — 2026-09-07

The strongest Form-C challenge sharpens the existing Consequence Case boundary test.

Form C remains the null and wins whenever it can provide equivalent settlement confidence with less native state/responsibility.

2026-09-10 — PRE-SCHEMA CONSEQUENCE & SETTLEMENT RECONCILIATION (working contract)

1\. Core distinction  
A material event change is not itself a consequence. A Sontu consequence is a downstream coordination obligation or materially affected commitment created by an event fact/change for which Sontu has a defined responsibility. The prototype must preserve the chain: event fact → material change → affected obligation(s) → required/optional action → settlement evidence → settled/reopened state.

2\. Candidate prototype consequence classes  
\- Participant commitment / attendance: a change may invalidate or require reconfirmation of an RSVP/commitment.  
\- Schedule / timing: a change affects availability, arrival, departure, sequencing, deadlines, or time-bound commitments.  
\- Location / access: a change affects where/how a participant, worker, vendor, or resource reaches or uses the event.  
\- Capacity / entitlement: a change affects admission, waitlist, allocation, reservation, ticket, or other entitlement.  
\- Host / staff responsibility: a change affects an assigned responsibility, owner, shift, handoff, or required host action.  
\- Resource / vendor dependency: a change affects a required external resource, supplier, room, equipment, service, or dependency.  
\- Payment / ticket entitlement: a change affects a payment, refund, ticket condition, entitlement, or financial action; specialist payment systems remain authoritative where applicable.  
\- Required participant action: a participant must acknowledge, choose, reconfirm, provide information, or take another action before coordination is complete.  
\- Cancellation / replacement: cancellation or substitution creates downstream obligations that must be individually resolved or explicitly waived.

3\. Consequence creation gate  
Do not create a Consequence Case for every edit. A case is warranted only when the existing Materiality \+ Boundary \+ Durability \+ Sontu Responsibility doctrine indicates that Sontu must preserve and track the downstream obligation. Cosmetic edits, harmless wording corrections, and transient information with no meaningful downstream obligation should not create cases.

4\. Settlement rule  
Notification sent does not equal settled. A consequence is settled only when evidence appropriate to that consequence shows that no further Sontu-owned coordination obligation remains. Evidence may include acknowledgement, reconfirmation, completed required action, authoritative external-system status, explicit host resolution/waiver where permitted, or a deterministic state transition whose prerequisites are satisfied. Settlement must be inspectable and attributable.

5\. Reopening  
A settled consequence can reopen when its settlement evidence is invalidated by a later material change, an authoritative external state changes, a required action is reversed/failed, or a correction shows that the prior settlement was based on stale/incorrect information. Reopening must preserve history rather than overwrite it.

6\. Prototype invariant  
Change ≠ consequence ≠ action ≠ settlement. Sontu must be able to explain each transition and must remain quiet when no meaningful consequence exists.

7\. Initial validation scenarios  
Adversarially test at minimum: time change; venue/access change; participant cancellation; capacity/waitlist change; vendor/resource failure; host cancellation; multi-party operational change. For each scenario test both true-positive consequence creation and a nearby edit that should produce no case.

8\. Competitive caution  
Do not claim uniqueness merely because Sontu uses consequence/settlement language. Current market evidence includes event execution products that explicitly model dependencies and consequences of change. Sontu differentiation must be demonstrated through the specific end-to-end consequence-to-settlement behavior and user value, not terminology.

9\. Pre-schema exit criteria  
Before persistence schema design begins: consequence classes and creation gate survive scenario/adversarial testing; settlement and reopening evidence are explicit; false-positive/no-case behavior is defined; Sontu-owned vs externally authoritative state is classified; acceptance/falsification tests are written; and founder decisions are requested only for genuinely subjective/borderline product behavior.

2026-09-10 — INTELLIGENCE / LLM CONTRACT HARDENING  
Status: pre-schema working contract. This section constrains intelligence behavior for the Core Validation Prototype and downstream architecture; it does not select a model vendor or persistence schema.

1\. ROLE OF INTELLIGENCE  
Intelligence is a probabilistic interpretation/planning layer over governed SONTU state. It may improve comprehension, reduce host effort and propose coordination actions. It is never the authoritative event, identity, authority, payment, entitlement, attendance, consequence-settlement or provider-state ledger.

2\. INPUT CONTRACT  
Permitted inputs include user text, transcribed voice, permitted event/context state, permitted event-scoped history, current Consequence Cases, reconciled provider evidence, and policy/instruction context. Retrieval is least-privilege and event/actor scoped. Voice and text enter the same semantic interpretation path after transcription; modality grants no additional authority.

3\. OUTPUT CONTRACT  
The model produces one of four conceptual outputs: INFORMATION\_RESPONSE; STRUCTURED\_PROPOSAL; CLARIFICATION\_REQUIRED; NO\_SAFE\_ACTION. A STRUCTURED\_PROPOSAL identifies intended operation, referenced event/context, candidate field/change, candidate affected obligations/cases, rationale/explanation, uncertainty and required confirmation level. Model prose is never itself a committed mutation.

4\. ACTION RISK / CONFIRMATION TIERS  
R0 — read/explain/summarize: no mutation; may execute without mutation confirmation after normal access checks.  
R1 — reversible low-consequence draft assistance: draft text, draft event facts, candidate classifications or recommendations; may update only explicitly non-authoritative draft state under product policy.  
R2 — consequential proposed mutation: publish/material event change, commitment/reconfirmation action, participant-affecting communication, consequence creation/waiver/settlement proposal, authority/delegation change, cancellation or comparable governed action. Requires deterministic revalidation and explicit human confirmation unless a later policy has narrowly pre-authorized that exact action class.  
R3 — externally consequential/irreversible/high-assurance action: payment/refund execution, destructive/terminal entitlement action, high-impact cancellation, sensitive disclosure or other action whose external effect cannot be safely inferred/reversed. Requires explicit confirmation plus provider/domain-specific authority and evidence; some R3 actions remain unavailable to the model entirely.  
Prototype default: no autonomous R2/R3 execution.

5\. DETERMINISTIC EXECUTION BOUNDARY  
Before any consequential mutation, application logic re-resolves target identity, current version/state, actor/acting context, permission, applicable policy, required confirmation, idempotency identity and any authoritative provider prerequisites. If state changed after the model proposal, the proposal is stale and must be rejected/recomputed rather than blindly executed. The model never supplies its own authorization proof.

6\. FACT / EVIDENCE RULES  
The model may extract a candidate fact from user language but must preserve source/provenance and confidence. It may not convert ambiguous natural language into authoritative consequential truth without the confirmation/evidence required by policy. Provider-derived facts retain provider freshness/status. Model inference cannot transform UNKNOWN/PENDING/FAILED/STALE provider evidence into success.

7\. CONSEQUENCE-CASE RULES  
The model may propose that a material change creates, updates or appears to settle a Consequence Case. Deterministic policy plus authoritative/reconciled evidence decides whether the case exists and whether a terminal disposition is valid. The model may explain why a case is open and suggest how to resolve it, but cannot mark settlement because it believes the obligation is probably satisfied.

8\. COMMUNICATION RULES  
The model may draft participant/host/vendor communications and select a candidate audience from governed affected-party state. Actual recipient resolution, protected-data access, sending authority, channel policy and delivery status are deterministic/provider governed. AI-generated wording must not invent event facts, guarantees, refund/payment outcomes or host commitments absent authority.

9\. UNCERTAINTY & CLARIFICATION  
Uncertainty is surfaced, not hidden. If a missing fact could change the target, authority, materiality, affected obligations or action outcome, the system asks for clarification or returns NO\_SAFE\_ACTION. Low-risk wording ambiguity may be resolved conversationally. Consequential ambiguity may not be silently guessed.

10\. FAILURE / FALLBACK  
Model timeout/unavailability must not corrupt governed state. The system may fall back to deterministic/manual UI for core event operations. No core authoritative event state may become inaccessible solely because the LLM is unavailable. If interpretation fails after the user has entered content, preserve recoverable input where safe. Provider/model retries must not duplicate consequential commands.

11\. PROVIDER ABSTRACTION  
SONTU exposes an internal intelligence contract independent of a specific model vendor. Provider adapters may differ in structured-output, tool-calling, realtime voice, latency or context capabilities, but domain commands and authority semantics remain SONTU-owned. Switching model/provider must not require redefining event/consequence truth.

12\. PRIVACY / DATA MINIMIZATION  
Send only the context needed for the current permitted task. Sensitive event context, participant data, accommodations, eligibility or private communications require purpose-appropriate access. Provider retention/training controls, regional requirements and production privacy terms must be reviewed before external deployment. Prototype data should be synthetic/minimized wherever real personal data is unnecessary.

13\. COST / LATENCY POLICY  
Intelligence must earn its invocation. Deterministic code handles simple validation, authorization, state transition and known rule evaluation. Model calls are reserved for language interpretation, ambiguity resolution, summarization, classification/proposal and reasoning where they materially reduce host/participant effort. Architecture must permit model selection/routing by task so a high-cost model is not required for every interaction. Exact budget and latency thresholds remain benchmark decisions, not domain constants.

14\. EVALUATION CONTRACT  
Before production, maintain a versioned evaluation set covering at least: correct no-action behavior; material versus non-material change classification; correct affected-obligation proposal; false Consequence Case creation; missed Consequence Case; unauthorized-action refusal; stale-state conflict; ambiguous actor/target; provider uncertainty; hallucinated event fact; false settlement; privacy leakage; duplicate/retry behavior; and adversarial prompt content embedded in event/user data. Evaluate both task success and unsafe/incorrect mutation rate. A model/provider change must pass the relevant regression set before promotion.

15\. PROMPT-INJECTION / UNTRUSTED-CONTENT BOUNDARY  
Participant text, imported descriptions, emails, provider payloads, uploaded content and other event data are untrusted data, not privileged instructions. They cannot alter system policy, permissions or tool authority. The execution layer accepts only typed allowed operations after deterministic validation; free-form model output never maps directly to privileged execution.

16\. AUDITABILITY  
Consequential AI-assisted actions record enough provenance to distinguish user input, model proposal, confirmation, deterministic authorization/policy decision, executed command and result. Model chain-of-thought is neither required nor treated as audit evidence; concise rationale/structured proposal metadata is sufficient.

17\. REALTIME VOICE POSITION  
Realtime conversational voice may later provide a natural host interface, but it is an interaction adapter over the same governed command contract. Interruptions, partial transcripts, speech-recognition errors and conversational corrections require special confirmation UX for consequential actions. 2026-09-10 — CORE VALIDATION STATE / SETTLEMENT / PERMISSION HARDENING

Status: pre-schema working authority for the frozen Core Validation Prototype fixture. It does not define persistence schema, APIs, UI components or production provider architecture.

1\. CONTROL PRINCIPLE  
The prototype preserves four separate semantic layers: EVENT FACT; CONSEQUENCE OBLIGATION; ACTION/ATTEMPT; SETTLEMENT EVIDENCE. A transition in one layer never silently implies a transition in another. Notification delivery, model confidence, user-interface completion, provider invocation and elapsed time do not establish settlement unless the governing obligation explicitly defines that evidence as sufficient.

2\. EVENT INSTANCE VERSION CONTRACT  
Prototype event lifecycle needed for the fixture: DRAFT → PUBLISHED → CANCELLED or CLOSED/COMPLETED. The proving scenario operates on PUBLISHED. A material edit to a published event preserves Event Instance identity and increments/creates a new authoritative event version. Non-material edits may also be historically recorded but do not create consequence obligations merely because a version changed.

Every consequential proposal/action is evaluated against a specific authoritative event version. A proposal based on an older version is STALE and cannot mutate current consequential truth without re-evaluation/reconfirmation.

3\. PARTICIPANT COMMITMENT / RECONFIRMATION CONTRACT  
Initial prototype commitment states required for the fixture: CONFIRMED; RELEASED/DECLINED. When an accepted material change creates a reconfirmation obligation, the participant's original historical commitment remains preserved while a separate reconfirmation outcome is evaluated for the new event version.

Reconfirmation outcome semantics: AWAITING\_RESPONSE; RECONFIRMED; RELEASED/DECLINED. AWAITING\_RESPONSE is unresolved. RECONFIRMED and RELEASED/DECLINED are terminal participant outcomes for that specific reconfirmation obligation/version. Silence, message delivery and link opening are not reconfirmation.

4\. CONSEQUENCE ESCALATION TRANSITIONS  
Evaluation begins after a governed material change or candidate consequence trigger.  
L0 OBSERVE: record/derive change context; no durable obligation.  
L1 INFORM/ROUTE: communication or routing is the complete accepted obligation. Terminal when policy-defined delivery/route evidence is satisfied; otherwise delivery failure remains visible but does not automatically become an L3 case.  
L2 RECONCILE: SONTU waits for/reads an external authoritative outcome. Terminal when sufficiently fresh authoritative evidence establishes the event-side answer. UNKNOWN/PENDING/FAILED/STALE remains unresolved at L2 unless SONTU explicitly accepts a separate durable obligation.  
L3 NATIVE CONSEQUENCE CASE: allowed only when Materiality \+ Boundary \+ Durability \+ SONTU Responsibility pass and L0–L2 cannot establish equivalent settlement confidence.

Escalation is monotonic in responsibility, not necessarily in UI steps: the system may determine directly that L3 is required, but must be able to explain why lower levels are insufficient. De-escalation from a proposed L3 to L2/L1 is permitted before native obligation acceptance when evidence shows a lower level is sufficient.

5\. MINIMUM CONSEQUENCE CASE STATE MACHINE  
OPEN\_UNRESOLVED: accepted governed obligation exists and settlement evidence is incomplete.  
PENDING\_EXTERNAL: case exists, but required terminal evidence currently depends on an external authority/action.  
RESOLVED: governed evidence establishes the required outcome; terminal unless reopened by invalidating evidence/new material fact.  
WAIVED: authorized host/policy explicitly removes the obligation where waiver is permitted; terminal unless the waiver itself is invalidated/corrected.  
SUPERSEDED: a later governed obligation/change replaces the original obligation; terminal for the original case while successor consequence remains independently governed.  
EXCEPTION: ordinary settlement cannot be established or completed and explicit host/policy handling is required. EXCEPTION is not equivalent to successful settlement; it is terminal only where policy permits exception disposition, otherwise it remains closure-blocking/unresolved.

Allowed prototype transitions:  
OPEN\_UNRESOLVED → PENDING\_EXTERNAL when required evidence is delegated to/waits on an external authority.  
OPEN\_UNRESOLVED → RESOLVED when sufficient governed evidence arrives.  
OPEN\_UNRESOLVED → WAIVED only by authorized host action and only where obligation policy permits waiver.  
OPEN\_UNRESOLVED → SUPERSEDED when a later governed change replaces the obligation.  
OPEN\_UNRESOLVED → EXCEPTION when normal resolution is impossible/failed and exception handling is required.  
PENDING\_EXTERNAL → OPEN\_UNRESOLVED when external dependency no longer controls the next required outcome but the obligation persists.  
PENDING\_EXTERNAL → RESOLVED when authoritative external evidence establishes settlement.  
PENDING\_EXTERNAL → EXCEPTION when authoritative resolution cannot be obtained under the allowed path.  
RESOLVED/WAIVED/SUPERSEDED/terminal-EXCEPTION → OPEN\_UNRESOLVED or a successor case only through explicit REOPEN/REPLACE logic caused by new authoritative evidence, correction or new material event version. Historical terminal disposition is never overwritten.

6\. SETTLEMENT EVIDENCE RULES — FROZEN FIXTURE  
No-case cosmetic edit: no settlement object exists.  
Awareness-only consequence: policy-defined delivery can be sufficient only when awareness/delivery is itself the complete accepted obligation. Provider acceptance alone is not end-recipient delivery when the chosen channel distinguishes them.  
Participant reconfirmation: each affected participant settles through authoritative RECONFIRMED or RELEASED/DECLINED outcome for the applicable event version. Aggregate case settles only when every required participant outcome is terminal or an authorized policy/host disposition explicitly removes the remaining requirement.  
External provider/resource reconciliation: sufficiently fresh authoritative provider status for the revised event fact settles the reconciled obligation. UNKNOWN, PENDING, FAILED or STALE cannot settle it. Simulation in Core Validation must be visibly tagged SIMULATED\_PROVIDER\_EVIDENCE.  
Host waiver: settlement-by-waiver is valid only where the obligation is waivable and the current authorized host explicitly confirms waiver. Waiver is a terminal disposition, not evidence that the original desired outcome occurred.  
Exception: records inability/approved exception, not fabricated success. The host-facing view must distinguish RESOLVED from WAIVED and EXCEPTION.

7\. AGGREGATE SETTLEMENT / PARTIAL SETTLEMENT  
For the frozen reconfirmation fixture with 12 affected confirmed participants, the aggregate is derived from participant-level required outcomes. Example: 10 RECONFIRMED \+ 1 RELEASED \+ 1 AWAITING\_RESPONSE \= 11 terminal outcomes, 1 unresolved, aggregate NOT SETTLED. The UI may say “11 of 12 resolved” but may not say “settled.”

Where several obligations have independent authorities/outcomes, they must not be collapsed into one aggregate that hides an unresolved obligation. Conversely, do not create one native case per notification when multiple people genuinely form one policy-defined settlement unit.

8\. REOPENING / VERSION INVALIDATION  
A prior settlement remains historical evidence tied to its event version and obligation context. It does not automatically carry forward after a new material change.  
Reopen or create a successor obligation when: a later material event version invalidates prior reconfirmation/readiness; authoritative external evidence reverses/corrects the prior terminal fact; a correction proves prior evidence stale/incorrect; or an authorized terminal disposition is invalidated by correction/authority change.  
Do not reopen solely because the LLM expresses uncertainty, a duplicate callback arrives, the same evidence is replayed, or a non-material edit occurs.

For the fixture: reconfirmation to 7:30 PM does not imply reconfirmation to a later 8:00 PM version. Prior 7:30 evidence remains in history; the applicable 8:00 obligation is newly unresolved/reopened according to deterministic policy.

## 15\. BOUNDED BETA RECONCILIATION — PUBLIC AND GUEST PARTICIPATION

Visibility and participation eligibility are independent event properties. PUBLIC controls unauthenticated discovery and detail access. Participation access controls who may commit: ANYONE or SONTU\_USERS\_ONLY. Existing public events default to SONTU\_USERS\_ONLY unless the host explicitly changes eligibility.

A guest commitment belongs to one event and stores a supplied name, normalized email, participation state and non-user participant identity. Its management credential is a random event-scoped secret; only a hash is persisted server-side. The browser-held credential may manage that guest RSVP but grants no account, profile, friendship, organization or other-event authority.

Guest join and withdrawal are transactional, capacity-safe and idempotent. Join rejects unavailable or full events without consuming capacity. Withdrawal releases capacity once. A verified Sontu account with the matching normalized email may claim the guest commitment through the governed member-join path, preserving one participant and one capacity allocation.

Email is required in the beta for reservation deduplication, RSVP recovery or claim, and essential event communications. The current guest email is not yet verified. Before using guest RSVP for capacity-sensitive or abuse-sensitive events at broader scale, add email verification or a time-bounded reservation/confirmation path. Email verification, RSVP commitment and event-change reconfirmation remain distinct states.

PROFILE & SOCIAL RELATIONSHIP DOMAIN RECONCILIATION — founder authority

This section consumes the current founder-locked UX authority for Profiles, Connections, Following & Host Reputation and defines the corresponding domain semantics. Where older language implied that a follower system or durable person-to-person relationship graph was categorically prohibited, this later founder authority supersedes that interpretation while retaining the prohibition on general personal timelines, generic status publishing and engagement-for-engagement's-sake.

Identity invariant  
Every durable SONTU account has one immutable account/user identity. Host, participant, follower, Connection, teammate and other roles/relationships do not create separate account identities. Mutable display names and @handles are presentation/addressability fields and must not serve as durable relationship keys.

Follow relationship  
Follow is unilateral. Subject A may follow subject B without B reciprocating or approving by default, subject to applicable Privacy & Safety, blocking, discoverability and entity-eligibility rules. Following does not create Connection, event access, messaging permission, privileged profile access, endorsement or reciprocal visibility. Unfollow removes the current Follow relationship without rewriting historical event relationships.

Connection relationship  
Connection is reciprocal between people and requires an accepted relationship. Minimum lifecycle states are pending/requested, accepted/connected, declined and removed/disconnected, with blocking/safety state taking precedence. The system must distinguish incoming and outgoing pending requests. Follow and Connection may coexist independently; accepting a Connection does not require or imply a Follow unless a later explicit product rule says otherwise.

Close Connection classification  
Close Connection is private unilateral metadata owned by one account and may be assigned only to one of that account's current Connections. It creates no reciprocal state, notification or public label. Removing the underlying Connection must make the Close classification inactive/removed without altering historical event records.

Private Connection Groups  
A Group is user-owned private organizational metadata over that user's Connections. Groups may have compliant custom names; membership is many-to-many and a Connection may belong to multiple Groups. Group membership confers no event permission or access by itself. Removing a Connection removes/inactivates that person's current memberships in the owner's private Groups without altering historical invitations/events already created.

Shared Event Context  
Shared Event Context is derived/contextual evidence that two identities have a legitimate common event relationship where policy permits that context to be exposed. It is not a social relationship and must never be stored or interpreted as automatic Connection. Derivation must respect event visibility/access, each person's applicable activity/discoverability controls, blocking and other safety rules. Protected/private event relationships cannot be inferred to unauthorized viewers through this context.

Activity visibility invariant  
Follow, Connection and shared-event context never override event access or participant privacy. Discovery/Feed may consume permitted relationship signals only after authorization/visibility evaluation. A recommendation must not reveal that a person is invited, Interested, Going, attended or otherwise related to an event when that relationship is not visible to the viewer.

Blocking precedence  
A blocking/safety relationship has precedence over ordinary social relationships for interaction/discoverability. Implementation may preserve necessary internal/audit history, but user-facing Follow/Connection/discovery behavior must resolve according to current safety authority rather than stale relationship state.

Host reputation domain  
Host reputation is derived evidence attached to the same immutable identity that hosted events; it is not a separate host account/profile. Follower count is an audience/popularity signal, not host-quality truth. Candidate reputation evidence may include completed hosting history, credible attendance, repeat attendance, post-attendance Follow behavior, verified attendee feedback with sufficient samples, cancellation/reschedule reliability and legitimate trust/safety/operational evidence. Registration/RSVP, entitlement, credential presentation and attendance remain distinct domain facts and must not be collapsed to manufacture reputation.

Post-attendance Follow provenance  
Where privacy and attribution rules permit, the system may preserve whether a Follow occurred after credible attendance/participation at an event hosted by the followed identity. This provenance is analytical/reputation evidence; it does not create a stronger Follow permission state or expose the attendee's event history publicly.

Super Host boundary  
Super Host is a future derived designation over sufficient evidence, not an account role or permission. Verified remains separate factual assurance. No Super Host threshold, weight or formula is authorized by this reconciliation. Any future qualification must consume evidence-backed Experience, Quality, Reliability, Audience and Trust signals and must not require mass scale such that excellent small-event hosts are structurally excluded.

Anti-gaming invariant  
Follower, feedback and host-reputation systems must be designed so obvious self/duplicate/manufactured activity cannot straightforwardly create authoritative quality claims. Public rating/reputation presentation must support sufficient-sample/confidence rules before tiny samples are represented as robust evidence. Exact abuse controls and thresholds remain downstream policy/implementation authority.

Historical integrity  
Changes to Follow, Connection, Close classification, Group membership, handle, privacy or blocking must not rewrite historical event participation, attendance, invitation, host-role, team-role, payment, credential or audit truth. Current relationship state and historical event truth are separate domains.
