1 — USER ROLE MODEL & E2E EXPERIENCE FRAME  
Joy does not divide ordinary people into permanent Host and Attendee account types. A Joy user is a person who may participate in events, host events, or do both. Host and participant/attendee are contextual roles relative to a specific event. The same signed-in user may be an attendee for one event, the host of another, and move between those perspectives without creating a second account or changing a global account type.

The product therefore has two primary end-to-end experience tracks that meet around the event:

HOST E2E — Decide to host → Establish personal/organization ownership → Define → Configure participation → Plan operational needs → Review/readiness → Publish → Distribute/invite → Monitor/manage → Prepare → Operate/check in → Complete → Review/history → Repeat or create another event.

PARTICIPANT E2E — Discover/receive invitation → Evaluate → Resolve access/identity/eligibility → RSVP/register/purchase → Receive confirmation/admission → Retrieve/prepare → Receive changes/reminders → Arrive/check in/join → Participate → Handle exceptions → Retain post-event history → Discover another event or become a host.

These are not separate products. They are two perspectives on the same event lifecycle. A consequential host action must have its participant-side consequence designed at the same time: publication creates something people can access; a material edit changes what participants rely on; cancellation changes participant state and may trigger refunds; check-in connects a participant credential to host operation.

A user who participates and hosts must have a coherent personal experience. Joy should make the current event role/context obvious without forcing a permanent mode switch. Hosting controls must not crowd ordinary participation, while participant information must remain reachable even for frequent hosts.

When Gate 1 is explicitly opened, journey planning must select and adapt only the lifecycle stages and scenario branches required by the approved Core Validation Build. The complete lifecycle narratives below remain canonical-direction evidence and stress-test material; they are not automatically first-build scope.

MASTER HOST E2E — COMPLETE LIFECYCLE

H0 — Intent and entry. A Joy user decides they want to organize something. They may begin from Create, from an existing/past event they want to repeat, from an organization context, or eventually from a template/recommendation. Joy does not require a separate host account. If identity is not yet established, authentication occurs when needed to create/persist the event.

H1 — Establish ownership and context. The user decides whether the event is theirs personally or belongs to an organization/business they are authorized to act for. Joy establishes a Draft with stable ownership. Acting personally versus for an organization must remain understandable throughout the event lifecycle.

H2 — Define the event. The host establishes what the event is for, category/subcategory, title/description, date/time/timezone, physical/virtual/hybrid format, location/access information, and other essential facts. Category affects useful prompts/defaults but does not move the event into a separate product.

H3 — Configure participation. The host decides who should be able to see and join: public/unlisted/private visibility, access/invitation rules, eligibility/restrictions, RSVP/free registration/paid admission, capacity, participant information, and check-in/admission behavior where applicable. Joy progressively exposes only relevant complexity.

H4 — Plan operational needs. The host considers what is required to actually deliver the event: people/operators, venue/access, equipment, supplies, services, communications and other event resources. For MVP, Joy may help the host capture or remember these needs where useful, but a transactional resource marketplace is post-MVP by default. The journey deliberately preserves a future extension where a host could obtain supplies, equipment, venues or services through Joy without making that marketplace a dependency of core event creation.

H5 — Review and readiness. Joy surfaces missing blockers, consequential settings and an attendee-facing preview. The host understands what participants will see, what they must do to join, whether money/restrictions are involved, and what will happen after publication. Draft can be left and safely resumed.

H6 — Publish. The host intentionally publishes. Joy establishes the authoritative published state, confirms success, and exposes the event only according to its configured visibility/access rules.

H7 — Acquire participants. The host distributes the event through public discovery where applicable, direct sharing, invitations, organization/community channels, and approved event-centered Feed publishing/promotion. Feed can help a host build anticipation and visibility without weakening configured access, eligibility or admission rules. Joy lets the host understand registrations/RSVPs/admissions and capacity without forcing them to assemble the truth from disconnected tools.

H8 — Manage before the event. The host monitors participation, communicates essential information, handles participant changes, adjusts allowed event details, and sees operational issues. Material changes are distinguished from harmless edits and produce appropriate participant consequences/notifications. If the host cancels, Joy preserves history and handles participant/refund consequences rather than deleting the event.

H9 — Prepare to operate. As the event approaches, the host can determine what is ready: event information, participant/admission state, capacity, access details, operators, check-in requirements and unresolved issues. Future marketplace/resource fulfillment may eventually integrate here, but core MVP readiness cannot depend on it.

H10 — Operate the event. The host/operator runs the event using the capabilities applicable to it: participant lookup, admission verification, QR/manual check-in, attendance state, protected virtual access, essential communication and issue handling. Operational truth remains authoritative and auditable.

H11 — Complete. The event reaches Completed state when appropriate. Completion does not erase the event, participants, transactions, attendance or consequential history.

H12 — Review and continue. The host can review essential results/history, participant/attendance outcomes, paid/refund status where applicable, and operational records. Useful prior event information may support repeating/copying a future event without making every event permanently active.

Host lifecycle branches that must remain coherent include: abandon/resume Draft; switch personal versus organization ownership before consequential commitment where allowed; private/invite event; free versus paid admission; restricted eligibility; virtual/hybrid access; capacity full; material change; cancellation; payment/refund problem; operator permission loss; network/server failure; event completion; and future resource procurement.

MASTER PARTICIPANT E2E — COMPLETE LIFECYCLE

P0 — Intent and entry. A person wants to attend or participate in something. They may discover it through Joy Discover, encounter event-centered content in Feed, follow a public web link, receive an invitation, see a host/organization share, or enter through another permitted distribution channel. Public unrestricted event information does not require an account merely to evaluate it.

P1 — Evaluate. The prospective participant understands what the event is, who hosts it, when/where/how it occurs, price/admission if any, availability, accessibility information, relevant requirements and the primary action needed to participate. Private/restricted information is not leaked during evaluation.

P2 — Resolve access and identity. If the next step requires identity, invitation permission, eligibility or protected access, Joy asks for only what is legitimately required. Authentication returns the user to the intended event/action instead of dumping them into generic home.

P3 — Commit to participate. Depending on the event, the user RSVPs, registers, accepts an invitation, obtains free admission, purchases paid admission, or otherwise completes the applicable participation action. Capacity, access and eligibility are revalidated at consequential submission.

P4 — Confirmation and admission. Joy gives an unambiguous result. A successful participant gets a persistent participation record and, when applicable, a ticket/credential/QR or other admission representation. Failed, pending and unknown outcomes are not presented as success.

P5 — Return and prepare. The participant can retrieve joined events later from their Joy identity, including after restarting or changing session/device subject to account access. They can see current event information, time/location/access, admission status, requirements and protected virtual information when authorized and released.

P6 — Stay informed. Before the event, the participant receives essential reminders and material host changes through supported channels. The current authoritative event state wins over stale information. If a change affects their decision to attend, applicable withdrawal/refund paths remain understandable.

P7 — Arrive or join. For a physical event, the participant presents admission or is looked up/checks in according to event policy. For virtual/hybrid events, authorized access becomes available according to release rules. Invalid, duplicate, refunded, wrong-event or unauthorized credentials do not appear valid.

P8 — Participate. The user experiences the event through the Event Hub/Profile and any activated contextual modules. Joy does not require social networking as a prerequisite. Where enabled, an event-scoped Discussion/Message Board supports general event conversation and an Ask Host assistant handles routine event questions/concerns, escalating to a human-host contact workflow when required. General user-to-user DMs are not implied.

P9 — Exception handling. If the event is cancelled, postponed, changed, unavailable, access is revoked, payment/refund has an issue, or a system failure occurs, the participant receives a truthful state and a useful next action. Privacy-sensitive denial does not disclose protected information.

P10 — Post-event. The completed event moves into relevant participation history rather than disappearing. The user can understand completed/cancelled/refunded status and retain approved historical information subject to privacy/retention rules.

P11 — Continue as a Joy user. The participant may discover another event or decide to create one themselves. No account conversion is required to become a host; the same identity simply acts in a different event context.

Participant lifecycle branches that must remain coherent include: public versus invited entry; unauthenticated evaluation; authentication interruption; free RSVP; paid purchase; eligibility/restriction; capacity full; cancellation/withdrawal/refund; material event change; physical check-in; virtual access; credential invalidation; event unavailable; system failure; post-event history; and participant-to-host transition.

HOST ↔ PARTICIPANT LIFECYCLE COUPLING  
The event is the shared object connecting both journeys. Gate 1 must reconcile at least these consequence pairs:  
\- Host publishes → eligible participants can discover/receive/access the event according to rules.  
\- Host changes material information → affected participants see authoritative changes and receive required notice.  
\- Host changes capacity/access/eligibility → participant availability and permitted actions change consistently.  
\- Participant registers/purchases/withdraws → host operational participant/admission state changes.  
\- Host cancels → participant state becomes cancelled and refund/communication consequences execute where applicable.  
\- Host/operator checks in a participant → participant credential/admission/attendance state and host counts remain consistent.  
\- Host completes event → participant and host histories reflect completion without losing consequential records.  
\- A person who is both host and participant across different events retains one identity and can reach both sets of relevant events without a permanent role switch.

2 — JOURNEY DESIGN RULES  
A journey is complete only when the user reaches the intended outcome and understands what happened. A technically successful API call is not a completed user journey.

Every critical journey must account for:  
\- Entry state and user intent.  
\- Required identity/authentication only when justified.  
\- User-visible progress and system status.  
\- Validation before consequential submission.  
\- Success state and next action.  
\- Recoverable errors.  
\- Permission/access denial.  
\- Empty/loading/degraded states where relevant.  
\- Material consequences such as payment, cancellation, eligibility or publication.  
\- Telemetry sufficient to identify abandonment/failure.

Prototype and Beta testing should use these journeys directly rather than inventing separate happy paths.

2 — J1 PUBLIC VISITOR EVALUATES A PUBLIC EVENT  
Actor: unauthenticated visitor.  
Goal: understand a public/unrestricted event and decide whether to participate.

Flow:  
1\. Visitor opens a shared event URL or reaches the event through public discovery.  
2\. Joy shows permitted public event information without forcing account creation.  
3\. Visitor can understand what the event is, host identity, date/time/timezone, physical/virtual/hybrid format, permitted location/accessibility information, admission type, price if applicable, capacity/availability where useful, and important participation requirements.  
4\. Visitor selects the relevant participation action.  
5\. Joy requests authentication only when the next action legitimately requires identity, protected access, registration or payment.

Acceptance criteria:  
\- Public/unrestricted event information can be viewed without an account.  
\- Page does not expose private/restricted information.  
\- Primary participation action is obvious.  
\- Cancelled/completed/unavailable events cannot misleadingly appear normally actionable.  
\- Time and timezone are understandable.  
\- Missing optional event fields do not create broken/empty UI artifacts.  
\- Loading/error/not-found states are explicit.  
\- Visitor can recover from an expired/bad link through a useful state rather than a dead screen.

3 — J2 INDIVIDUAL HOST CREATES AND PUBLISHES A SIMPLE EVENT  
Actor/context: signed-in Joy user acting as the event host.  
Goal: create and publish an event without specialist knowledge.

Flow:  
1\. Host chooses Create Event.  
2\. Joy establishes a Draft owned by the host.  
3\. Host enters essential event information.  
4\. Host selects category and format.  
5\. Host configures visibility/access, admission/registration, capacity and applicable restrictions.  
6\. Joy validates required information and surfaces unresolved blocking issues.  
7\. Host reviews the attendee-facing representation.  
8\. Host publishes intentionally.  
9\. Joy confirms publication and provides distribution/share actions.

Acceptance criteria:  
\- Draft exists without accidental publication.  
\- Host can leave and resume a saved Draft in functional Beta.  
\- Fields/configuration adapt to selected event needs without presenting every possible capability.  
\- Visibility, eligibility and admission are not presented as the same setting.  
\- Publication cannot proceed while required blocking information is invalid/missing.  
\- Consequential restrictions or paid configuration receive appropriate review/confirmation.  
\- Successful publication has an unmistakable success state.  
\- Published event is accessible only under configured rules.  
\- Duplicate submit/retry cannot unintentionally create multiple published events.  
\- Publication action is auditable.

4 — J3 HOST CREATES A PRIVATE / INVITE-ONLY EVENT  
Actor: individual or authorized organization host.  
Goal: create an event whose protected information is limited to permitted participants.

Flow:  
1\. Host creates/configures event.  
2\. Host chooses Private/invite-only visibility/access.  
3\. Joy explains at product-appropriate depth what private means.  
4\. Host configures invitations/access.  
5\. Host publishes.  
6\. Permitted invitee accesses the event through a valid route.  
7\. Non-permitted visitor is denied protected information.

Acceptance criteria:  
\- Possession of a URL alone does not grant private access.  
\- Search/discovery does not expose private event content.  
\- Unauthorized user receives a safe, understandable denial state.  
\- Authentication occurs where needed to establish permission.  
\- Host can understand who has access to practical MVP depth.  
\- Removing/revoking access has defined behavior and does not rely on obscurity.

5 — J4 ATTENDEE RSVPS / REGISTERS FOR A FREE EVENT  
Actor/context: Joy user or visitor acting as a prospective participant/attendee.  
Goal: obtain a confirmed participation record.

Flow:  
1\. User evaluates event.  
2\. User selects RSVP/Register.  
3\. Joy authenticates if identity is required.  
4\. User supplies only required participant information.  
5\. Joy validates availability/capacity and eligibility/access.  
6\. User confirms registration.  
7\. Joy creates participation record.  
8\. User sees confirmation and can later retrieve event participation information.

Acceptance criteria:  
\- Capacity is revalidated at consequential submission, not trusted from stale page state.  
\- Duplicate action does not create duplicate participant records.  
\- User receives explicit confirmation or explicit failure; no ambiguous spinner/unknown outcome.  
\- Host participant view reflects successful registration.  
\- User can cancel/withdraw where policy permits.  
\- Cancellation does not erase audit/history needed for operation.  
\- Registration failure preserves entered non-sensitive information where safe enough to retry.

6 — J5 ORGANIZATION HOST CREATES AND OPERATES AN EVENT  
Actor: authorized organization member.  
Goal: operate an event on behalf of an organization rather than personally.

Flow:  
1\. User signs in.  
2\. User selects organization context where authorized.  
3\. User creates event owned by organization.  
4\. Joy applies organization permissions to consequential actions.  
5\. Authorized team members can operate the event according to assigned permissions.  
6\. Event remains owned by organization if an individual member leaves/is removed.

Acceptance criteria:  
\- UI makes acting-as-self vs acting-for-organization understandable.  
\- Event owner is the organization, not merely the creating employee/member.  
\- Unauthorized organization member cannot publish/cancel/change restricted settings.  
\- Permission failure is explicit and safe.  
\- Member removal does not orphan organization events.  
\- Consequential team/event actions are auditable.

7 — J6 HOST CHANGES A PUBLISHED EVENT  
Actor: authorized host/operator.  
Goal: modify an event while preserving attendee trust and operational truth.

Flow:  
1\. Host opens published event management.  
2\. Host edits allowed information.  
3\. Joy identifies material changes when applicable.  
4\. Host reviews consequences.  
5\. Host confirms change.  
6\. Joy persists updated event and history.  
7\. Affected attendees receive required notice through configured communication path.

Acceptance criteria:  
\- Published edits do not silently overwrite consequential history.  
\- Material time/venue/virtual-access/eligibility/admission changes receive appropriate confirmation.  
\- Host understands whether attendees will be notified.  
\- Failed update does not leave UI implying success.  
\- Attendee-facing information becomes consistent after successful update.  
\- Required notification failure is observable/recoverable operationally.

8 — J7 HOST CANCELS AN EVENT  
Actor: authorized host/operator.  
Goal: cancel safely and communicate consequences.

Flow:  
1\. Host selects Cancel Event.  
2\. Joy explains consequences and requires intentional confirmation.  
3\. Host supplies cancellation information where required.  
4\. Joy marks event Cancelled rather than deleting operational history.  
5\. Attendees receive cancellation communication.  
6\. Paid-event refund consequences follow the payment/refund authority when applicable.

Acceptance criteria:  
\- Cancellation cannot be triggered accidentally through a single ambiguous action.  
\- Cancelled event cannot continue accepting normal registrations/purchases.  
\- Existing participants can understand that the event is cancelled.  
\- Cancellation history is retained/auditable.  
\- Notification/refund failures surface for operational follow-up.  
\- Cancel does not masquerade as delete.

9 — J8 ATTENDEE PURCHASES PAID ADMISSION  
Stage: prototype \+ staged Beta; required by MVP.  
Actor/context: Joy user acting as an eligible participant/attendee.  
Goal: obtain valid paid admission exactly once for the intended purchase.

Flow:  
1\. User evaluates paid event and admission option.  
2\. Joy presents price/fees/essential terms clearly before commitment.  
3\. User authenticates where required.  
4\. Joy validates access, eligibility, availability and admission option.  
5\. User enters/completes payment through approved payment architecture.  
6\. Joy handles payment result deterministically.  
7\. Successful purchase creates payment/admission records and credential.  
8\. User receives clear confirmation and can retrieve admission.

Acceptance criteria:  
\- Price and material fees are visible before purchase confirmation.  
\- Double taps/retries do not create unintended duplicate charges/admissions.  
\- Payment pending/success/failure states are distinguishable.  
\- A client timeout does not cause Joy to claim failure when payment outcome is actually unknown; reconciliation path exists.  
\- Admission is not issued merely because the client says payment succeeded.  
\- Failed payment does not create valid admission.  
\- Successful purchase is retrievable after app/browser restart.  
\- Transaction and admission history are auditable.  
\- Refund/cancellation terms are accessible before purchase to required legal/product depth.

10 — J9 PAID ATTENDEE CHECKS IN  
Actor: attendee \+ authorized event operator.  
Goal: verify valid admission and record entry.

Flow:  
1\. Attendee presents valid credential/QR or operator performs approved lookup.  
2\. Operator scans/looks up credential.  
3\. Joy validates credential/event/admission status.  
4\. Joy records successful check-in.  
5\. Operator receives immediate unambiguous result.

Acceptance criteria:  
\- Valid credential checks in successfully.  
\- Duplicate/reused credential is detected and clearly differentiated from valid first use.  
\- Wrong-event, refunded/cancelled/invalid credential does not appear valid.  
\- Network/degraded/offline behavior follows defined operational policy rather than silently guessing.  
\- Manual fallback does not bypass authorization/audit requirements.  
\- Check-in action records operator/time/event/credential context to appropriate audit depth.  
\- Re-entry, if supported, follows explicit policy.

11 — J10 RESTRICTED / AGE-GATED EVENT ACCESS  
Stage: prototype \+ staged Beta; required by MVP.  
Actor: prospective attendee.  
Goal: access only information/actions they are legitimately entitled to receive.

Flow:  
1\. User encounters permitted public metadata or valid access route.  
2\. Joy identifies that protected access requires authentication/eligibility.  
3\. User authenticates.  
4\. Joy performs the approved eligibility-assurance flow.  
5\. Eligible user receives authorized event information/actions.  
6\. Ineligible/unverified user receives safe denial or unresolved-verification state.

Acceptance criteria:  
\- Public visibility never equals eligibility.  
\- Protected event information is not leaked before authorization.  
\- URL possession does not bypass restriction.  
\- Failure state does not disclose sensitive protected information.  
\- Joy does not claim eligibility was proven using a method that downstream legal/product authority considers insufficient.  
\- Eligibility/verification errors are recoverable where appropriate.  
\- Privacy/data collection is minimized to approved requirements.

12 — J11 VIRTUAL / HYBRID ATTENDEE GAINS EVENT ACCESS  
Actor: registered/authorized attendee.  
Goal: receive the correct virtual participation information without exposing protected access publicly.

Flow:  
1\. User views permitted event information.  
2\. User registers/purchases/qualifies as required.  
3\. At the approved time/state, Joy exposes protected virtual access information to the authorized user.  
4\. User can retrieve access again from their event/admission view.

Acceptance criteria:  
\- Protected join URL/code is not embedded in public event metadata.  
\- Unauthorized visitor cannot retrieve protected virtual access.  
\- Timezone is clear.  
\- Host changes to virtual destination trigger appropriate material-change handling.  
\- Missing/not-yet-released access information has a deliberate state rather than appearing broken.

13 — J12 CAPACITY EXHAUSTS DURING REGISTRATION/PURCHASE  
Actor: prospective attendee.  
Goal: receive truthful availability outcome during concurrency.

Flow:  
1\. User sees apparent availability.  
2\. Another participant takes the remaining capacity before submission completes.  
3\. Joy revalidates capacity during consequential action.  
4\. User receives sold-out/full state rather than false confirmation.

Acceptance criteria:  
\- Capacity cannot be oversold merely because multiple clients saw the same stale availability.  
\- No successful participation/admission is shown unless capacity reservation/commit succeeded.  
\- Payment architecture must prevent or correctly compensate a charge when admission cannot be fulfilled.  
\- User receives a useful next state such as full/sold-out; waitlist only if that capability is in scope.

14 — J13 AUTHENTICATION INTERRUPTS A USER FLOW  
Actor: visitor who reaches an identity-required action.  
Goal: authenticate without losing legitimate journey context.

Flow:  
1\. Visitor starts from event context.  
2\. Selects an action requiring identity.  
3\. Joy authenticates/signs up user.  
4\. User returns to the intended event/action when safe.

Acceptance criteria:  
\- Authentication is not demanded earlier than necessary.  
\- Successful authentication returns user to useful context rather than generic home.  
\- Failed/cancelled authentication does not mutate event/registration/payment state.  
\- Expired event/action context produces a deliberate recovery state.

15 — J14 USER LOSES PERMISSION OR ELIGIBILITY MID-FLOW  
Actor: host/operator or attendee.  
Goal: prevent stale client authorization from causing an unauthorized action.

Acceptance criteria:  
\- Consequential action rechecks server-side authorization/eligibility as appropriate.  
\- Stale UI permission does not override authoritative access state.  
\- User receives a clear denial/recovery state.  
\- Unauthorized mutation is not partially applied.  
\- Security-relevant denial is observable to appropriate operational telemetry without exposing sensitive information.

16 — J15 NETWORK / SERVER FAILURE DURING CONSEQUENTIAL ACTION  
Applies to publish, registration, payment, cancellation, material update, refund and check-in.

Acceptance criteria:  
\- Joy differentiates failed, pending/unknown and successful outcomes where uncertainty exists.  
\- Retrying is safe/idempotent where duplicate consequences would be harmful.  
\- UI never fabricates success to hide latency/failure.  
\- User has a recovery/recheck path.  
\- Operational telemetry captures failure class/context.  
\- Persisted authoritative state wins over stale local UI.

17 — J16 EVENT NOT FOUND / UNAVAILABLE / REMOVED  
Actor: visitor or participant following an old link.

Acceptance criteria:  
\- Not-found, private/no-access, cancelled, removed for policy reasons and temporary system failure are not misleadingly collapsed into one state when the distinction is safe and useful.  
\- Privacy-sensitive denial does not reveal existence/details that should remain hidden.  
\- Existing legitimate participants receive appropriate access to historical/cancellation information where policy permits.  
\- Public visitor receives useful navigation/recovery rather than a dead end.

24 — CROSS-JOURNEY ACCEPTANCE STANDARDS  
For every critical flow:  
\- One clear primary action per decision point where practical.  
\- No unexplained dead ends.  
\- No accidental destructive/consequential action.  
\- No client-only enforcement of permissions, eligibility, capacity or payment truth.  
\- No false success states.  
\- No duplicate consequential results from ordinary retry/double-submit.  
\- No forced account creation merely to view unrestricted public information.  
\- No protected information exposed through public/private boundary errors.  
\- No loss of event ownership when organization personnel change.  
\- No conflation of registration, payment, credential, check-in and attendance.  
\- No deletion used to hide consequential lifecycle/financial history.  
\- Material event changes are visible and communicated according to downstream rules.  
\- User can tell what happened and what to do next after success, denial or recoverable failure.

25 — TELEMETRY REQUIREMENTS FROM JOURNEYS  
Detailed analytics definitions belong downstream, but the journeys require instrumentation points sufficient to observe:  
\- Event creation started/draft established.  
\- Draft abandonment/recovery.  
\- Publish attempt/success/failure.

28 — DETAILED SCENARIO & BRANCH RECONCILIATION

Gate 1 now decomposes the completed master Host and Participant lifecycles into implementation-guiding scenario families. These scenarios do not create separate products or permanent user types; they stress the same event lifecycle from different contexts.

S1 — Ownership and acting context. A user creates or manages an event personally or for an organization. Branches include selecting context, changing context before consequential commitment where allowed, insufficient organization permission, member removal, operator delegation, and organization continuity. Acceptance: ownership is always explicit; organization events do not become personal because personnel change; consequential actions recheck authority.

S2 — Invitations, distribution and acquisition. A host publishes and distributes through public discovery, direct share, invitations, saved audiences, organization/community channels, or approved event-centered Feed content/promotion where in scope. Branches include unrestricted public link, unlisted share, private invite, expired/revoked invite, duplicate invite, forwarding, Feed-originated event entry and attribution. Acceptance: distribution never weakens configured access; invitation state is measurable; protected content is not leaked; Feed content remains event-centered; host can understand practical delivery/response state.

S3 — Free RSVP/registration, withdrawal and participant changes. A participant commits without payment, supplies only required information, receives persistent confirmation and may later withdraw or amend permitted participant information. Branches include duplicate submission, capacity loss during submission, registration closed, eligibility change, plus-one/guest only when explicitly supported, and host-side participant removal. Acceptance: one authoritative participation record; truthful status; capacity and eligibility revalidated; withdrawal does not erase consequential history.

S4 — Capacity, waitlist and admission availability. Capacity may apply globally or to an admission class. Branches include full capacity, concurrent last-space attempts, reopened capacity, waitlist if activated, promotion from waitlist, class-specific availability and host capacity change. Acceptance: no oversell from stale clients; availability is authoritative at commitment; waitlist is never implied unless configured; participant and host counts reconcile.

S5 — Paid admission, refund and transfer. A participant purchases an admission class and receives a credential only after authoritative payment success. Branches include pending/unknown payment, duplicate retry, refund, partial/full event cancellation consequence, transfer only if supported, admission invalidation and charge/payment reconciliation. Acceptance: payment, order, admission and credential remain distinct; no duplicate charge/admission; refund/transfer changes credential validity consistently; terms are visible before commitment.

S6 — Material change, postponement and rescheduling. A host changes consequential published information. Branches include time/date, venue, virtual destination, eligibility, admission terms, capacity and postponement/reschedule. Acceptance: Joy distinguishes material from harmless edits; preserves change history; affected participants receive appropriate notice; reschedule preserves the original event relationship and explicitly resolves admission validity, refund/withdrawal options and re-confirmation where required.

S7 — Cancellation and event unavailability. Host cancellation, policy removal, access revocation and temporary technical failure produce different states where safe. Acceptance: cancellation is intentional and auditable; registrations/purchases stop; participant history remains; refund/notification failures surface; privacy-sensitive denial does not disclose protected information.

S8 — Physical admission and check-in operations. Operator verifies a participant through QR/credential or approved lookup. Branches include valid first entry, duplicate scan, wrong event, refunded/invalid credential, re-entry, multiple lanes/operators, manual lookup, printed/physical fallback, accessibility/priority handling, on-site admission only if supported, and network/power degradation. Acceptance: QR is a representation rather than source of truth; check-in is auditable; fallback does not bypass authorization; concurrent operators reconcile to authoritative attendance state.

S9 — Virtual/hybrid access. Authorized participants retrieve protected virtual access according to release rules. Branches include not-yet-released access, changed destination, revoked authorization, hybrid physical/virtual choice and expired event access. Acceptance: protected join information never becomes public metadata; authorized users can retrieve it reliably; material changes propagate through the same change rules.

S10 — Host operational readiness, communication and reminders. Before an event the host reviews participant/admission state, capacity, operators, access requirements, unresolved issues and essential communications. Branches include scheduled/triggered reminders, delivery failure, material-change notice, operational alert, event Discussion/Message Board activity, Ask Host assistant enabled/disabled state, routine automated answer, low-confidence or judgment-dependent question, explicit human request and escalation to host contact. Acceptance: operational failures are visible; communication status is distinguishable from event truth; reminders do not become a prerequisite for the event itself; the assistant is visibly automated and grounded in permitted event information; it cannot make consequential commitments; escalation is understandable and carries only permitted useful context.

S11 — Completion, history, repeat and duplication. Completed/cancelled events remain historical records. A host may duplicate/repeat an event into a new Draft. Acceptance: duplication may copy reusable configuration but never copies participant records, payments, credentials, check-ins, communications, analytics or consequential history; participant and host histories accurately reflect the original event outcome.

S12 — Participant-to-host and multi-context continuity. A person can attend some events and host others with one identity. Acceptance: no account conversion or permanent role switch; hosting controls do not obscure participation; relevant hosted and joined events remain reachable.

S13 — Specialized event roles. Vendor/exhibitor, speaker/presenter, volunteer, staff/operator and media roles may layer role-specific workflows onto an event. Branches may include application/approval, booth/category preferences, supporting evidence, fees/deposits, credentials, access windows, assigned resources and setup/teardown. Acceptance: specialized roles extend the shared event model rather than creating separate event products; stage scope controls which workflows are actually implemented.

S14 — Contextual event gamification. Game mechanics may exist only when they materially improve the event itself—for example event-specific challenges, participation mechanics or host-designed experiences. Sontu must not manufacture platform engagement through generic XP, streaks, follower-style progression or rewards for using Sontu itself. Acceptance: event gamification is optional, context-bound, cannot block or falsify core event state, cannot manipulate trust/reputation, and does not create a platform-level engagement loop.

S15 — Failure, recovery and stale-state handling. Consequential actions including publish, register, purchase, update, cancel, refund and check-in must handle network/server failure, timeout, retry, stale authorization and conflicting state. Acceptance: failed, pending/unknown and successful outcomes remain distinct; retries are safe where duplicate consequences matter; persisted authoritative state wins; user receives a useful recovery/recheck path; telemetry captures failure class without redefining product truth.

S16 — Registration questions, guest/plus-one and acknowledgements. Where scope permits, a host may collect a deliberately limited set of event-relevant participant responses, guest counts/plus-ones or required acknowledgements. Branches include optional versus required questions, lawful organization/company fields, prerequisites, waivers/acknowledgements, guest-count limits and participant edits before cutoff. Acceptance: collection is bounded and purpose-specific; sensitive or arbitrary data is not requested merely because custom fields exist; guest records remain attributable to the primary registration as designed; acknowledgements are not treated as legal assurance beyond the approved Legal/Safety standard.

S17 — Schedule, multi-day, series and session variation. The baseline event has one occurrence with clear start/end/timezone. Where stage scope activates added schedule depth, branches may include multi-day representation, simple recurring/series events, sessions/tracks and session-level capacity/admission only when explicitly supported. Acceptance: the parent event remains coherent; timezones and occurrence boundaries are unambiguous; unsupported conference/course/league complexity is not implied; adding schedule depth does not fork the core event model.

S18 — Calendar handoff and participant preparation. After confirmed participation, a user may add supported event information to an external calendar and return to Joy for authoritative changes. Branches include physical/virtual/hybrid details, timezone conversion, event reschedule and stale exported calendar information. Acceptance: calendar export is a convenience representation, not authoritative event state; protected access information is not exposed inappropriately; Joy clearly remains the source for material updates.

S19 — Trust, support, moderation and administrative intervention. Activated features require a proportionate report/support path and internal administrative ability to inspect relevant event/user state and address operational or policy problems. Branches include user report, prohibited event/content, account/content disablement, restricted-event issue, operational support request and privacy-permitted export. Acceptance: administrative action is permissioned and auditable; support tooling does not silently rewrite event truth; affected public/private information follows safety/privacy rules; incident escalation can be traced without exposing unnecessary participant data.

S20 — Discovery, browsing and event findability. Public/listed events can participate in Joy discovery to the stage-approved depth while unlisted/private events remain protected. Branches include category, location and time filtering where supported, no-results/low-supply states, cancelled/unavailable events and transition from public evaluation into participation. Acceptance: discovery respects visibility and restricted-information rules; ranking/filtering does not redefine eligibility or availability; useful public evaluation remains possible without forced account creation.

S21 — Post-event retention and follow-up. After completion, approved post-event actions may support repeat participation and hosting without turning Joy into a person-centered social network. Branches include host follow-up invitation to a future/new event, audience reuse only where permitted, event-centered Feed highlights/recaps, and later richer media/gallery participation if activated. Acceptance: follow-up communication respects consent and communication rules; a completed event is not silently reopened; new invitations create a new event/participation relationship; Feed/post-event content cannot alter attendance or event-history truth.

Category-pressure reconciliation: the scenario set now explicitly covers every unresolved pressure point identified by the category authority at the level required before UX: guest/plus-one and bounded registration questions (S16); multi-session/series representation (S17); specialized participant roles (S13); acknowledgements/waiver touchpoints without inventing legal sufficiency (S16); admission classes/refund/transfer/re-entry (S5/S8); fallback check-in (S8); protected virtual access (S9); material-change notice (S6/S10); and restricted-information behavior (S7/S20 plus J10). Form B correction

Minimum internally justified journey spine

LIMITED PARTICIPANT CORE: receive or resolve permitted event context → understand current truth and required action → make or update a consequential commitment where Sontu is the appropriate authority → retrieve the current state later without unnecessary account friction → receive/resolve material change → perform event-day action only where Sontu ownership materially improves the outcome → understand closure/follow-up state.

Participant-account rule

N88-G2 PROGRESSIVE JOURNEY PACKAGE — 2026-09-07

Purpose and boundary  
This package reconciles the provisional Form B journey model with the four-archetype internal pressure test. It defines one progressive host journey and one bounded participant journey that preserve the same coordination semantics from a simple private gathering through recurring community, wedding/milestone and business/professional contexts. It is requirements reasoning only. It does not lock navigation, routes, visual design, implementation architecture, prototype scope or N88-G3 readiness.

ONE PROGRESSIVE HOST JOURNEY  
H-A — INTENT / ACTING AUTHORITY. The host begins with what they are organizing and whether they act personally or for an organization. Sontu establishes durable event/undertaking identity and explicit acting authority. Simple gathering: personal authority is nearly invisible after confirmation. Recurring/community: Series/Program context may be selected or established. Wedding: household/co-host authority may become relevant without creating enterprise roles. Business: organization ownership and scoped operator authority become explicit.

H-B — MINIMUM SHARED TRUTH. The host provides only the event facts necessary for another party to understand the undertaking: purpose/identity, relevant time, place/access and distribution/access context. The system does not require a category-specific mega-form. Simple gathering can stop at a very small set. Other archetypes reveal additional configuration only when consequence requires it.

H-C — COORDINATION RELATIONSHIPS / COMMITMENTS. Sontu asks what commitments actually matter. Simple gathering may need only invited/coming/not-coming. Recurring community may add capacity/waitlist. Wedding may add party/plus-one and bounded preparation information. Business may add registration, organization roles or external entitlement status. Payment, specialist admission and other states remain integrated/deferred unless Sontu ownership is justified.

H-D — READINESS / ATTENTION. Before activation and while the event is active, the host sees only unresolved coordination state that requires understanding or action: missing event truth, unanswered consequential commitments, capacity pressure, participant preparation gaps, provider uncertainty, permission problems or other material blockers. Optional advanced planning does not become universal setup.

H-E — ACTIVATE / DISTRIBUTE. The host intentionally makes the relevant shared truth available to the intended audience and receives a credible participant-facing representation or approved distribution/integration path. Publication/activation and distribution remain distinct. Simple private events can use a secure direct link/invite. Public community events may use purposeful public distribution. Business events may use existing organizational channels/integrations.

H-F — MONITOR / CHANGE / OPERATE. The host sees authoritative current event context, consequential commitments, material changes, unresolved failures and the next useful action. A material edit previews affected people/relationships and follow-up before commitment. Specialist operational actions remain in specialist systems when appropriate, with Sontu showing only coordination-relevant reconciled state. Event-day Sontu interaction appears only when it improves a real task.

H-G — RECONCILE / CLOSE. The host resolves material unfinished state, deliberately closes/completes the event or instance, preserves consequential history and sees any legitimate reusable context. Closure does not erase cancellation, commitments, attendance evidence, commercial consequences or change history.

H-H — REPEAT / CONTINUE. For recurrence, a new Event Instance derives only approved reusable Series/Program context. For one-time events, duplication creates a new event identity if useful. P-D — RETRIEVE / PREPARE. The participant can return to the current event truth and their relevant status through the lowest-friction viable mechanism. Simple gatherings may use a secure recoverable link. Higher-consequence contexts may justify stronger identity or a persistent relationship surface. Preparation information is limited to what the event actually requires.

P-E — MATERIAL CHANGE. When consequential event truth changes, the participant sees the current state, the material difference and any required response without reconstructing the situation from disconnected messages. Reconfirmation, withdrawal, refund implications, access changes and cancellation remain distinct where relevant.

P-F — EVENT-DAY ACTION, ONLY IF JUSTIFIED. Sontu appears during the event only when a concrete information/action need exists: retrieve access, present entitlement/credential, respond to an operational change, contribute event-scoped media, or another contextually justified action. No event-day screen time is manufactured.

P-G — CLOSURE. The participant can understand completed/cancelled/postponed/reconciled state and any legitimate unresolved consequence. Post-event media or follow-up may exist when event-relevant, but closure does not automatically create a social relationship, feed or permanent Sontu membership.
