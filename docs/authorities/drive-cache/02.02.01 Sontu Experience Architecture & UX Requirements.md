SONTU EXPERIENCE ARCHITECTURE & UX REQUIREMENTS

Authority role  
This document owns Sontu’s product experience architecture: surfaces, navigation, information hierarchy, interaction/state requirements and cross-surface UX rules. It is downstream of Product Foundation, Event Model, Category Requirements, Scope, and User Journeys & Acceptance Criteria. It does not redefine product semantics or technical architecture.

1 — EXPERIENCE PRINCIPLE  
Sontu should feel like one coherent event system with two primary perspectives: participate in events and operate events. Complexity should appear only when the event configuration requires it.

The experience must not expose the entire capability model as a giant settings form. Progressive disclosure, contextual defaults and event-type-aware configuration are required.

2 — PRIMARY SURFACES  
Sontu App  
Authenticated participant and host experience. Supports discovery, joined events/admissions, event creation/management, organization context, account/settings and protected actions.

Public Web  
First-class distribution and evaluation surface for public/unrestricted events. Viewing does not require an account. Participation actions may transition into authentication or app/web authenticated flow when identity is legitimately required.

Host Operations  
A coherent event-management surface inside the authenticated product. It should not require hosts to hunt across unrelated areas to understand or operate an event.

Internal Admin/Support  
Separate privileged operational surface or mode. It must not leak into normal host/attendee navigation merely because support tooling exists.

3 — APP INFORMATION ARCHITECTURE

APPROVED CONSUMER NAVIGATION DIRECTION  
Sontu’s regular app is attendee-facing by default. Hosting remains available to every eligible identity, but host-management complexity should not dominate global navigation merely because a user can host.

Phone global shell:  
\- Top-left: Profile/avatar entry for profile, account/settings, help/support, logout and other low-frequency personal controls.  
\- Top-right: Search and Notifications as persistent utilities.  
\- Bottom: Home, Discover, Events, Feed. This is the founder-approved working navigation direction. Feed is an event-centered content and attention surface, not a general personal social timeline.

Home — answers “What matters to me right now?” It is Sontu’s personalized action-and-relevance surface rather than the event-content feed, invitation inbox or duplicate Events repository. It can prioritize the user’s next event, time-sensitive preparation, tickets/credentials, check-in readiness, relevant host status and contextually useful event information. Invitations and invitation-response work belong in Events. Home may adapt its information hierarchy according to the user’s active participant and hosting relationships.

Discover — answers “What else could I do?” Attendee-facing exploration includes permitted public events, For You if/when evidence supports personalization, Near You/location-aware discovery, search, filters, categories and map/nearby presentation. Direct event entry remains first-class.

Events — answers “What am I doing/planning to do, or what is already attached to me?” It is the signed-in user’s chronological event hub, representing upcoming relationships such as attending/registered, invited, interested/saved and hosted events, with clear relationship labels and filters/views where useful. Hosting is contextual, not a permanent account mode. A hosted event card is clearly marked as hosted. Opening the card enters event detail; an authorized host/operator receives an obvious Edit/Manage action into that event’s host workspace. Create Event belongs in Events rather than occupying a permanent global navigation position.

Feed — answers “What’s happening in the event world around me?” It is Sontu’s event-centered content and attention layer across the event lifecycle. Subject to stage-approved social/media scope, it can support event/host/venue/organizer-originated posts and updates, anticipation and promotional content before events, permitted event activity during events, and post-event highlights, media, recaps and follow-up content. Feed may eventually support promoted event content as a business distribution/attention surface, but monetized placement requires the applicable business, trust, ranking and disclosure rules before activation. The controlling principle remains that Sontu’s social object is the event, not the person: Feed does not authorize general-purpose personal-profile posting or profile timelines.

Host access — regular Sontu must keep casual and moderately sophisticated hosting low-friction without a permanent Hosting tab. Hosts can reach management from their hosted event cards/details, contextual Home surfaces where justified, and appropriate profile/menu entries. The product should measure whether this creates unacceptable management friction during prototype testing.

Mixed is the default working direction. These are presentation presets, not account modes or permission states: the same identity can host and participate without switching roles. Home should also adapt contextually—for example, hosting information can rise when the user has an actively managed event and recede when it is no longer relevant. Exact module ordering, optional per-module controls and final customization UI remain prototype/human-QA decisions.

This is a product-surface separation, not permission to fork event truth into incompatible systems. Exact boundary remains to be specified downstream.

Event Hub / Event Profile — opening an event from Events, Discover, Feed, Notifications, Search or a permitted shared/deep link resolves to the same event-centered destination, adapted to the viewer’s relationship and permissions. Overview is universal and prioritizes cover/identity, host, date/time/location or virtual format, participation/admission state, primary action and concise essential information; secondary detail is progressively disclosed. Activated modules may include Updates/Timeline, Media, Activities, Discussion/Message Board, Schedule/Agenda, Ticket/Credential, Map/virtual access and other event-specific capabilities. Modules appear only when populated, activated or relevant so a simple event remains simple. Authorized hosts/collaborators additionally receive an obvious Host Dashboard/Manage surface for the same event rather than a separate competing event identity. Event-specific actions default to the Event Hub rather than bloating Home or the global Events list.

Saved / Bookmarks — saved/interested events are a personal relationship state and may be represented within Events and Discover. Saving does not register, reserve capacity, grant access or imply endorsement.

Navigation behavior — global roots remain intentionally few; high-frequency utilities use top chrome rather than consuming bottom positions. The four consumer roots have distinct jobs: Home \= personalized action and relevance; Discover \= deliberate event exploration; Events \= the user’s event relationships and management; Feed \= event-centered content and attention before, during and after events. Wider authenticated web may adapt the same information architecture to side/top navigation rather than copying phone chrome. Event detail and host workspaces are contextual destinations beneath the global shell. Back/cancel returns to the initiating context where safe; authentication interruptions restore intended route/action. This navigation model is founder-approved; evidence from human QA may still refine presentation without casually changing these root jobs.

4 — PUBLIC WEB ARCHITECTURE  
Public event page hierarchy should prioritize:  
1\. What the event is.  
2\. When and where/how it occurs.  
3\. Who hosts it.  
4\. What the attendee needs to know.  
5\. Admission/price/availability.  
6\. Primary participation action.  
7\. Secondary details.

Do not lead with account creation, Sontu marketing or platform chrome at the expense of the event itself.

Public pages require deliberate states for scheduled, in-progress where relevant, sold out/full, cancelled, completed, unavailable/not found and access-restricted transitions.

5 — EVENT DETAIL EXPERIENCE  
Event detail should use one conceptual hierarchy across app and web even if presentation differs.

Event Hub baseline:  
\- One event identity/profile shared across entry routes, with viewer-specific permissions and relationship state.  
\- Lightweight positive event reaction/hype capability at Beta depth; exact label/mechanic is prototype-tested rather than assumed to be a generic social Like.  
\- Host trust markers are semantically separated: Verified represents an actually verified fact/identity or organization assurance; host achievements represent gamified milestones; a future Super Host designation represents evidence-backed hosting quality/reliability and is not activated until sufficient history and criteria exist.  
Core information:  
\- Event title/context/category where useful.  
\- Host identity.  
\- Date/time/timezone.  
\- Format.  
\- Permitted location/virtual information.  
\- Description/key participation information.  
\- Admission/registration state.  
\- Capacity/availability when useful.  
\- Eligibility/restriction messaging where permitted.  
\- Primary CTA.  
\- Material updates/cancellation state.

Authenticated participants can additionally access their participation/admission status, credential and protected event information as authorized.

6 — EVENT CREATION ARCHITECTURE  
Creation should be a guided configuration flow rather than one enormous form.

Recommended stages:  
1\. Basics — title, category/context, description.  
2\. When & Where — date/time/timezone, physical/virtual/hybrid configuration.  
3\. Access — public/unlisted/private, invitations/access rules.  
4\. Participation — open/RSVP/free registration/paid admission, capacity.  
5\. Requirements — eligibility/restrictions and category-relevant configuration.  
6\. Review — attendee-facing preview and blocking validation.  
7\. Publish — intentional consequential action.

Stages may collapse for simple events when testing proves fewer steps are clearer. The information architecture should preserve conceptual separation even if UI combines screens.

7 — PROGRESSIVE DISCLOSURE  
Simple events should stay simple.

Examples:  
\- Private birthday should not show enterprise team configuration, ticket classes, vendor workflows or conference sessions.  
\- Free community event should not force payment configuration.  
\- Paid event reveals payment/ticketing requirements.  
\- Restricted event reveals eligibility configuration and warnings.  
\- Organization event reveals relevant ownership/team context.  
\- Virtual event reveals protected virtual-access controls.

Category can influence defaults/templates/prompts, but capability settings remain grounded in shared semantics.

8 — HOST EVENT WORKSPACE  
Each hosted event should have one operational home.

Recommended workspace sections:  
\- Overview  
\- Event Details  
\- Participants / Admissions  
\- Communications  
\- Check-in, when configured  
\- Results, when meaningful  
\- Settings / Access

Overview should answer: What state is this event in? What needs attention? How many people are participating? Is capacity/admission healthy? Are there unresolved operational failures? What is the next likely host action?

Avoid vanity analytics displacing operational needs.

9 — ORGANIZATION CONTEXT  
Sontu must make personal vs organization action context explicit.

Requirements:  
\- Host can tell who owns an event before publication.  
\- Organization switch/context should not be hidden in an obscure setting.  
\- Permission-sensitive actions should be unavailable or safely denied when unauthorized.  
\- Team member removal/role changes must be reflected without relying on stale UI.  
\- Organization-owned events remain visually associated with organization identity.

10 — EVENTS HUB  
Events should unify the user’s event relationships chronologically while keeping each relationship understandable. Attending, invited, interested/saved and hosting states use clear labels/filters rather than separate global destinations. A person attending an event should not encounter host-management UI unless authorized; hosted events remain easy to identify and manage from their cards/details.

Participant states should be human-readable rather than exposing raw domain enums. Examples: Registered, Ticket ready, Awaiting payment confirmation, Cancelled, Refunded, Event cancelled, Completed.

11 — DISCOVERY  
Discovery depth should match supply.

Gate 2/Beta architecture:  
\- Search/browse entry.  
\- Useful category, location/date/time filtering only where sufficient supply exists. Location-aware discovery should support an explicit “Near you”/nearby mode using foreground device/browser location when the user permits it, with manual city/area selection as a fully functional fallback. Background/continuous location is not required.  
\- Direct links remain first-class.  
\- Empty discovery state should help rather than pretend marketplace density exists.

Do not design an algorithmic recommendation feed as a prerequisite to Sontu’s core loop.

12 — AUTHENTICATION TRANSITIONS  
Authentication should occur at the boundary where identity becomes necessary.

Requirements:  
\- Unrestricted public event viewing remains account-free.  
\- After authentication, return the user to the intended event/action.  
\- Authentication cancellation/failure does not mutate event/payment/registration state.  
\- Protected/private/restricted routes can require authentication before content exposure.

13 — STATE ARCHITECTURE  
Every consequential surface must explicitly support:  
\- Initial/empty.  
\- Loading.  
\- Loaded/success.  
\- Validation error.  
\- Recoverable server/network error.  
\- Permission/access denied.  
\- Unavailable/not found where applicable.  
\- Pending/unknown outcome where distributed/payment operations can be uncertain.

Do not use indefinite spinners as an outcome.

14 — CONSEQUENT ACTION UX  
Publish, cancel, material event changes, payment, refund, ownership/permission changes and similar actions require UX proportional to consequence.

Requirements:  
\- Clear action label.  
\- Consequence visible before commitment.  
\- Confirmation only where it prevents meaningful harm; avoid confirmation fatigue.  
\- Success/failure/pending result explicit.  
\- Retry safe and understandable.  
\- Destructive action visually distinct but not theatrically alarming.

15 — PAYMENT EXPERIENCE  
Before purchase commitment, attendee must understand event/admission choice, price and material fees/terms.

Payment UX must distinguish:  
\- Ready to pay.  
\- Processing.  
\- Successful.  
\- Failed.  
\- Pending/unknown/reconciliation required where applicable.

Never show a valid ticket/credential solely because a client-side payment screen completed.

16 — CHECK-IN EXPERIENCE  
Operator check-in must optimize for rapid, unambiguous decisions.

Required result states include:  
\- Valid / admitted.  
\- Already used / duplicate.  
\- Wrong event.  
\- Invalid/cancelled/refunded.  
\- Unable to verify / degraded state.

Visual and text treatment must make the result understandable under real event conditions. Manual lookup/fallback, if in scope, should be reachable without weakening authorization/audit controls.

17 — RESTRICTED EVENT EXPERIENCE  
Public metadata and protected information must be visually/structurally separated.

Requirements:  
\- User understands additional verification/access is required without revealing protected content.  
\- Ineligible/unverified users receive safe states.  
\- Restricted-event UX must not imply Sontu guarantees legal eligibility beyond the approved assurance method.  
\- Sensitive eligibility data should not be casually repeated across screens.

18 — VIRTUAL/HYBRID EXPERIENCE  
Public event information must not accidentally expose protected join links/codes.

Authorized attendee should have a reliable place to retrieve virtual access when released. Before release, show a deliberate state such as access becoming available later rather than a broken/missing-link impression.

19 — MATERIAL EVENT CHANGES  
When a published event changes materially:  
\- Host should see that the change may affect attendees.  
\- Confirmation/notification consequence should be clear.  
\- Attendee should see the updated truth and material change messaging where applicable.  
\- Cancelled event state should dominate stale participation CTAs.

20 — EMPTY STATES  
Empty states should explain the product state and offer the next useful action.

Examples:  
\- No hosted events → Create an event.  
\- No joined events → Discover events or open an invite.  
\- No participants yet → share/invite guidance, not a blank table.  
\- No discovery results → adjust filters/search; do not fabricate recommendations.

21 — ERROR AND DEGRADED STATES  
Errors should answer:  
\- What happened, at user-appropriate depth?  
\- Did the consequential action occur?  
\- What can the user do now?

Technical identifiers/log details belong in telemetry/support, not normal user messaging.

When outcome is unknown, say it is unresolved rather than guessing success/failure.

22 — ACCESSIBILITY  
Accessibility is baseline product quality.

Gate 2 designs should support:  
\- Keyboard/focus order for web prototype where applicable.  
\- Sufficient contrast.  
\- Meaning not communicated by color alone.  
\- Readable target sizes.  
\- Screen-reader-semantic design assumptions.  
\- Error association with relevant controls.  
\- Motion that is nonessential and reducible where used.  
\- Clear language and predictable navigation.

23 — RESPONSIVE EXPERIENCE

Route families are conceptual and may be implemented with platform-appropriate route syntax, but their relationships are binding for Gate 2 planning.

PUBLIC / DISCOVERY  
\- Discover: browse/search/filter permitted public events; empty and low-supply states; direct event links remain first-class.  
\- Public Event Detail: event-first hierarchy, public metadata only, primary participation CTA, share/calendar actions where supported, explicit sold-out/cancelled/completed/unavailable states.  
\- Restricted Access Transition: safe public metadata → authentication/eligibility boundary → authorized detail or safe denial.

PARTICIPATION  
\- My Events — Upcoming/Active: joined events ordered by relevance/time with human-readable participation state.  
\- My Events — History: completed/cancelled/refunded historical relationships without crowding active events.  
\- Participant Event Detail: authoritative event information plus the user’s participation/admission state, requirements, material updates and permitted withdrawal/refund actions.  
\- Admission/Credential: ticket/QR or other credential representation, validity state, event identity and practical entry information; never claims validity from stale client state.  
\- Participation Commit: RSVP/free registration or admission-selection flow with bounded participant questions, capacity/eligibility revalidation and explicit success/failure.  
\- Paid Checkout: admission choice → terms/fees → payment handoff/processing → success, failure or unresolved reconciliation state.  
\- Virtual Access: authorized join information with not-yet-released, changed and unavailable states.

CREATION  
\- Create Entry: establish acting context/owner and create or resume a Draft.  
\- Basics: title, category/subcategory, description and cover media where supported.  
\- When & Where: start/end/timezone plus physical/virtual/hybrid configuration.  
\- Access: public/unlisted/private and invitation/access configuration.  
\- Participation: open/RSVP/free/paid mode, capacity, admission classes when activated, registration questions/guest rules when activated.  
\- Requirements: eligibility/restrictions, acknowledgements and category-relevant configuration only when applicable.  
\- Operational Setup: operators/check-in/communications and other stage-approved readiness options; simple events can bypass irrelevant sections.  
\- Review & Preview: attendee-facing representation, missing blockers, consequential settings and save state.  
\- Publish Result: explicit success/failure/pending where applicable plus next actions to share/invite/manage.

HOSTING  
\- Hosting List: Draft, Published/Upcoming, In Progress and History/Cancelled groupings; ownership context visible.  
\- Host Event Overview: lifecycle state, readiness/attention items, participation/capacity/admission summary, communication or operational failures, next likely actions.  
\- Event Details: edit permitted configuration; material changes route through consequence review rather than silent save.  
\- Access & Invitations: visibility/access configuration, invite distribution/status and saved audiences only when in scope.  
\- Participants / Admissions: participant records, admission/payment/credential distinctions, filters/search and permitted participant actions.  
\- Communications: compose/send essential announcements; reminder/change/cancellation communication status; delivery failure surfaced operationally.  
\- Check-in: scan/lookup entry, rapid result state, re-entry/fallback policy when activated and multi-operator-safe interaction assumptions.  
\- Results / History: essential registrations/admissions/attendance/refund outcomes and event history without vanity metrics displacing operations.  
\- Duplicate / Repeat: create a new Draft from reusable event configuration; explicitly excludes participant, payment, credential, check-in, communication, analytics and historical records.

ORGANIZATION / ACCOUNT / SUPPORT  
\- Organization Context: organizations the user belongs to, acting context and organization identity.  
\- Organization Team: stage-approved membership/role management with safe removal and permission-change states.  
\- Account: identity/profile, notification preferences, session/security controls, accessibility/language settings where supported and legal/account actions.  
\- Support / Report: contextual support/report entry; normal users do not see privileged admin tooling.  
\- Internal Admin/Support: separate privileged surface for relevant user/event inspection, operational intervention and audit-safe actions.

OVERLAYS / CONSEQUENTIAL FLOWS  
\- Material Change Review: summarizes changed consequential fields, participant impact and notification/reconfirmation/refund implications before commit.  
\- Postpone/Reschedule Review: preserves event relationship and makes admission validity, participant options and notices explicit.  
\- Cancel Event: consequence summary, reason where required, intentional confirmation and result/follow-up state.  
\- Withdraw/Refund: participant-facing consequence and result state where policy permits.  
\- Capacity Full / Waitlist: truthful full state; waitlist entry/promotion only when configured.  
\- Permission / Eligibility Denial: safe denial without protected-information leakage.  
\- Failure / Unknown Outcome: recheck/retry path without fabricating success.

Cross-route rules: a user should never need to infer whether they are acting as participant, personal host, organization operator or privileged admin. Context must be visible at consequential points. Deep links and authentication interruptions preserve intended destination where safe. Public event URLs remain useful outside the app. No route may make a cached client representation more authoritative than event, permission, payment, admission or attendance truth.

App and web should share information hierarchy, not necessarily pixel-identical layouts.

\- Primary surfaces/navigation are coherent.  
\- Critical journeys map to screens/states without dead ends.  
\- Public web and app responsibilities are clear.  
\- Host and attendee perspectives are distinct but connected.  
\- Creation handles simple and complex configurations through progressive disclosure.  
\- Organization context is understandable.  
\- Payment/restricted/check-in states are represented.  
\- Loading/error/empty/denial/pending states are designed, not deferred.  
\- Accessibility/responsive requirements are explicit.

\- Prototype-relevant visual hierarchy/design-system rules are concrete enough to implement consistently.

29 — PUBLIC, DISCOVERY & EVENT-DETAIL IMPLEMENTATION SPECIFICATION

PUBLIC EVENT PAGE  
Purpose: let an unauthenticated or authenticated person understand an unrestricted public event and decide what to do without first learning Sontu or creating an account.  
Entry: direct/shared URL, Discover result, search engine/deep link, authenticated in-product link. Exit: participation commit, authentication/eligibility transition, share/calendar handoff, Discover/back, host identity where supported.  
Hierarchy: event cover/media when present → title and concise event context → date/time/timezone and location/format → host identity → primary participation/admission state and CTA → essential description/requirements → availability/capacity where useful → secondary details and share/calendar actions. Sontu promotional chrome must not outrank event truth.  
Primary CTA is state-derived: RSVP/Register, Get ticket, Join waitlist when configured, View ticket/registration when already participating, Sign in/Verify access when legitimately required, or no commit CTA when cancelled/completed/unavailable. Sold-out/full, cancelled and completed states replace stale acquisition CTAs.  
Public content must never expose protected invite data, private location details, virtual join credentials, restricted eligibility evidence, participant lists or host-operational information.  
Loading uses event-detail skeleton/layout reservation rather than an indefinite blocking spinner. Not-found/unavailable distinguishes unavailable content from a generic network failure where the system can know the difference. Recoverable network failure offers retry without inventing cached event truth.  
Responsive: phone uses a compact event-first stack with the primary action persistently reachable when appropriate; wider web may use a constrained content column plus action summary without changing hierarchy.

DISCOVER / RESULTS  
Purpose: help people find permitted public events while Sontu supply is still developing.  
Core controls: search/query entry; stage-approved date/location/category filters; a location control supporting Near you/current foreground location when permission is granted and manual city/area selection otherwise; clear active-filter state; result cards with title, time, location/format, host where useful, admission/availability cue and event image when available. Location permission is requested in context rather than as an unexplained startup requirement.  
No-results state distinguishes no supply from over-filtering where possible and offers clear filters/change search/direct-link guidance. Do not fabricate recommendation density. Direct event URLs remain first-class even if Discover is sparse.  
Result selection opens event detail and preserves Discover query/filter context on back. Loading, pagination/incremental retrieval and retry must avoid duplicate result confusion.

AUTHENTICATION TRANSITION  
Authentication is an interruption, not a destination. Preserve the intended event, requested action and safe non-sensitive form progress. After success, return to the exact legitimate continuation point and revalidate capacity, eligibility, event state and price before consequential commitment. Cancellation returns to the event or prior safe context without creating registration, order or admission state. Authentication failure communicates retry/recovery without implying the requested event action succeeded.

PRIVATE / INVITE ACCESS  
A private event route exposes only the minimum safe pre-authentication representation permitted by its access policy. Valid invitation/access resolution leads to authorized event detail; invalid, expired, revoked or wrong-account access produces a safe denial without confirming protected details beyond what policy permits. Signing in does not itself grant access.

RESTRICTED / AGE-GATED ACCESS  
Where public metadata is allowed, show enough event context to explain that additional access/eligibility is required. Verification/eligibility is a separate transition before protected detail or commitment. Pending, failed, ineligible and unavailable-verification states are explicit. Do not repeat sensitive eligibility evidence unnecessarily or imply Sontu guarantees legal eligibility beyond the approved assurance method.

EVENT-DETAIL STATE MATRIX  
Scheduled/open: normal event truth \+ valid participation CTA.  
Full/sold out: no normal acquisition CTA; waitlist only if configured.  
In progress: event truth remains available; participation action depends on event policy rather than assumed closure.  
Materially changed: prominent change notice precedes stale secondary content and routes existing participants to their updated relationship/options.  
Cancelled: cancellation dominates; registration/purchase CTAs removed; existing participants see their consequence/refund information through authenticated relationship surfaces.  
Completed: historical event truth may remain public where policy permits; acquisition CTA removed; appropriate follow-up/new-event action may appear only when configured.  
Unavailable/not found: no fabricated event details or stale CTA.  
Restricted/private: protected information withheld until authorization.

HOST-CONTROLLED DISTRIBUTION UX  
After successful publication, the immediate host result should make the first-value loop obvious: view the credible attendee-facing page, copy/share its permitted link, use stage-approved native share handoff or invitation controls, and move directly into event management. Sontu should not force the host into analytics/settings before distribution. Source/share attribution may be captured where privacy-appropriate but should not add friction to sharing.

PUBLIC/DISCOVERY ACCEPTANCE  
A first-time visitor can determine what, when, where/how, who hosts, admission/availability and the next legitimate action without an account for unrestricted public events. Authentication returns to intent. Protected information never leaks through public states. Back navigation preserves useful discovery context. Cancelled/full/completed states cannot present stale commit actions. A newly published host can reach a shareable event representation immediately.

30 — PARTICIPANT, MY EVENTS & ADMISSION IMPLEMENTATION SPECIFICATION

MY EVENTS — UPCOMING / ACTIVE  
Purpose: provide one reliable chronological home for events attached to the signed-in user through participation, invitation, interest/save or hosting relationships.  
Default ordering prioritizes the next actionable/upcoming event rather than creation time. Each item shows event identity, date/time, location/format cue and human-readable relationship state. Hosting ownership does not replace or merge the participation relationship if the same person is also attending.  
Primary item action opens Participant Event Detail. Credential shortcut may appear when a valid/retrievable admission exists and proximity to the event makes it useful. Pending payment, event cancellation, material change or required participant action must be visible without requiring the user to infer it from a generic badge.  
Empty state offers Discover and legitimate invite/deep-link entry rather than implying the user must host.

MY EVENTS — HISTORY  
Completed, cancelled, withdrawn and refunded relationships are separated from active/upcoming use. History preserves truthful relationship/outcome state and may offer repeat/follow-up discovery where configured, but cannot reopen the completed relationship or imply a historical credential remains valid.

PARTICIPANT EVENT DETAIL  
Hierarchy: event truth and material status → the user’s participation/admission state → next required action → practical event information → credential/access when authorized → permitted change/withdraw/refund actions → secondary event details.  
Existing-participant surfaces must prefer authoritative current event/relationship state over cached public-page assumptions. Material changes, cancellation, refund status and virtual-access changes are prominent.

PARTICIPATION COMMIT — FREE / RSVP / REGISTRATION  
Flow: choose/confirm participation mode if necessary → answer only configured bounded questions/guest information/acknowledgements → review material commitment → server-side revalidation → explicit result.  
Required fields are visibly distinguished from optional fields. Validation occurs at useful field/step boundaries without erasing valid answers. Authentication interruption preserves safe progress. Capacity, event availability and eligibility are revalidated at commitment; a concurrency loss produces a truthful full/waitlist/failure result rather than apparent success.  
Success establishes the participation relationship and routes to Participant Event Detail/My Events with clear confirmation. Failure leaves no ambiguous registration claim.

PAID ADMISSION / CHECKOUT  
Flow: select valid admission class/quantity/guest configuration → show price, material fees and terms → authenticate/collect permitted attendee data as required → payment handoff/processing → authoritative success, failure or unresolved state.  
A client payment completion screen never creates a valid admission by itself. Pending/unknown payment displays an unresolved order state with safe recheck/support path and no valid credential. Failure permits safe retry without duplicate-order ambiguity. Successful payment routes to participant/admission detail with the resulting authoritative admission state.

ADMISSION / CREDENTIAL  
Credential surface prioritizes rapid practical use: event identity, admission holder/entitlement where appropriate, date/time, entry guidance, credential/QR representation and human-readable validity state. A QR image is not itself proof of validity. Refunded/cancelled/invalid/wrong-event/used states cannot retain a normal-valid visual treatment.  
Credential retrieval must be possible from My Events and Participant Event Detail without navigating through purchase history. Offline/display caching, if later activated, must visually communicate last-known representation and cannot override server/operator truth.

VIRTUAL / HYBRID ACCESS  
Authorized access is reachable from Participant Event Detail when released. Before release, show when/how access will become available. Changed or revoked access replaces stale join information. Public pages never expose protected join credentials.

PARTICIPANT EXCEPTIONS  
Withdrawal/refund: show policy/permitted consequence before commitment, then explicit success/failure/pending result.  
Event cancelled: cancellation dominates, with refund/follow-up state where applicable.  
Postponed/rescheduled: preserve relationship; show old→new material timing and any reconfirmation/refund choice required.  
Capacity lost during commit: show truthful failure or waitlist option; never silent retry into a different admission.  
Invitation revoked/access lost: safe denial and support path where appropriate; do not leave protected content cached as usable.  
Duplicate/replayed commit: idempotent result should return the existing relationship/order when safe rather than create duplicates.

PARTICIPANT RESPONSIVE / ACCESSIBILITY  
Critical status and primary action remain near the top on phone. Credential display supports high-contrast scanning conditions and does not rely on color alone. Forms preserve labels, error association, keyboard/focus order on web and accessible target sizes. Dense historical/secondary information collapses below current event truth rather than shrinking critical controls.

PARTICIPANT ACCEPTANCE  
A participant can recover an upcoming event and credential after leaving the original flow; can distinguish registered, ticket-ready, pending-payment, refunded, cancelled and completed states; cannot receive a valid-looking credential from an unresolved payment; sees material event changes before stale actions; and can complete a simple RSVP without encountering host/organization configuration.

31 — EVENT CREATION IMPLEMENTATION SPECIFICATION

CREATE ENTRY & OWNERSHIP  
Purpose: start a new event or resume an existing Draft while making the acting owner explicit before consequential configuration. Primary consumer entry is Create Event from Events; additional legitimate entries may include a hosted-event context, duplicate/repeat action or organization context.  
The first creation surface shows the acting owner as Personal or a permitted Organization. If the user belongs to multiple organizations, ownership selection is explicit rather than inferred from the last screen visited. Users without organization permission cannot select that organization. Changing owner after meaningful configuration requires a consequence-aware transition because permissions, branding, payment capability and operators may differ.  
A new creation action creates or resumes a Draft, never a Published event. Duplicate/Repeat creates a new Draft from reusable configuration only and excludes participants, orders/payments, credentials, check-ins, communications, analytics and historical records.

DRAFT PERSISTENCE & RECOVERY  
Draft progress should save automatically at safe field/step boundaries and expose a human-readable save state such as Saved, Saving, or Save failed. A transient save failure does not discard the local form silently; the user receives retry/recovery behavior and must not be told a draft is saved when persistence is unresolved.  
Leaving creation intentionally preserves a valid Draft unless the user explicitly discards it. Returning through Events/Create Event or the hosted-event management context can resume the Draft at the last useful stage. Multiple drafts are distinguishable by title or fallback label, owner and last-edited time. Abandoned untitled drafts must not multiply invisibly; creation entry should offer resume vs start new when an obvious recent draft exists.  
Browser/app interruption, authentication refresh and ordinary navigation should preserve safe non-sensitive progress where technically feasible. Payment credentials, sensitive eligibility evidence and other prohibited data are not persisted merely for convenience.

STAGE 1 — BASICS  
Core fields: Event title — required before publish, concise length validation, no artificial requirement before the user can begin drafting. Category — required before publish where category drives requirements/defaults; category is a classification/defaulting aid, not a separate event model. Subcategory — optional or conditionally required only where an approved category rule needs it. Description — optional while drafting; publish requirement depends on event configuration/category policy. Cover media — optional in Beta where supported; upload/replace/remove states and failure are explicit.  
Category selection may reveal relevant suggestions later but must not dump every category capability onto the Basics screen. Changing category preserves compatible data and clearly flags incompatible configuration requiring review rather than silently deleting it.

STAGE 2 — WHEN & WHERE  
Fields: start date/time — required before publish; end date/time — required when the event model/category needs a bounded end, otherwise optional with a deliberate no-end/estimated-end rule if approved; timezone — explicit and defaulted from reliable context but editable; format — Physical, Virtual or Hybrid; physical venue/location fields when physical component exists; virtual access configuration when virtual component exists.  
End cannot precede start. Timezone changes show the resulting event time clearly. Multi-day/series/session configuration appears only when activated by an in-scope event capability; a birthday or simple meetup should not encounter conference scheduling controls.  
Private or restricted location details can be configured without implying they will be publicly displayed. Virtual join links/codes are treated as protected access information and preview must demonstrate what is public vs participant-only.

STAGE 3 — ACCESS  
Visibility options use human language with consequence summaries: Public — discoverable/shareable according to approved discovery rules; Unlisted — accessible through permitted direct distribution but not normal public discovery; Private/Invite — protected by configured invitation/access rules.  
Visibility is separate from eligibility. An 18+ public event can have public metadata while requiring protected eligibility before participation/protected content. Changing visibility after publication is a material change when it alters who can access the event and routes through the material-change review.  
Invitation controls appear only for configurations that use them. Host can proceed to review without pre-sending invitations; publishing and distribution are separate actions.

STAGE 4 — PARTICIPATION  
Participation mode choices expose only valid models: Open/no registration when permitted; RSVP; Free registration; Paid admission when the stage and merchant/payment requirements allow it.  
Capacity is optional unless required by venue/category/configuration. When enabled, capacity must be a valid positive quantity and the UI explains whether it limits registrations/admissions rather than pretending to model physical safety capacity beyond Sontu’s authority.  
Waitlist appears only when capacity and stage scope support it.  
Paid admission reveals admission-class configuration. Each class defines a human-readable name, quantity/capacity allocation where applicable, price, sales/availability timing where supported and legitimate entitlements. Default/simple paid events can use one General admission without forcing tier design. Additional classes such as VIP, complimentary, family/group, staff/volunteer, vendor/exhibitor or media appear only when the host intentionally activates them and the event context supports them.  
Registration questions, guest/plus-one rules and acknowledgements are optional capabilities. Hosts must see which fields are required from participants and cannot collect arbitrary sensitive data without the legal/privacy rules permitting it.

STAGE 5 — REQUIREMENTS & SPECIALIZED CONFIGURATION  
This stage is generated from actual event configuration, not a generic advanced-settings warehouse. It may include age/eligibility restrictions, required acknowledgements, category-relevant safety/participation information, virtual-access release behavior, or specialized-role configuration.  
Specialized roles such as vendor/exhibitor, speaker/presenter, volunteer, staff/operator and media are activated deliberately. When activated, Sontu may expose role-specific application/approval, assigned space/resources, credentials, setup/teardown, fees/deposits or evidence fields only to the extent they are in scope. Ordinary attendee registration remains separate from specialized-role workflows.  
Trade show/conference complexity should emerge through these activated capabilities and scheduling/role configuration rather than through a separate product architecture.

STAGE 6 — OPERATIONAL SETUP  
Shown when the event uses operational capabilities. Controls may include host operators/team access, check-in activation, re-entry policy where supported, admission lookup/fallback assumptions, communications/reminder settings and event-day readiness options.  
Organization/team permissions are never granted merely by adding a display name. Operator assignment selects authorized identities/roles and previews their permitted operational scope. A simple private event can skip this stage entirely when no operational setup is needed.

STAGE 7 — REVIEW & ATTENDEE PREVIEW  
Review is an actionable readiness surface, not a dump of raw form values. It groups: Event identity; When/Where; Public/protected access representation; Participation/admission; Requirements; Operations; Ownership; unresolved blockers/warnings.  
Blocking issues prevent Publish and link directly to the field/stage that resolves them. Non-blocking recommendations are visually distinct and cannot masquerade as required. Preview renders the attendee-facing representation appropriate to visibility, including what an unauthenticated public visitor can see and what remains protected.  
Host can edit from Review and return without losing the review context.

PUBLISH  
Publish is an intentional consequential action. Before commit, the host sees owner identity, visibility, participation/admission model, date/time and any material warning requiring acknowledgement. Avoid redundant confirmation when Review already makes consequence clear, but never allow an accidental ambiguous publish action.  
Server-side publication revalidates required fields, ownership/permission, event timing, payment/merchant readiness where paid, and configuration consistency. Result is explicit: Published; Failed/not published with recoverable cause; or unresolved only if the underlying operation genuinely cannot yet be determined. The UI cannot show a public/share link as authoritative until publication succeeds.  
Successful publish routes to a result state with View event, Share/Copy link where permitted, Invite where configured, and Manage event. The host then enters the normal Host Event Workspace rather than remaining trapped in the wizard.

PROGRESSIVE DISCLOSURE RULES  
A simple private birthday can be created with owner, basics, time/place, private access, simple RSVP/open participation and review; it should not see merchant onboarding, admission tiers, exhibitors, sessions or operator lanes. A free public community event adds public distribution and capacity/registration only when selected. A paid professional event reveals merchant/payment/admission requirements. A restricted nightlife event reveals eligibility and protected-access requirements. An organization conference/trade show can reveal teams, admission classes, sessions/specialized roles, check-in and operational setup progressively.  
Category may provide defaults and recommended capabilities, but the host can understand what each activated capability does; category never silently creates consequential rules.

CREATION VALIDATION & FAILURE STATES  
Field validation is local where possible; cross-field/configuration validation occurs at stage transition and Review. Validation never erases valid user input. Permission loss while editing preserves the draft safely but blocks unauthorized consequential changes. Network/server save failure communicates whether the latest changes are persisted. Publication failure leaves the event Draft unless authoritative state proves otherwise. Duplicate taps/retries cannot create multiple published events from one Draft.

CREATION RESPONSIVE / ACCESSIBILITY  
Phone uses one clear stage/task at a time with persistent progress and Save/Continue behavior without tiny dense configuration tables. Complex admission classes, specialized roles or schedules may use focused subflows. Wider web can show a stage rail and contextual preview. Labels remain persistent, errors associate with fields, keyboard/focus order follows the form, and progress is not communicated by color alone.

CREATION ACCEPTANCE  
A first-time personal host can create and publish a simple event without encountering irrelevant enterprise controls. An organization operator can identify the owner before publish. A regular Sontu host can progressively activate the approved consumer-app hosting capabilities without switching event models; enterprise/high-complexity operations are reserved for the separate professional organizer surface while sharing the underlying Sontu event system. A host can leave and recover a Draft. Publish cannot succeed with missing blockers or stale permission/payment readiness. Successful publication immediately provides the credible attendee-facing representation and distribution actions.

32 — HOST OPERATIONS IMPLEMENTATION SPECIFICATION

HOSTING LIST & DRAFTS  
Hosting is the operational home for events the user owns or is authorized to operate. Groupings distinguish Draft, Published/Upcoming, In Progress and History/Cancelled. Each item shows event identity, owner context, date/time and lifecycle/attention state. Personal and organization events can coexist without a permanent role switch; ownership is visible on the item and workspace.  
Draft item actions prioritize Resume creation, Preview where meaningful and discard only with appropriate consequence. Published items open Host Event Overview. Empty state offers Create and organization-context guidance only when relevant.

HOST EVENT OVERVIEW  
The overview answers five questions before analytics: What state is the event in? What needs attention? How many people are participating/admitted? Is there an operational or communication problem? What should the host do next?  
Top hierarchy: event identity \+ owner \+ lifecycle state; material alert/attention items; next operational action; participation/capacity/admission summary; event-day readiness when relevant; recent consequential activity. Revenue/engagement vanity metrics cannot displace unresolved payment, capacity, permission, communication or check-in problems.  
State-specific next actions may include Share/Invite after publish, resolve readiness blocker, review participants, send essential update, open check-in, resolve failed communication, complete event, or review results.

EVENT DETAILS & SETTINGS  
Hosts can inspect the same configuration used during creation. Draft edits save normally. Published edits are classified as non-material or potentially material. Potentially material changes route to Material Change Review before commit; the host sees changed fields, participant impact, required notification/reconfirmation/refund implications and resulting public/participant representation.  
Visibility, timing/location, admission availability, eligibility and cancellation-related configuration cannot be silently changed behind participants. Permission-sensitive settings are hidden/disabled or safely denied according to role.

ACCESS & INVITATIONS  
Workspace shows event visibility/access mode, permitted share link, invitation actions/status and audience reuse only when in scope. Host can distinguish event access from participant registration status. Revoking an invite/access relationship does not silently rewrite historical registration/payment truth; resulting participant access consequences follow the domain rules.  
Distribution status should focus on actionable failures and accepted/sent states rather than pretending email/push delivery guarantees attendance.

PARTICIPANTS / ADMISSIONS  
Purpose: operationally inspect and manage people/relationships without collapsing registration, payment, admission credential and attendance into one status.  
Default table/list fields adapt to configuration but can include participant identity, registration/RSVP state, admission class, payment/refund state, credential state, attendance/check-in state and relevant guest/specialized-role cue. Search/filter supports operational lookup without requiring hosts to know internal IDs.  
Participant detail exposes only permitted information and actions. Consequential host actions such as refund, revoke/cancel admission, resend credential/invite or resolve an exception require role permission and explicit result state. A failed action cannot optimistically rewrite the participant row as success.  
For specialized roles, role-specific operational fields may appear in a focused view rather than bloating every attendee row.

COMMUNICATIONS  
Host can compose essential event announcements to a legitimate configured audience. Before send, show event identity, audience scope and message preview. Material-change/cancellation communications generated by consequential workflows remain linked to those workflows rather than requiring the host to remember to send them manually.  
Send result distinguishes accepted/queued from delivered where the provider cannot guarantee delivery synchronously. Delivery failures surface as operational attention with retry/alternate follow-up where supported. Communication history records event, audience, initiator, timestamp and outcome appropriate to audit/privacy rules.  
Sontu should not become a general-purpose social inbox as a prerequisite to event operations. General user-to-user DMs are not part of the approved direction. Each event may instead activate an event-scoped Discussion/Message Board for participant/host conversation and a separate Ask Host assistant channel. The host can enable or disable the assistant. When enabled, it answers bounded questions from authoritative/permitted event information, handles repetitive informational concerns, clearly identifies itself as automated, does not invent policy or make consequential commitments, and escalates to a direct host/contact workflow when confidence is insufficient, the user requests human contact, or the concern requires host judgment. Escalation should pass useful conversation context where permitted without exposing private host contact details by default.

CHECK-IN / EVENT-DAY OPERATIONS  
When activated, Check-in opens into a fast operator surface. Primary modes: scan credential; manual participant/admission lookup; recent results/exception recovery. Each attempt returns one dominant textual and visual result: Valid/admitted, Already used/duplicate, Wrong event, Invalid/cancelled/refunded, or Unable to verify/degraded.  
A valid scan/lookup still requires authoritative admission/check-in rules; QR possession alone is not truth. Multi-operator check-in must tolerate near-simultaneous attempts without both appearing as first admission. Re-entry follows configured policy and is distinguishable from duplicate misuse.  
Manual exception handling requires appropriate permission and audit. Degraded connectivity/power representation must tell the operator whether verification is unavailable versus definitively invalid. If offline admission is later activated, its conflict/reconciliation rules must be explicit before use; the UX cannot invent offline authority.  
For large events, operator UI may support lane/admission-class filters, accessibility/priority handling and temporary physical-credential workflow when those capabilities are activated, without changing the shared check-in model.

MATERIAL CHANGE / POSTPONE / RESCHEDULE  
Review summarizes old→new consequential values, affected participant/admission relationships, required notifications and available participant options. Commit is intentional and produces explicit success/failure. Rescheduling preserves the original event relationship and historical change record rather than creating an unrelated event. Host then sees communication/reconfirmation/refund work still requiring attention.

CANCEL EVENT  
Cancellation is separated from ordinary edit controls. Review shows event identity, consequence to participants/admissions, refund/communication implications and reason when required. Successful cancellation immediately changes event truth and removes stale acquisition/operation actions. Failed/unresolved cancellation cannot display a cancelled event merely because the client submitted the request.

RESULTS / HISTORY / REPEAT  
After completion, workspace prioritizes operationally meaningful outcomes: registrations/admissions, attendance/check-in, refunds/payment outcomes where permitted, communication history and event change history. Completed event configuration and transactional history are immutable except through explicitly authorized correction/amendment mechanisms defined downstream.  
Repeat/Duplicate creates a fresh Draft from reusable configuration only. It never copies participant relationships, payments/orders, credentials, attendance/check-ins, communications, analytics or historical audit records. Follow-up invitations, when activated, create a new event/relationship rather than reopening the completed event.

HOST FAILURE & PERMISSION STATES  
Permission loss during an open workspace causes authoritative re-evaluation before the next sensitive action; stale UI cannot preserve operator authority. Save/action failures state whether the requested change occurred. Unknown outcomes offer recheck rather than blind duplicate retry. Deleted/unavailable/cancelled events route to truthful historical/unavailable states rather than generic 404 when the user is authorized to know the relationship.

HOST RESPONSIVE / ACCESSIBILITY  
Phone prioritizes overview, participant lookup, communications status and check-in actions; dense participant/admission data becomes searchable cards/focused detail rather than an unreadable squeezed table. Wider web can use tables and split panes for operations. Check-in targets are large, result states use text/iconography in addition to color, and critical event-day actions remain keyboard/focus accessible where web is used.

HOST ACCEPTANCE  
A personal host can publish, share, inspect registrations and operate a simple event without organization complexity. A business/organization operator can see ownership and permission context. Where advanced professional capabilities are supported, a trade show/conference operator uses the separate professional organizer surface over the same authoritative event model rather than forcing enterprise complexity into regular Sontu. Material changes and cancellation cannot occur silently. Event-day operators can distinguish valid, duplicate, invalid and unverifiable admissions quickly. Completed events preserve history and repeat hosting creates a clean new Draft.

33 — ORGANIZATION, ACCOUNT & SUPPORT IMPLEMENTATION SPECIFICATION

ORGANIZATION CONTEXT  
Purpose: let a person act for themselves or an organization without turning host/participant into permanent account types. Organization context is visible where ownership, permissions, branding, payment capability or operational authority can change an outcome.

Organization selection is contextual. The Profile drawer provides an explicit Personal / Business or Organization mode/context toggle when the identity has or creates an organization context. This is an acting/presentation context over the same underlying identity, not a separate account. Business/Organization context may expose a somewhat richer management set such as organization profile, members, role assignment, organization-owned events, branding, reporting and advanced operational controls as stage-approved. Basic paid ticketing remains event-capability-driven and is not restricted to organizations; organization context may add team, permission, reporting or settlement controls around it. Create, Events and consequential host actions still show the acting owner/operator directly. Switching context never silently transfers an event, participant relationship, order or credential.

An organization-owned event displays organization identity and the signed-in operator’s permitted role/scope where useful. If permission is removed or changed, the next protected read/action revalidates authority. Stale open screens cannot preserve access. A denied user receives a safe explanation and route back to personal/other permitted context without leaking organization-only information.

ORGANIZATION TEAM  
Stage-approved team management supports viewing members and role/scope, inviting or adding members where permitted, changing approved roles and removing access. The UI must distinguish organization membership from event-specific operational assignment. Removing a member does not delete historical audit attribution or transfer ownership to that person.

Before a consequential role/removal change, show affected scope when it is material. Result states are explicit: updated, failed/not changed, or unresolved when genuinely unknown. A user cannot grant a role they do not have authority to grant. The final Functions & Features/domain workstream owns exact role taxonomy and permission matrix; UX must consume it rather than invent parallel permissions.

ACCOUNT  
Account is the user-level home for identity/profile, organization memberships, notification preferences, accessibility/language settings where supported, session/security controls, support entry and legal/account actions. Hosting configuration does not belong here merely because the same person is a host.

Account actions that affect authentication, active sessions, deletion/privacy requests or other consequential state require proportionate consequence messaging and explicit result. Signing out returns public-capable routes to a safe public state where possible; protected routes require authentication and preserve only safe intended-route context.

SUPPORT / REPORT  
Support/report entry is contextual from relevant event, participant/admission or account surfaces and also reachable from Account. It carries permitted context such as event identity and problem category so the user does not need to reconstruct the issue manually, while avoiding unnecessary sensitive data.

Reporting an event/user/content is not represented as immediate adjudication. Submission states distinguish received/failed and explain expected next step at appropriate depth. Safety-critical or emergency wording must not imply Sontu provides emergency response unless that operating capability is explicitly approved.

INTERNAL ADMIN / SUPPORT  
Privileged tooling is a separate authenticated surface or mode with clear privileged context. It may expose stage-approved inspection/intervention functions, but ordinary users never see admin navigation simply because the same product has support tooling. Privileged actions require authorization, auditability, event/user context and explicit result state. Impersonation or silent mutation is not assumed; any such capability requires separate downstream approval.

ORGANIZATION / ACCOUNT RESPONSIVE & ACCESSIBILITY  
Phone favors clear context labels, member cards/focused detail and bounded settings groups rather than dense permission matrices. Wider web may use tables for team administration. Role/status meaning uses text, not color alone. Permission errors identify the affected action without exposing protected information. Keyboard/focus behavior and accessible labels apply to membership, settings and support forms.

ORGANIZATION / ACCOUNT ACCEPTANCE  
A user who belongs to multiple organizations can tell which identity owns an event before publishing or changing it; a personal event remains clearly personal; permission loss cannot be bypassed through stale UI; team membership is distinguishable from event operator assignment; ordinary account settings do not become a host-control warehouse; support can be entered with useful context without exposing privileged admin tooling.

34 — CROSS-CUTTING OVERLAY & TRANSITION IMPLEMENTATION SPECIFICATION

PRIVATE / INVITE  
Private access is resolved before protected content. Invite links/tokens are treated as access inputs, not proof that the current person is authorized. States include valid/authorized, authentication required, wrong account where policy can safely say so, expired, revoked, invalid and unavailable. Back/cancel returns to a safe pre-protected state. Protected location, participant data and virtual credentials never flash during loading or denial.

RESTRICTED / ELIGIBILITY  
Eligibility transition separates public metadata, identity/authentication and eligibility decision. States include not started, verification required, pending where supported, verified/eligible, failed/retryable, ineligible and verification unavailable. The interface explains what is required and why at useful depth without repeatedly displaying sensitive evidence. Eligibility expiry or changed requirements revalidate before protected commitment/access.

PAID / PAYMENT  
Checkout is a focused consequential flow rather than a generic modal stacked over unrelated event state. Price/admission choice and material fees/terms remain reviewable before payment. Leaving before commitment creates no successful order/admission claim. Processing prevents ambiguous duplicate submission. Unknown/pending outcome routes to an order-resolution state with recheck/support, never to a valid credential. Successful payment returns to participant/admission detail.

VIRTUAL / HYBRID  
Protected join information is available only to authorized participants and only according to release policy. States include not yet released, available, changed, revoked and temporarily unavailable. A material access change supersedes cached join information. Hybrid events keep physical and virtual instructions distinguishable while presenting one event relationship.

CAPACITY / WAITLIST / CONCURRENCY  
Capacity is revalidated at commitment. Full state removes ordinary commit actions. Waitlist appears only when configured and clearly establishes a waitlist relationship rather than registration/admission. If capacity is lost between selection and commit, the user receives a truthful concurrency result with permitted alternatives; Sontu does not silently change admission class, quantity or event.

MATERIAL CHANGE / RESCHEDULE  
The transition shows old→new consequential values, affected relationship implications and required notification/reconfirmation/refund choices before commit. Existing participants encounter a prominent changed-event state on return. Reconfirmation, when required, is a distinct participant action with explicit result; lack of reconfirmation is not silently treated as acceptance unless policy explicitly says so.

CANCELLATION  
Cancellation review is intentionally separate from routine edit/save. Successful cancellation immediately becomes authoritative across public, participant and host surfaces; stale registration/purchase/check-in CTAs disappear. Refund and communication work may remain pending and must be represented separately from cancellation itself. Failed or unresolved cancellation preserves truthful prior/unknown state.

FAILURE / UNKNOWN OUTCOME  
Every consequential overlay distinguishes validation failure, permission/eligibility denial, recoverable transport/server failure and unknown operation outcome where possible. Retry is offered only when safe. Unknown outcomes use recheck/reconciliation rather than duplicate submission. User-facing language answers whether the action occurred whenever the system knows; technical diagnostics remain in telemetry/support.

OVERLAY / TRANSITION ACCEPTANCE  
Authentication, eligibility, payment and consequential-action interruptions return users to the correct legitimate continuation point; protected data never leaks through loading/denial; capacity and permission are revalidated before commitment; cancelled/materially changed truth replaces stale actions; unresolved payment/publication/cancellation states cannot masquerade as success; back/cancel never creates unintended domain state.

35 — REUSABLE INTERACTION, RESPONSIVE & VISUAL-HIERARCHY RULES

ACTION HIERARCHY  
Each screen has at most one dominant primary action for the user’s immediate task. Secondary actions remain available without competing visually. Destructive/consequential actions are separated from routine navigation and save actions. Labels describe the outcome (Publish event, Cancel event, Refund admission) rather than generic Confirm/Submit where consequence matters.

FORMS & VALIDATION  
Persistent labels are preferred over placeholder-only fields. Required/optional status is understandable before submission. Field errors appear adjacent to the field and summary/navigation to the failing stage is provided when errors span stages. Valid input survives validation failure. Conditional fields are inserted in predictable context and removed values are not silently destroyed when toggling a capability unless the user is warned or the data is safely retained for reversal.

SAVE / ASYNC FEEDBACK  
Use explicit Saved/Saving/Save failed for persistent editable work where autosave exists. Short actions may use local progress indicators, but indefinite global spinners are not outcomes. Optimistic UI is prohibited for permission, payment, publication, admission validity, check-in, cancellation and other authoritative consequential state unless domain behavior explicitly makes it safe.

STATUS  
Status treatments combine concise text with iconography/structure where useful; color is supplementary. Domain truth is translated into human-readable language without merging distinct states. Attention styling is reserved for actionable or materially changed conditions rather than decorating normal states.

LISTS, CARDS & TABLES  
Participant/discovery surfaces default to scannable cards/lists. Dense host operations may use tables on wider screens when comparison across rows matters. Phone converts dense tables into searchable/filterable lists with focused detail; it must not squeeze desktop tables below usable target/readability thresholds.

DIALOGS / SHEETS / FULL FLOWS  
Use dialogs/sheets for bounded confirmation or small contextual actions. Multi-step payment, creation, eligibility and complex configuration use dedicated routes/subflows so state, recovery and accessibility are reliable. Nested modal chains are prohibited for core journeys.

NAVIGATION / BACK  
Global navigation roots remain stable. Contextual event workspaces may have local navigation. Back returns to the previous meaningful context and preserves safe filters/form progress. Cancel exits the current action without implying domain rollback if an earlier authoritative step already succeeded; when partial success exists, the resulting state is explained before exit.

RESPONSIVE BREAKPOINT BEHAVIOR  
Exact CSS breakpoints are implementation details, but Gate 2 must support three behavioral classes: compact phone; intermediate/tablet/narrow web; wide web. Compact layouts use one primary content column, reachable primary actions and focused subflows. Intermediate layouts may introduce secondary panes selectively. Wide host operations may use persistent local navigation, tables and split detail. Public event hierarchy remains event-first at every width.

ACCESSIBILITY BASELINE  
Interactive controls have accessible names and adequate target size. Keyboard/focus order follows visual/task order on web. Opening a dialog/subflow moves focus appropriately and closing returns it to the invoking control when possible. Validation errors are programmatically associated with fields. Dynamic consequential results are announced appropriately. Reduced-motion preference is respected for nonessential animation. No status, eligibility, validity or check-in decision relies on color alone.

VISUAL HIERARCHY  
Event identity/truth and current task outrank platform decoration. Typography/spacing distinguish page title, event identity, section heading, body/supporting text and metadata consistently. Critical material-change/cancellation/payment/check-in states can interrupt normal hierarchy; promotional/gamification elements cannot. Brand expression must fit these hierarchy roles rather than invent per-screen interaction conventions.

GAMIFICATION PLACEMENT  
Confirmed gamification may appear in discovery, hosting progress, participation and post-event continuation only where it reinforces legitimate progress. Points, achievements, rewards or celebratory treatment cannot obscure payment/admission/event truth, pressure unsafe participation, reward bypassing restrictions, or displace an unresolved operational problem. Exact mechanics remain owned by Functions & Features.

25 — PRESENTATION & PERSONALIZATION ARCHITECTURE

25.1 Core rule  
Sontu uses one stable product shell and one canonical design system. Personalization must not create separate applications, duplicate capability trees, or unpredictable navigation. Presentation adaptation changes emphasis, ranking, density, and default views while preserving product semantics and user orientation.

25.2 Initial behavioral tendencies  
V1 design should support four non-exclusive consumer tendencies rather than permanent user types:  
• Explorer — primarily asks “What could I do?” Emphasize photography, recommendations, categories, collections, and experience-led discovery.  
• Nearby / Spontaneous — primarily asks “What is happening around me now?” Emphasize time, distance, nearby discovery, map access, tonight/weekend context, and rapid decision information.  
• Connector — primarily asks “What is happening around events and communities I care about?” Emphasize event-centered activity, updates, permitted social context, and Feed relevance without becoming a general personal social network.  
• Planner / Participant — primarily asks “What am I doing next and what do I need?” Emphasize upcoming commitments, credentials, preparation, schedule, requirements, material updates, and event-day readiness.

These are weighted preferences, not mutually exclusive identity labels. One person may express several tendencies and may behave differently by situation or over time.

25.3 Host boundary  
Host is not a fifth consumer presentation type. Hosting is a contextual operational job. Authorized host information and controls rise when relevant and resolve into the event’s host workspace. Professional/complex organizer UX remains subject to the existing professional-host boundary.

• Global navigation jobs and route semantics.  
• Sontu typography family and component language.  
• Core spacing and layout grid.  
• Iconography conventions.  
• Event identity and Event Hub semantics.  
• Permissions, trust, safety, payment, credential and consequential-action behavior.  
• Accessibility requirements.  
• Semantic status colors and meanings.  
• Core interaction patterns.

Presentation may adapt:  
• Home module priority and ordering.  
• Discover default presentation.  
• Map prominence.  
• Photography prominence and supported card density.  
• Event-centered social/activity prominence.  
• Ranking and emphasis of relevant modules.

Adaptation should generally compose the same reusable modules rather than fork screens or maintain separate component trees.

25.5 Surface matrix  
Home:  
• Explorer: inspiration/recommendations rise after immediate obligations.  
• Nearby: nearby/tonight and location-aware opportunities rise.  
• Connector: relevant event activity and updates rise.  
• Planner: next event, preparation, credentials and time-sensitive actions rise.

Discover:  
• Explorer: visual/editorial browsing is prominent.  
• Nearby: map/location/time-oriented discovery is prominent.  
• Connector: community/event-context discovery may rise where evidence and permissions support it.  
• Planner: search, date, category and deliberate filtering are prominent.

Events:  
Events remains the canonical relationship hub for all tendencies. Planner users may receive greater preparation emphasis; Nearby may emphasize imminent events; Connector may receive more event-activity context. Relationship truth and chronological understandability do not change.

Feed:  
Feed remains event-centered. Connector may receive the strongest Feed emphasis; Explorer may see inspiration and event-originated content; Nearby may receive locally relevant event activity; Planner may treat Feed as secondary. Personalization must not convert Feed into a general personal social timeline.

Event Hub:  
The Event Hub keeps one conceptual hierarchy and identity. Explorer may receive stronger experiential imagery; Nearby may receive stronger time/location/navigation prominence; Connector may receive stronger activated activity/discussion context; Planner may receive stronger credentials/schedule/requirements prominence. Consequential and time-critical information overrides presentation preference.

25.6 Priority hierarchy  
When signals conflict, use this order:  
1\. Safety, access, trust and operational urgency.  
2\. Current event context and time-sensitive requirements.  
3\. Explicit user preferences.  
4\. Inferred preferences, only when supported by sufficient evidence.  
5\. Generic Sontu default.

Personalization must never hide or materially demote cancellation, access restrictions, payment uncertainty, ticket/credential readiness, material event changes, check-in requirements, safety information or other consequential state.

25.7 Onboarding  
Do not ask users to choose an abstract visual persona or permanent mode. Short onboarding questions may instead establish intent, such as discovery interest, spontaneity/planning preference, nearby relevance, event activity interest and hosting intent. “Not sure” / mixed use must remain valid. Initial preferences should be editable later.

25.8 Cosmetic personalization  
Cosmetic personalization is independent of behavioral presentation. Architecture should support System / Light / Dark appearance and a limited set of curated Sontu accent palettes. Curated palettes should be token-based and accessibility-tested. Arbitrary user-selected RGB colors are not required for V1. Semantic colors for success, warning, error, destructive actions, access states and other meaning-bearing UI remain governed by the design system and must not be remapped merely to match a theme.

25.9 V1 implementation boundary  
Architect for extensibility but keep initial adaptation deliberately constrained. V1 may adapt a small number of presentation variables, initially:  
1\. Home module priority.  
2\. Discover default presentation.  
3\. Map prominence.  
4\. Event-centered social/activity prominence.  
5\. Photography/content density within approved component variants.

Do not build four separate Homes, four Discovers or four Event Hubs. Implement reusable modules/components plus a presentation-configuration layer. Additional behavioral dimensions may be introduced later only when research or product evidence demonstrates a meaningful user job that is not adequately represented by existing dimensions.

25.10 Contextual adaptation  
Preference does not outrank immediate usefulness. Example: an Explorer whose registered event begins shortly should see ticket/credential, directions, timing and material updates before general inspiration. A person actively operating a hosted event should receive relevant host attention regardless of their normal consumer tendency. Contextual adaptation must remain understandable rather than causing arbitrary spatial rearrangement.

25.11 Design direction  
The canonical Sontu visual system should combine:  
• Editorial / world-first foundation — immersive real-world imagery, restrained product chrome, strong legibility and generous hierarchy.  
• Convergence identity — subtle brand language derived from separate paths, shared centres, gathering, place, motion and continuity.  
• Operational precision — information density increases when the user is preparing for, attending or operating an event.

Consumer Sontu should feel immersive and alive without becoming visually noisy. Host/operational Sontu should feel calm and precise while remaining recognizably part of the same product.

25.12 Design-validation requirement  
Before broad implementation, representative canonical screens should validate the single Sontu design system and its adaptive behavior. At minimum validate Home, Discover and Event Hub across materially different presentation tendencies, plus Events, Feed, event creation, host overview, credential/ticket, onboarding/preferences, and critical empty/error/degraded states. Visual comparison must use realistic device proportions and should not rely on distorted generated-device mockups as layout evidence.

25.13 Open design decisions  
The following remain prototype/human-QA decisions rather than locked implementation constants:  
• Exact Sontu default accent palette and optional curated palettes.  
• Exact type family and scale.  
• Exact card radius, elevation and image ratios.  
• Exact motion timing and convergence transitions.  
• Exact onboarding question wording and number of questions.  
• Whether presentation preferences are exposed as individual controls, a higher-level preference control, or both.  
• Exact thresholds for any future inferred adaptation.

The controlling requirement is stable orientation with useful personalization: one Sontu, multiple ways of emphasizing what matters.

26 — CANONICAL VISUAL SYSTEM — CANDIDATE A  
Status: Design candidate for prototype validation; not yet final visual constants — September 12, 2026

26.1 Character  
Sontu should feel like a window into worthwhile real-world experiences rather than an event database. The visual character combines editorial clarity, immersive real-world imagery, restrained digital chrome, subtle convergence geometry, and increasing operational precision as a user approaches or operates an event.

26.2 Surface architecture  
Light appearance: warm-neutral rather than clinical pure-white presentation. Use a quiet page canvas, near-white elevated surfaces, dark neutral text, subtle borders and limited shadows. Photography supplies most high-chroma color.  
Dark appearance: near-black/charcoal canvas with slightly lifted neutral surfaces rather than absolute black cards floating on black. Preserve photographic richness and text contrast without neon treatment.

The exact neutral values remain prototype-tested. The design system must use semantic surface tokens rather than hard-coded page colors.

26.3 Accent/theme architecture  
Sontu requires one canonical default accent plus a small curated palette set. Accent colors may affect brand emphasis, selected navigation, non-semantic controls, progress, decorative convergence elements and other approved expressive states. They must not remap semantic success/warning/error/access meanings.

Candidate theme families for visual testing:  
• Sontu Default — a distinctive energetic but mature accent; avoid generic corporate blue as the only brand signal.  
• Horizon — cooler, calm world/travel expression.  
• Ember — warmer, social/experience expression.  
• Grove — natural/outdoor expression.  
• Violet — cultural/nightlife expression.

Names and exact values are provisional. Theme support must use semantic tokens so palettes can be added or retired without component rewrites.

26.4 Typography  
Use one highly legible modern sans-serif family for the product UI, with sufficient weight range for editorial hierarchy. Do not rely on a decorative display face for normal navigation or operational content. The system should create character through scale, weight, spacing, imagery and composition before adding a secondary typeface.

Working hierarchy:  
• Display / event hero — large, confident, compact line length.  
• Page title — strong but subordinate to immersive event identity.  
• Section heading — clear scanning anchor.  
• Body — comfortable reading at mobile scale.  
• Label / metadata — compact but never tiny.  
• Operational/status text — optimized for fast comprehension rather than visual novelty.

Exact family, sizes and line heights remain prototype-tested. Support dynamic type/accessibility scaling assumptions.

26.5 Spacing and grid  
Use a consistent 4-point-compatible spacing system with an 8-point primary rhythm. Mobile page gutters should feel generous enough for editorial quality while preserving information density when needed. Components should derive spacing from tokens rather than arbitrary local values.

Design density has three supported expressions within one system:  
• Immersive — larger imagery and breathing room for discovery.  
• Standard — default balanced product density.  
• Operational — tighter but still readable density for tickets, schedules, host controls and event-day tasks.

Density is contextual/presentation-driven, not a separate visual theme.

26.6 Imagery  
Real experience imagery is a primary Sontu interface material, not decoration.

Rules:  
• Prefer authentic place/activity/experience imagery that helps a person understand what participation may feel like.  
• Event imagery should establish experience and place before generic branding artwork when good event imagery exists.  
• Avoid stock-photo visual language where possible.  
• Preserve meaningful focal points with controlled crops.  
• Use consistent approved aspect-ratio families rather than arbitrary image dimensions.  
• Do not place critical text over uncontrolled bright/busy imagery without a readability treatment.  
• Cards without imagery must remain intentionally designed rather than looking broken or unfinished.

Candidate ratios to validate include a landscape discovery ratio, a taller immersive/editorial ratio, square media/activity ratio, and wide Event Hub hero treatment. Exact ratios remain prototype-tested.

26.7 Geometry  
Cards should feel contemporary and tactile without becoming toy-like. Use moderate rounded corners consistently; avoid excessive pill shapes for containers. Pills/chips are reserved for compact filters, states and appropriate controls.

Use borders, tonal surface separation and whitespace before heavy shadows. Elevation should communicate hierarchy or interaction, not decorate every card.

26.8 Navigation  
Phone shell remains:  
• Top-left profile/avatar.  
• Top-right Search and Notifications.  
• Bottom roots: Home, Discover, Events, Feed.

Bottom navigation should be visually quiet and persistent, with strong selected-state legibility. It should not compete with event photography. Labels remain visible unless prototype evidence strongly supports another accessible treatment.

Contextual destinations such as Event Hub and Host Workspace sit beneath the global shell. Event-day or focused flows may simplify chrome when appropriate while preserving safe return/context.

26.9 Icons  
Use one coherent outlined/variable icon family with simple recognizable geometry. Avoid mixing unrelated icon styles. Filled/stronger variants may communicate selected state where accessible. Custom Sontu/convergence iconography should be limited to brand-specific concepts rather than replacing universally understood symbols such as search, notifications, map or ticket.

26.10 Convergence visual language  
Sontu’s philosophical signature should appear subtly through composition and motion rather than repeated literal logos.

Candidate motifs:  
• Independent paths or lines approaching a shared centre.  
• Multiple elements aligning around one event/place/time.  
• Layered arcs/horizons suggesting world/place and continuation.  
• Groups of independent points retaining separation while forming a temporary pattern.  
• Event transitions in which source imagery/content expands into a shared Event Hub destination.

Avoid generic community-circle diagrams, literal people silhouettes, confetti, location-pin branding and decorative geometry that does not communicate product meaning.

26.11 Motion  
Motion should explain continuity and convergence, not create spectacle.

Working rules:  
• Event card → Event Hub should preserve visual continuity where platform capabilities permit.  
• Module reordering/adaptation should use subtle transitions so users understand movement rather than perceive arbitrary rearrangement.  
• Contextual operational information may rise/expand as an event approaches.  
• Success feedback may use restrained completion motion.  
• Motion is nonessential, reducible, and never delays urgent interaction.  
• Avoid autoplay decorative animation across normal browsing surfaces.

Exact duration/easing values remain prototype-tested.

26.12 Core component families  
The first design-system prototype must establish reusable variants for:  
• Event cards: immersive, standard, compact/operational.  
• Event hero.  
• Section/module container.  
• Primary/secondary/tertiary/destructive actions.  
• Filter chips and segmented controls.  
• Search field.  
• Navigation bar and top utilities.  
• Event relationship/status label.  
• Host/trust identity treatment.  
• Ticket/credential surface.  
• Schedule/list row.  
• Activity/feed post tied visibly to an event.  
• Map event marker/card relationship.  
• Empty/error/degraded-state panel.  
• Form fields and guided-creation step structure.

Variants must share tokens and semantics rather than become separate components for each behavioral tendency.

26.13 Representative-screen validation set  
Before Candidate A becomes locked visual authority, test it against realistic phone proportions and realistic content on:  
1\. Home — Explorer emphasis.  
2\. Home — Planner/event-soon emphasis.  
3\. Discover — editorial/list emphasis.  
4\. Discover — Nearby/map emphasis.  
5\. Events — mixed relationship states.  
6\. Feed — Connector emphasis.  
7\. Event Hub — immersive pre-commit state.  
8\. Event Hub — registered/event-soon state.  
9\. Ticket/credential.  
10\. Event creation — simple event.  
11\. Host event overview.  
12\. Onboarding/preferences/theme selection.  
13\. Critical empty/error/degraded state.

The design passes only if it remains recognizably one Sontu system across immersive and operational extremes.

26.14 Anti-patterns  
Do not:  
• Clone Airbnb, Eventbrite, Meetup, Partiful or a generic social feed.  
• Use excessive gradients, glassmorphism or neon simply to signal modernity.  
• Turn every surface into large image cards.  
• Hide essential labels behind icon-only novelty.  
• Use theme colors for semantic status meaning.  
• Let personalization move global navigation roots.  
• Let editorial aesthetics reduce event-day clarity.  
• Let operational density make consumer discovery feel like enterprise software.

26.15 Candidate-A validation decision  
Candidate A is the working visual foundation: editorial/world-first \+ convergence signature \+ operational precision. Exact palette, type family, numeric scale, radii, image ratios and motion timings remain intentionally unlocked until representative-screen prototype comparison and human review.

27.1 Token architecture  
All UI styling must resolve through semantic tokens. Components must not hard-code brand hex values, light/dark surfaces, spacing, radii, typography sizes or state colors locally. Theme and appearance changes remap semantic tokens while component semantics remain stable.

27.2 Brand color anchors — Classic Ocean  
Working production anchors from the approved Classic Ocean direction:  
• ocean-300: \#38BDF8  
• ocean-500: \#0EA5E9  
• ocean-650: \#2563EB  
• navy-900: \#0F2D5B

These are brand-expression anchors, not automatic text/background combinations. Final contrast pairs must pass accessibility validation before lock.

27.3 Semantic color roles  
Brand/interactive:  
• accent-primary — primary Sontu interactive/brand emphasis.  
• accent-primary-hover/pressed — interaction states derived from approved palette while maintaining contrast.  
• accent-subtle — low-emphasis selected/background treatment.  
• focus-ring — highly visible keyboard/accessibility focus treatment.

Light appearance candidate roles:  
• canvas — warm near-white page background.  
• surface-1 — primary card/sheet surface.  
• surface-2 — secondary/raised/quiet grouped surface.  
• surface-inverse — dark high-contrast surface.  
• text-primary — near-black/navy-neutral.  
• text-secondary — medium neutral.  
• text-tertiary — lower-emphasis neutral that still passes intended contrast.  
• border-subtle — low-contrast separation.  
• border-strong — explicit control/container boundary.

Dark appearance candidate roles:  
• canvas — near-black/blue-black rather than pure black.  
• surface-1 — lifted charcoal/navy-neutral.  
• surface-2 — secondary lifted surface.  
• surface-inverse — light surface when required.  
• text-primary — near-white.  
• text-secondary — light neutral.  
• text-tertiary — reduced-emphasis neutral.  
• border-subtle / border-strong — appearance-specific neutral boundaries.

Semantic state roles are theme-independent in meaning:  
• success  
• warning  
• error  
• destructive  
• info  
• pending/unknown  
• disabled

Exact neutral and semantic-state hex values remain to be contrast-tested and locked after screen validation.

27.4 Typography candidate  
Primary UI family candidate: Sora, subject to actual device/readability testing and licensing/technical availability. System fallback must be defined for every platform. If Sora reduces dense operational readability, use a more neutral UI family while retaining Sora or a refined custom treatment for the Sontu wordmark/brand display only.

Candidate mobile scale:

• title-2: 22 / 28, weight 600–700

• caption: 12 / 16, weight 500

Do not use body text below 14 px as normal information UI. 12 px is reserved for secondary metadata/captions with sufficient contrast and is not appropriate for essential instructions or actions. Support platform text scaling/dynamic type rather than assuming fixed pixels.

27.5 Spacing  
Base unit: 4\.  
Primary rhythm: 8\.  
Candidate spacing tokens:  
• space-1 \= 4  
• space-2 \= 8  
• space-3 \= 12  
• space-4 \= 16

• space-12 \= 48

Default phone content gutter candidate: 16 px; immersive sections may intentionally reach screen edges when imagery warrants it. Dense operational content must not reduce safe touch separation merely to fit more information.

27.6 Radius  
Candidate radius tokens:  
• radius-xs \= 6  
• radius-sm \= 8  
• radius-md \= 12  
• radius-lg \= 16  
• radius-xl \= 24  
• radius-pill \= 999

Rules:

• Chips/filter pills: radius-pill.

27.7 Borders and elevation  
Prefer 1 px semantic borders, tonal surface separation and whitespace over persistent shadows. Elevation tokens should be limited to cases such as floating controls, menus, sheets, map cards and temporary overlays. Standard event cards should not all cast visible shadows.

27.8 Touch targets and controls  
Interactive targets must meet platform accessibility guidance; use 44×44 CSS-point-equivalent as the minimum candidate target envelope for primary mobile interaction unless platform-native controls provide an equivalent accessible hit area.

Candidate control heights:  
• primary/secondary button: 48–52  
• compact button: 40 visual height with \>=44 accessible hit target  
• text input/search: 48–52  
• bottom navigation: platform-safe-area-aware, with each root receiving a full-width accessible target zone

27.9 Buttons  
Primary: solid accent-primary with accessible foreground.  
Secondary: surface/background treatment with explicit border or tonal separation.  
Tertiary: text/icon action without container where hierarchy permits.  
Destructive: semantic destructive treatment; never theme-accent colored.

Buttons use action-specific labels. Avoid vague “Continue” when the next consequential action can be named clearly. Loading/pending states must preserve action context and prevent unsafe duplicate submissions.

27.10 Bottom navigation  
Roots remain Home, Discover, Events, Feed. Do not add a redundant page title/header solely to repeat the selected bottom-navigation destination. Root pages should use their upper area for useful context, utilities or content rather than “Home,” “Discover,” or “Feed” headings when navigation already communicates location.

Selected root uses accent/strong icon treatment plus readable label. Unselected roots use neutral icon/label treatment. Navigation must remain recognizable under every curated accent theme.

27.11 Top chrome  
Default root shell:  
• left: profile/avatar entry when context permits.  
• right: Search and Notifications utilities according to approved architecture.  
• Sontu brand presence may appear contextually but should not create a redundant tall header.

Contextual destinations may replace root chrome with back, share, save, overflow or event-specific controls. Event Hub immersive hero may place safe overlay controls over imagery when contrast and touch targets are maintained.

27.12 Cards  
Event card variants:  
• immersive — imagery-forward; used selectively in discovery/inspiration.  
• standard — balanced image \+ event truth.  
• compact — dense relationship/operational presentation.

All variants must expose the minimum information required for the user’s current decision. Avoid repeated metadata that does not improve the decision. Relationship/status labels must remain semantically clear.

Candidate image ratios for validation:  
• immersive portrait/editorial: 4:5  
• standard landscape: 16:10  
• compact thumbnail: 1:1 or 4:3 depending information density  
• Event Hub hero: full-width responsive treatment, crop controlled by focal point

Ratios are candidates until real screen testing.

27.13 Imagery edge treatment  
When a hero or immersive image is full-bleed against the device viewport, its outer screen-edge corners follow the viewport/device boundary rather than adding nested rounded corners. Internal cards retain their tokenized radii. This explicitly incorporates founder review from the first Sontu UI validation pass.

27.14 Iconography  
Use one coherent outline/variable icon family. Candidate visual size: 20–24 px for common navigation/action icons inside \>=44 px target envelopes. Selected navigation may use a filled/strong variant. Do not create custom icons for universal concepts without a compelling semantic reason.

27.15 Forms  
Labels remain visible and persistent; placeholder text is supplementary and must not serve as the only label. Required/optional status should be concise and consistently positioned. Errors associate directly with the affected field and include corrective guidance where possible. Group creation steps according to the approved guided event-creation architecture rather than presenting one giant form.

27.16 Density tokens  
• density-immersive — larger media, increased vertical spacing, reduced simultaneous metadata.  
• density-standard — default balanced composition.  
• density-operational — tighter vertical rhythm and more visible information, while preserving body readability and touch targets.

Presentation preferences/context select approved variants; they do not arbitrarily scale every component.

27.17 Motion candidates  
• micro feedback: approximately 120–180 ms  
• ordinary state transition: approximately 180–260 ms  
• shared/contextual transition: approximately 240–360 ms where continuity adds understanding

Use platform conventions when they are better than custom timing. Motion must be reducible and nonessential. Do not delay operational feedback to complete decorative animation.

27.18 Responsive breakpoints — conceptual  
Design mobile-first but do not encode phone assumptions into domain components.  
Candidate layout families:  
• compact: phone/small window  
• medium: tablet/large foldable/small desktop window  
• wide: desktop/web

Exact pixel breakpoints depend on implementation framework and content behavior. Responsive adaptation should be driven by available space and component requirements rather than device-name detection.

Compact: bottom navigation, single-column primary flow, contextual full-screen destinations.  
Medium: increased gutters; selected two-column opportunities; navigation may remain bottom or adapt according to platform conventions.  
Wide: side/top navigation may replace phone chrome; Event Hub and host workspace may use multi-column layouts; maximum readable content widths prevent uncontrolled stretching.

27.19 Accessibility gate  
Before visual token lock:  
• Validate WCAG-relevant text/control contrast for every appearance and curated theme.  
• Validate focus visibility on web.  
• Validate touch targets.  
• Validate text scaling and truncation behavior.  
• Validate that semantic meaning is not color-only.  
• Validate reduced motion.  
• Validate light/dark imagery overlays.  
• Validate map markers and selected states with non-color cues.

27.20 Candidate lock boundary  
The following may be implemented only after representative-screen review confirms them: exact typography family/weights, neutral palette values, semantic-state values, card radii, image ratios and motion timings.

The following are already architectural requirements: semantic tokenization, Classic Ocean brand anchors, 4/8 spacing discipline, stable four-root navigation, no redundant root-page headers, full-bleed edge behavior, reusable density/card variants, theme-independent semantic colors, accessibility gating and responsive layout families.

28.1 Supersession rule  
For the active Sontu design workstream, this section plus sections 25–27 supersede earlier September 6–7 exploratory/refoundation language where that language states or implies that: (a) no fixed consumer navigation may be selected, (b) Home / Discover / Events / Feed is necessarily superseded, (c) a Feed root is not required solely because general social-network behavior is prohibited, or (d) participant-facing product surfaces must remain only bounded/accountless host-first utilities. 28.2 Canonical consumer phone shell  
Current founder-approved consumer phone roots are:  
• Home — personalized relevance and immediate usefulness: what matters to me now?  
• Discover — deliberate exploration: what else could I do?  
• Events — event relationships and contextual management: what am I doing/planning/hosting?  
• Feed — event-centered content and attention: what is happening around the event world I care about?

Top utilities remain Profile/avatar at left and Search \+ Notifications at right where the root shell applies. Hosting remains contextual rather than becoming a fifth global root. Create Event belongs within Events/contextual hosting entry rather than occupying a permanent global navigation slot.

28.3 Event Feed definition  
Feed is canonical as an EVENT FEED. It is not a general social/personal feed.

Every Feed item must have meaningful event ecosystem context. Eligible origins/content include, subject to permissions and stage-approved capabilities:  
• Event-originated announcements, updates and material/non-material communications appropriate for Feed visibility.  
• Host, organizer or venue content tied to a specific event or legitimate event program/series context.  
• Pre-event hype, teasers, performer/speaker/activity reveals, preparation content and promotional storytelling tied to events.  
• Permitted during-event activity, updates, media and highlights when digital participation improves the real-world experience.  
• Event-scoped attendee contributions/media where the event configuration permits them.  
• Post-event highlights, recaps, media, thank-yous, outcomes and useful follow-up tied to the completed event or a legitimate continuation/repeat event.  
• Clearly disclosed promoted/sponsored EVENT content in a future stage only after ranking, trust, disclosure and commercial rules authorize it.

28.4 Explicit exclusions  
Feed does NOT authorize:  
• General-purpose personal status posting.  
• A personal-profile timeline detached from events.  
• Influencer/follower content whose relevance exists only because a person has followers rather than because of event context.  
• Random selfies/lifestyle posts without legitimate event context.  
• A platform objective of maximizing scroll time, streaks, posting frequency or engagement detached from real event outcomes.  
• General user-to-user social networking or DMs merely because Feed exists.

Sontu's social object remains the event. People, hosts, organizers, venues and communities may be visible actors around events, but Feed must preserve event context strongly enough that removing the event relationship would normally make the post inappropriate for Sontu Feed.

28.5 Lifecycle role  
Feed supports the event lifecycle rather than competing with Event Hub:  
• Before — anticipation, discovery context, hype, promotion, preparation and meaningful updates.  
• During — justified live updates/activity/media where useful; the product should still recede when no digital action or information need exists.  
• After — highlights, recaps, media, thanks and legitimate follow-up/continuation.

Material changes, cancellation, credential/access requirements, payment uncertainty, safety and other consequential truth must not rely on Feed visibility. Those states remain authoritative in Event Hub/Events/Home/Notifications or other appropriate consequential surfaces. Feed may echo them where useful but never becomes the sole source of consequential truth.

28.6 Feed versus Discover versus Event Hub  
Discover helps a person deliberately find events. Feed exposes event-world activity/content over time. Event Hub is the authoritative event-centered destination. A Feed item that causes the user to inspect or act on an event resolves into the same Event Hub rather than creating a competing post-centric event identity.

28.7 Personalization  
Connector tendency may receive the strongest Feed prominence and event-activity ranking. Explorer may receive more event-originated inspiration/promotion. Nearby may receive locally relevant event activity. Planner may receive less Feed emphasis. These differences affect ranking/emphasis, not the event-only content rule or global root semantics.

28.8 Feed visual requirement  
Canonical Feed design should make event context immediately legible. A post should visibly identify the relevant event/program and appropriate origin (event, host, organizer or venue) without resembling an ordinary personal social post. Media may be prominent, but event identity, timing/context and route to Event Hub remain understandable. The design should avoid generic social-profile chrome becoming the dominant hierarchy.

28.9 Commercial boundary  
Feed may become a legitimate event distribution surface for hosts and organizers. Future promoted event content must be clearly disclosed, relevance/ranking governed, and incapable of overriding consequential event truth. Commercialization does not convert Feed into a general advertising or influencer timeline.

28.10 Design-workstream consequence  
Representative-screen validation continues using Home / Discover / Events / Feed as the current consumer shell. The next canonical screen is Feed — Connector emphasis, designed strictly under this event-only definition. Older refoundation passages remain provenance/evidence and must not be used downstream to remove Feed or reopen the four-root shell unless a later explicit founder decision supersedes this section.

29 — HOST WORKSPACE SURFACE & EVENT OPERATIONS RECONCILIATION  
Status: CURRENT FOUNDER-APPROVED DESIGN AUTHORITY — September 12, 2026

29.1 One product, two host workspace surfaces  
Sontu uses one governed event system with two complementary host workspace presentations:  
• Mobile Host Workspace — native/compact Sontu app surface for in-field, time-sensitive and lightweight host/team work.  
• Sontu Host Portal — responsive wide-screen web workspace for deeper event configuration, coordination and oversight. Intended primarily for laptop/desktop and usable on sufficiently large tablets/landscape viewports when the responsive layout remains effective.

These are not separate products or separate event records. They share the same authoritative event state, identity/acting authority, permissions, design system, modules and audit semantics. A change on one surface must resolve to the same governed state on the other.

29.2 Responsive rule  
Do not block a device solely by device name. Compact/mobile layouts prioritize field operation. Wide portal layouts activate when available space supports them. 30.29 — Profiles, Connections, Following & Host Reputation — founder lock

Purpose and doctrine  
SONTU supports a lightweight social/relationship graph only where it strengthens real-world relationships, event discovery, invitations, hosting continuity, trust or future gathering. The social graph serves real-world gathering; real-world gathering does not serve the social graph. SONTU's social graph exists to strengthen real-world relationships and experiences. Events remain its primary shared context, not personal content publishing.

One identity; universal following  
Every SONTU account uses the same identity model and every eligible person may potentially host or participate. Follow is therefore not restricted to a special Host account/type. Subject to Privacy & Safety, blocking and discoverability controls, any person may follow another person. Follow is unilateral and does not require reciprocal acceptance by default. Organizations and other later-authorized event-producing identities/entities may use the same conceptual Follow relationship where appropriate.

Follow semantics  
Follow means that another identity's permitted event-world activity is relevant to the follower. It may influence Discover, event-only Feed ranking, future-event awareness and stage-approved notifications. Follow does NOT imply friendship, Connection, messaging permission, privileged profile access, endorsement, event access or reciprocal visibility. A user may follow someone because they like events that person hosts, finds or attends without wanting a reciprocal Connection.

Connections  
Connection is a reciprocal person-to-person relationship. Baseline lifecycle: request → accept or decline → connected → remove/disconnect. Blocking or applicable safety/privacy action overrides connection availability and visibility. Shared attendance, invitation, organization membership, event-team participation or following does not automatically create a Connection.

Close Connections  
A Close Connection is a private unilateral classification that the user may apply to an existing Connection. It requires no reciprocal approval and should not notify or label the other person. It exists for the owner's organization, invitation targeting and stage-approved relevance behavior; it is not a public friendship tier or status badge.

Private Groups  
Users may organize Connections into private custom Groups such as Family, Close Friends, Work, Cousins, School, Car Crew or any compliant user-defined context. Groups may overlap and a Connection may belong to multiple Groups. Group membership is private organizational metadata and must not become a public relationship label. Groups may support invitation/audience selection and other later-authorized event-centered workflows.

Shared Event Context  
A legitimate shared-event relationship may create a discoverability/context signal where event visibility, participation visibility and Privacy & Safety permit it. Examples include people who attended or otherwise legitimately participated in the same event. Shared Event Context never automatically creates a Connection. It may support contextual recognition such as a shared event, permitted people discovery, Follow or Request Connection. Private, restricted or otherwise protected event relationships must not leak through this mechanism.

Followers and Following presentation  
Followers and Following are legitimate visible profile/audience signals and may be shown as counts on lightweight profiles. They are not, by themselves, measures of hosting quality or trust. SONTU must not create follower leaderboards, follow-for-follow incentives, follower-growth streaks, popularity XP or other mechanics whose primary purpose is status competition or follower accumulation. Privacy/discoverability controls may limit relevant visibility without changing the underlying relationship semantics.

Activity visibility and discovery  
Following a person does not grant access to everywhere they go. A person's Interested, Going, attendance or other event relationships may influence follower/Connection discovery only when both the event's access/visibility rules and that person's applicable activity-visibility settings permit it. Private/restricted event participation, protected location/access information and blocked relationships cannot leak through recommendations, Feed, mutual/shared-event context or follower surfaces.

Examples of permitted contextual relevance, when authorized by visibility/privacy rules, include: Hosted by someone you follow; a Connection is interested; several Connections are going; or an event is relevant among people you follow. These are event-discovery signals, not authorization for a personal activity timeline.

Lightweight profile contract  
The existing lightweight-profile doctrine remains controlling. A typical member-facing profile may contain avatar/photo, preferred display name, @handle, optional concise bio/links/interests, Follow/Following state, Connect/Connected state, Followers/Following counts, permitted mutual/shared-event context, factual verification/trust context and progressively available hosting reputation where sufficient evidence exists. Do not add a personal wall, generic status posts, arbitrary personal photo grid, detached personal timeline, follower leaderboard or elaborate social-profile gamification.

Owner Profile Hub / Connections Hub  
The owner's private profile/relationship management experience should provide coherent access to Profile, Connections, Close Connections through relationship management, private Groups, Followers and Following. Connections supports incoming/outgoing request states, accept/decline, remove/disconnect, group assignment and appropriate safety/privacy actions. Following and Followers remain distinct from Connections. Exact presentation may adapt responsively without changing these semantics.

Invitation and repeat-event use  
Connections, Close Connections and private Groups may be reusable invitation audiences. Hosts may also be permitted to invite legitimate prior participants, prior interested users or other event-derived audiences for repeat/follow-up events without requiring a Connection, subject to invitation/privacy/anti-abuse authority. Event participation and social Connection must never be artificially coupled merely to make invitation reuse possible.

Host reputation versus popularity  
Follower popularity and hosting reputation are separate concepts. Because every person may host, hosting reputation progressively attaches to the same SONTU identity when sufficient authoritative hosting evidence exists; there is no separate host profile. Follower count may provide useful audience/social-proof context but must never alone establish host quality, trust or Super Host status.

Candidate evidence families for future host reputation include: completed hosting history; unique/credible attendee volume; repeat attendees and repeat-attendance rate where attendance evidence is reliable; attendee-to-follow behavior after an event; verified attendee feedback with sufficient sample size; event completion and cancellation/rescheduling reliability; legitimate operational/trust/safety evidence; returning audience behavior; and other evidence-backed event outcomes. Metrics must distinguish registration/RSVP from credible attendance evidence and must not fabricate attendance from lack/presence of a credential alone.

Attendee-to-follow signal  
SONTU should preserve the analytical distinction between a generic Follow and a Follow occurring after credible participation/attendance at that host's event. Post-attendance Follow may be treated as a stronger behavioral indication of future-event interest because the person experienced the event before choosing continued relevance. This signal may contribute to internal host-quality/reputation analysis when privacy, attribution and anti-gaming requirements are satisfied; it need not be exposed as a raw conversion statistic on ordinary consumer profiles.

Verified feedback and anti-gaming  
Any attendee feedback used for host reputation must be grounded in legitimate event participation/attendance evidence to the extent technically and operationally feasible. Public averages/designations require a sufficient sample threshold rather than presenting tiny samples as robust reputation. SONTU must not reward positive ratings, permit hosts to manufacture reputation through obvious self/duplicate participation, or allow follower count alone to dominate quality. Exact fraud detection, confidence weighting, minimum sample sizes and reputation calculations remain downstream evidence/policy decisions.

Super Host boundary  
Verified and Super Host remain semantically separate. Verified represents factual identity/organization or other explicitly verified assurance. Super Host is a future evidence-backed hosting-quality/reliability designation. Super Host must be multidimensional rather than a raw follower or star-rating threshold. Candidate evidence families include Experience, Quality, Reliability, Audience and Trust. The qualification model must permit excellent small/intimate-event hosts to qualify without requiring mass audience scale. Exact thresholds, weights, decay periods and disqualification/recovery rules are intentionally NOT locked until sufficient SONTU usage and abuse evidence exists.

Feed and social boundary  
The event-only Feed authority remains controlling. Following may improve ranking/relevance of permitted event-originated or event-contextual content, but does not authorize general personal posting. People, organizations, hosts, venues and communities may be visible actors around events while event context remains necessary for Feed eligibility. General user-to-user DMs remain outside this lock unless separately authorized.

Privacy & Safety precedence  
Blocking, safety restrictions, account/event privacy, event visibility/access and discoverability controls override social convenience. A Follow or Connection must never grant access to protected event information. Exact controls for who may find, follow, request Connection, view followers/following, see permitted event activity or appear in shared-event discovery must be defined/consumed through Privacy & Safety authority and implemented consistently across Search, Profile, Discover, Feed, Events and invitations.

Domain/data implementation requirements  
Durable Follow, Connection, Close Connection, Group membership and event-derived context relationships must reference immutable account/entity IDs rather than mutable @handles. Follow and Connection are distinct relationship models and must not be represented as one overloaded friendship state. Connection request state, reciprocal Connection state, unilateral Follow state, private Close classification and private Group membership must remain distinguishable in authoritative storage and authorization. Relationship deletion/blocking/privacy changes must not corrupt historical event, attendance, host-role or invitation records.

Implementation handoff rule  
The implementation workstream may build the profile/relationship surfaces and state transitions described here but must not invent additional social-network behavior. Where exact privacy options, abuse limits, Super Host qualification or notification frequency remain unresolved, preserve extensibility and safe defaults rather than hard-coding speculative policy.

Founder disposition  
Profiles remain intentionally simple, but SONTU's relationship system is not intentionally vague. Follow, Connection, Close Connection, private Groups, Shared Event Context and Host Reputation are distinct concepts with the semantics above. This section supersedes earlier language where 'Connections' was named but exact follow/reciprocity semantics were left wholly undefined, while retaining the prohibition on general personal timelines and engagement-for-engagement's-sake.
