1 — PRODUCT IDENTITY

Primary international name: Sontu / SONTU.  
Secondary Vietnamese identity: Sốntụ.

Sontu is an independent participant-and-host event platform intended to help real-world events succeed through coherent coordination rather than digital attention capture. The coined brand story draws from Vietnamese sống (live/living/alive) and tụ (gather/assemble/converge). “Where lives converge” remains explanatory brand territory, not a locked tagline.

Sontu is not defined by one emotion. A successful event may create connection, belonging, remembrance, accomplishment, learning, meaning, celebration, contribution, enjoyment, participation, or another event-appropriate outcome.

2 — PRODUCT THESIS

Sontu should own a coherent event lifecycle from host intent and creation through distribution, participant understanding, commitment, preparation, arrival, participation, closeout, learning and useful repeat continuity.

The product succeeds when the event succeeds for the people involved—not when Sontu captures more of their attention.

Sontu does not need a novel feature that competitors cannot reproduce. The controlling product-quality question is whether Sontu combines the right capabilities into a substantially more coherent, lower-friction and more useful system than fragmented alternatives. Feature overlap is acceptable. A capability fails only when owning it provides no meaningful usability, coordination, workflow, outcome or economic advantage.

3 — ONE GOVERNED EVENT STATE

Sontu should operate from one authoritative governed event state. Participant, standard host, advanced Host Control Center, operational role surfaces and future permissioned AI/LLM access must resolve against the same underlying event state.

Consequential information should be entered or changed once and propagate to every relevant surface. Examples include capacity affecting registration and waitlists; seat assignment affecting credentials and arrival information; room changes affecting schedules, maps and notifications; cancellation releasing capacity; access changes affecting credentials and checkpoints; and event closure affecting follow-up and retention.

A second disconnected event system is not acceptable merely because a workflow is advanced.

4 — PROGRESSIVE COMPLEXITY

Sontu may own a broad capability library while presenting a contextually small interface. Capability availability does not mean universal visibility.

Simple events must remain simple. A dinner, casual meetup or ordinary workshop should not require enterprise-style configuration. Private, paid, restricted, capacity-sensitive or operationally complex events may progressively reveal the controls they need.

Complex event types should be compositions of reusable Sontu capabilities rather than independent products such as separate Wedding Sontu, Conference Sontu or Expo Sontu.

5 — SURFACE MODEL

Sontu has complementary surfaces over the same governed state.

Standard participant experience: understand the event; evaluate fit and trust; RSVP/register/apply/purchase where relevant; prepare; remain current; retrieve credentials; arrive; use contextual event utilities; complete relevant follow-up; and retain only useful continuity.

Standard host experience: express intent; create ordinary events quickly; configure consequential access/capacity/invitation/ticket rules; preview the participant experience; publish/share/invite; manage commitment, communication and admission; see actionable exceptions; close the event; and reuse governed state.

Advanced web Host Control Center: an optional information-dense but task-oriented workspace for events requiring simultaneous management of complex operational state. Candidate capability areas include space/floorplans, tables/seats, rooms/zones, multi-track programs, exhibitors/vendors/sponsors, booths, session capacity, staffing/volunteers, badge/access classes, advanced segmentation, operational maps, communications, live exceptions and outcomes.

Purpose-built operational surfaces: door/check-in, staff, volunteer, speaker, exhibitor/vendor and similar roles receive only the information/actions needed for their task.

Future AI/LLM/agent access: permissioned natural-language creation, discovery, evaluation, RSVP/registration, waitlist, cancellation/release, calendar coordination and host operations may be exposed over the same governed state. Agent access is another interface, not another product model.

6 — COMMON EVENT PRIMITIVES

The candidate shared vocabulary for broad Sontu capability is compositional rather than event-type-specific. Core concepts include Space; Time; People/Parties; Roles; Entitlements; Capacity/Inventory; Program/Activities; Organizations/Commercial Participants; Credentials/Access; Assignments; Resources; Communication/Change; Tasks/Operations; Interaction; and Outcomes/History.

Specialized workflows may have specialized interfaces while sharing the same underlying event, actor/party, entitlement, assignment, schedule, policy and permission state.

Exact domain schema, database representation and API boundaries remain deferred to later architecture work.

7 — PARTICIPANT ACCESS AND ACCOUNT MODEL

Accountless participation is first-class where event consequence permits it. A person should not need a durable Sontu account merely to understand an ordinary public event, respond to an invitation, register, retrieve a ticket/QR, revisit current event information, or contribute event-scoped media when a secure event-scoped capability can perform the job.

Identity, Account, Invitation, Commitment, Party Entitlement, Ticket/Admission Entitlement, Credential, Payment and Attendance are distinct concepts.

Accounts should earn adoption through durable value: one place for upcoming/past events, easier recovery, reusable preferences, followed hosts/organizations/series, history/corrections, personalized discovery, saved tickets/receipts, integrations and other legitimate cross-event convenience.

Identity and assurance should scale with consequence. Accountless does not mean unauthenticated or insecure. Restricted or high-impact actions may require stronger verification.

8 — PARTICIPANT EXPERIENCE

The default participant lifecycle is:  
External source / Sontu discovery / future AI agent → authoritative event artifact → rapid fit/trust evaluation → appropriate commitment → preparation/change handling → arrival/admission → contextual during-event utility → closeout/resources/media → optional useful continuity.

The participant should be able to determine quickly: What is this? When and where is it? Who is hosting? Is it for me? What does participation require or cost? What should I do next?

After commitment, the event-scoped home/return surface should become the authoritative current state rather than forcing participants to compare old emails, messages, PDFs and app screens.

For simple events Sontu should largely recede after admission. More complex events may surface current/next activity, personal schedules, maps, rooms, sessions, changes, resources, entitlement checks and purpose-bound interactions.

9 — COMMITMENT MODEL

Sontu should not collapse every participant relationship into one generic RSVP state. Interest, RSVP/registration, application, waitlist, ticket ownership, current intent/reconfirmation, cancellation/release and attendance answer different questions.

Commitment should be proportional to event consequence. Open/low-consequence events should remain lightweight and ordinary nonattendance should generally be neutral. Capacity-sensitive commitments may justify stronger confirmation, easy release/cancellation, waitlist recovery and reliable attendance evidence. Paid, curated/approval and restricted events add their own consequence-specific state without making payment or identity equivalent to attendance.

The desired behavior is not perfect attendance at all costs. Success may be either honoring a consequential commitment or releasing it responsibly early enough for the event to recover capacity.

10 — PARTY, TICKETING, CREDENTIAL AND ADMISSION MODEL

An invitation or order may represent a party and N admission units rather than assuming one person equals one credential.

A party may be authorized for 0, 1 or N additional guests. Additional-guest requests may be approved, partially approved or declined by the host according to capacity and event policy.

Group admission may use one shared credential representing multiple remaining admissions, split individual credentials, or a mixed arrangement. The authoritative entitlement/admission ledger—not the QR image—is the source of truth.

Arrival should degrade gracefully where policy permits: QR/wallet/app credential → accountless event return link → email/SMS → authorized lookup/manual resolution. Restricted events may disable weaker fallback paths.

Admission should remain deterministic and explainable. Intelligence may assist with exceptions but must not replace authoritative entitlement/access rules.

11 — HOST EXPERIENCE

The standard host lifecycle is:  
Intent → minimum viable event → consequential configuration → participant-experience preview → publish/share/invite → commitment/capacity management → communications/preparation → live operations → reconciliation → learning → reuse/recurrence.

Creation should be intent-first and progressive. Sontu should ask only for the minimum necessary event state, then request or infer consequential missing decisions as complexity emerges.

Hosts should preview the participant contract before publishing: what participants can see, what action they are being asked to take, what information/proof is required, what confirmation/credential results and what obligations/cancellation path exist.

Host operations should prioritize actionable state and exceptions rather than dashboard accumulation. The core questions are: Who is committed? What is unresolved? Is capacity at risk? What changed? Who needs information? What requires my decision? What must be prepared?

12 — ADVANCED HOST CONTROL CENTER

Advanced hosting is a legitimate long-term Sontu capability, not categorically outside the product merely because enterprise competitors offer similar tools.

The Control Center becomes relevant when an event introduces operational structure such as reserved positions, multiple rooms/tracks, exhibitors/booths, complex staffing, scoped access zones, significant resource conflicts or event-day exception volume.

Floorplans are views/editors over governed Space/Position state, not an independent architecture. Seating connects spatial inventory to party/participant assignment, accessibility/VIP constraints, credentials, admission and wayfinding. Convention/expo operations similarly compose space, program, organizations, entitlements, access, staffing and participant outputs.

Control Center capability is canonical but not an initial implementation bundle. Advanced functionality is complexity- and evidence-earned: a validation event should receive only the advanced-host capability genuinely required to test or operate that event. Floorplans, CAD/BEO import, booth commerce, complex multi-track operations, 2D/3D editors and similar capabilities do not become release requirements merely because the Control Center exists in the product model. Exact Control Center information architecture, editor mechanics, hardware and release sequencing remain deferred.

13 — COMMUNICATION AND CHANGES

Communication should derive from governed event state. A host should make a material change once; Sontu should determine who is affected, whether communication is warranted and what current authoritative information the message should reference, with appropriate host control for consequential outbound communication.

Operational event communications and marketing/relationship communications are distinct purposes and require distinct permission/consent handling.

Notification volume is not success. During-event notifications have especially high interruption cost and should be limited to critical/material changes, personally relevant imminent actions and intentionally configured program reminders.

14 — DURING-EVENT INTERACTION

Sontu should support event-purpose interaction without becoming a generalized social network. Polls, Q\&A, voting, exercises, scavenger hunts, trivia, exhibitor passports, challenges, networking/contact exchange, meeting coordination, group discussion and similar tools are contextual capabilities when they improve the event itself.

Gamify the event, not Sontu usage. Generic XP, streaks, follower-status competition or platform-engagement mechanics are not foundational product objectives.

Participant-to-participant communication should remain purpose-bound and contextual. Generalized cross-event DMs, infinite feeds and popularity/status mechanics are outside the default model.

15 — EVENT MEDIA

Event-scoped shared photo/video albums are a legitimate contextual Sontu capability for events where collective memory or shared documentation is useful, including weddings, reunions, trips, festivals and milestone events.

Hosts should control who may view/upload, moderation/removal, upload windows, retention and export. Accountless upload may be supported where risk permits through event-scoped access.

Media must reuse the event's governed access/privacy/lifecycle state rather than become a detached social product. Storage, bandwidth, video processing, moderation and retention have real costs and privacy implications and must be governed and priced deliberately.

16 — EVENT CLOSURE AND CONTINUITY

Events should move through LIVE → RECONCILING → CLOSED or equivalent lifecycle states. Close the event before extending the relationship.

Attendance evidence must distinguish Attended, Responsibly cancelled/released, Verified no-show where evidence supports it, Unknown/unverified, and host/platform/event-caused exceptions. Lack of a scan alone is not a verified no-show.

Post-event feedback should be proportional and purpose-aware. Ask only when the resulting evidence can inform a meaningful decision. Event success cannot be reduced to a universal enjoyment score.

Completion is a successful terminal state. A completed event with no unresolved issue, promised artifact, useful feedback request or chosen ongoing relationship may simply close and stop asking for attention.

17 — RETENTION AND REPEAT VALUE

Retain utility, not engagement. Healthy participant retention may mean returning only when another worthwhile event exists.

Durable state should concentrate on explicit profile information, chosen host/organization/series relationships, useful event history and participant-chosen reusable preferences. Event-specific sensitive/contextual information should normally expire when its purpose ends unless explicitly promoted to durable state for legitimate reuse.

Repeat-host retention should come from less work and better decisions on the next event: reusable structure, governed settings, recurring operational knowledge, relationship permissions and evidence-backed learning.

18 — COMMITMENT HISTORY AND PARTICIPANT FAIRNESS

Any cross-event commitment history is consequential and high-risk. Sontu must not create public reliability scores, hidden universal desirability scores or unchallengeable blacklists.

Where commitment history is retained, the factual ledger should preserve context and evidence: verified attendance, responsible cancellation/release, verified no-show, Unknown/unverified and relevant exceptions. Unknown is neutral. Recent/relevant behavior should outweigh remote behavior so recovery is possible.

Hosts may eventually receive bounded semantic context where evidence establishes legitimate value, but consequential use requires transparency, provenance, correction/dispute, sufficient evidence, contextual relevance and safeguards against exclusion loops. Exact labels, thresholds and automated decisions remain deferred.

Participant-facing Intelligence should be restorative rather than punitive: help people understand and improve responsible commitment behavior rather than merely classify them for hosts.

19 — INTELLIGENCE DOCTRINE

Sontu Intelligence exists to compress complexity, reduce work and surface useful decisions. It is not an alternate authority over event state.

Useful roles include translating intent into draft configuration; asking only for consequential missing information; summarizing what matters/changed; answering grounded questions; detecting conflicts; identifying affected participants; drafting communications; recommending whether reconfirmation is warranted; surfacing capacity/waitlist opportunities; reconciling evidence; summarizing outcomes; and helping prepare a repeat event.

Deterministic rules govern entitlement, capacity, payment state, eligibility, credentials, admission and other consequential constraints. High-impact changes require appropriate human authority, confirmation and auditability.

AI must not invent identity, eligibility, attendance, payment success, host authorization or event facts. It must be able to say that evidence is insufficient and recommend no change.

20 — EXTERNAL AI / AGENT ACCESS

Sontu should preserve a future architectural path for permissioned external AI/LLM assistants to create, discover, compare, register/RSVP, waitlist, cancel/release, query changes, coordinate calendars and perform authorized host actions. This is canonical direction, not an early-release commitment: external agent execution should remain implementation-deferred until the deterministic event state, permissions, confirmations, privacy controls and auditability needed to govern it are mature enough to support it safely.

Native UI and agent access are two interfaces over one product model. External agents receive no privileged bypass. The same validation, permissions, confirmation, privacy and audit rules apply regardless of interface.

21 — TRUST, PRIVACY AND SAFETY

Privacy and purpose are product state, not later policy decoration. Data should be separated by purpose, visibility, consequence, retention and correction requirements.

Low-risk public events should not require generalized identity verification, continuous location or permanent sensitive answers. Restricted events may require stronger assurance while minimizing retained proof.

Location/geofencing may be one bounded attendance signal where justified but must not become continuous surveillance or sole attendance truth. Prefer just-in-time/time-boxed evidence and preserve lower-risk fallbacks where event policy allows.

Operational roles follow least privilege. High-impact changes should be attributable and auditable.

Sontu can provide platform controls but cannot guarantee physical event safety. Event hosts remain responsible for event-specific factual representations and real-world delivery within the eventual contractual framework.

22 — PAYMENT AND TICKETING BOUNDARY

Sontu may own coherent registration, checkout, ticketing, order, entitlement, refund/cancellation and participant UX while delegating cardholder-data collection, payment processing and other regulated payment rails to specialist providers.

Order, purchaser, payment authorization/capture, fees/tax, refund, dispute/chargeback, payout, entitlement, credential and admission consumption remain distinct governed states.

Exact payment processor, merchant/platform-of-record structure, tax/payout/reserve/fraud architecture and jurisdiction-specific obligations remain deferred.

23 — COMMERCIAL MODEL

Participants should generally remain free and accountless where event policy permits. Monetization should primarily align with host/organizer/professional value, transactions, real resource consumption and advanced operational capability—not participant attention.

The candidate commercial model is hybrid:  
\- single-event / temporary access for finite events;  
\- recurring host/organization subscriptions for repeated value;  
\- professional/multi-event access through subscription, concurrent-event capacity, credits or slots;  
\- transaction economics for paid registration/ticketing where justified;  
\- contextual add-ons for meaningful incremental resource consumption or advanced operational value.

A one-time event purchase should unlock the Sontu capabilities the event needs rather than create a disconnected event-type product. Additional media storage/retention and advanced Host Control Center capability are strong candidate add-on classes.

Avoid microtransaction clutter, intentionally crippled base events and subscription lock-in for inherently finite events. Commercial access duration and data-retention duration are distinct.

Exact prices, package names, quotas, storage allowances, durations, transaction fees and willingness-to-pay remain unvalidated.

24 — DISTRIBUTION AND DISCOVERY

Sontu should be useful before it has marketplace density. Hosts must be able to distribute authoritative event artifacts through direct links, email/SMS invitations, existing social/community channels, websites, QR and future agents.

Native discovery can become more important as legitimate event supply and participant preference state grow, but launch value must not depend on an empty marketplace becoming liquid first.

Discovery should optimize worthwhile event fit and participation rather than infinite browsing depth.

25 — INDEPENDENCE AND INTEGRATION BOUNDARY

Sontu is intended to be an independent event platform. Competing event platforms are benchmarks/null alternatives, not dependencies for Sontu's core lifecycle.

Sontu may integrate enabling infrastructure where it improves the system: calendars, maps, communications delivery, payment processors, identity/eligibility verification, AI/model providers, storage/media infrastructure and similar specialist services.

Own a capability when ownership materially improves lifecycle coherence, governed state or user outcomes. Integrate/delegate when specialist infrastructure is structurally better and Sontu gains no lifecycle advantage by recreating it.

26 — SUCCESS CRITERIA

Primary success measures should reflect real event outcomes and reduced coordination burden. Candidate measures include time to publish an accurate event; unnecessary setup avoided; participant comprehension; informed commitment; responsible cancellation/release; attendance where meaningful; recovered capacity; reduced repetitive host questions; communication/rework burden; event-day exceptions; successful closeout; participant satisfaction; time to create the next occurrence; repeat host/participant value; and host confidence/control.

Time spent, DAU, feed depth, notification opens, messages sent, app-action counts and similar engagement metrics are not primary success measures unless tied to a legitimate event outcome.

27 — EXPLICIT NON-GOALS / REJECTIONS

Sontu should not become, by default:  
\- a generic social feed or generalized messaging network;  
\- an attention-maximizing engagement product;  
\- a collection of disconnected event-category products;  
\- a disconnected advanced Control Center;  
\- a generic CRM, ERP, warehouse/procurement/workforce suite or CAD product;  
\- a payment processor merely for product completeness;  
\- a public participant reputation/status system;  
\- a continuous-surveillance platform;  
\- an enterprise feature race detached from lifecycle value;  
\- an AI novelty product or system in which AI silently controls consequential state.

28 — DEFERRED ARCHITECTURE AND VALIDATION

The following remain intentionally unresolved until the appropriate later planning, architecture, legal or validation stage: exact first-release scope and sequencing; final launch wedge; exact information architecture/navigation; final domain/database/API schema; exact Control Center IA/editor mechanics; 2D/3D floorplan and CAD/BEO import; hardware/RFID/passive tracking; detailed booth commerce; exact offline synchronization; detailed networking/messaging moderation; exact commitment-history semantics/thresholds; exact retention periods; exact payment/legal structure; jurisdiction-specific privacy/consumer/accessibility/minors/marketing/ticket/liability implementation; exact prices/packages/quotas; and quantitative willingness-to-pay/CAC/support/unit economics.

29 — INITIAL PROVING DIRECTION

Research currently favors small and repeat community/interest events as a clean initial proving environment because they exercise distribution, commitment, preparation, attendance, communication and repeat continuity without requiring the full advanced stack.

Private invited/milestone events such as weddings are also strategically valuable proving cases because they exercise party entitlements, finite one-event purchasing, seating/logistics, shared media and closeout.

This is a proving direction, not a permanent category boundary and not an authorization to fix Gate 1 release scope while research remains locked.

30 — FALSIFICATION / PIVOT CONDITIONS

Sontu should be materially narrowed, repositioned or stopped if later human validation shows that the combined system provides no meaningful usability, coordination, workflow, outcome or economic advantage; participants experience it mainly as another account/app burden; progressive complexity makes ordinary events harder; common primitives cannot represent important specialized workflows cleanly; state propagation creates more complexity than it removes; hosts will not pay enough to support the economics; repeat hosts obtain insufficient recurring value; native media/payment/advanced capabilities impose disproportionate cost/compliance burden; useful value requires invasive identity/location/reputation infrastructure; or Intelligence increases uncertainty and administrative work rather than reducing it.

These are falsification conditions, not yet operational thresholds. Before Gate 1 can complete, the downstream validation authority must define the actual experiments used to test the core thesis, including the test window, minimum sample/evidence requirement, observable behaviors, quantitative or qualitative thresholds where defensible, and predetermined interpretation of pass, inconclusive, pivot or stop outcomes. Thresholds must be derived from the experiment and decision being tested rather than invented solely to create numerical precision.

The first implementation scope must be defined downstream as a Sontu Core Validation Build: the smallest intentionally incomplete but coherent implementation capable of testing whether one governed event state produces a meaningfully better host-and-participant lifecycle than the fragmented alternatives it replaces.

The validation build is an experiment, not a miniature promise to implement the complete canon. It should exercise the minimum end-to-end lifecycle required by the selected proving events and omit canonical future capabilities that are unnecessary to test the current hypothesis. N88-G2 CONSEQUENCE-CASE PRODUCT-BOUNDARY RECONCILIATION — 2026-09-07

The current provisional Form B product nucleus is further clarified by the Consequence Case primitive established through internal domain pressure testing. Sontu does not promise to manage all event work. Where Sontu assumes responsibility for consequential coordination across an event fact/change, affected parties and/or specialist authorities, it may preserve a durable Consequence Case representing WHAT coordination obligation or outcome must become true and WHETHER governed evidence establishes that it has been settled. The people and specialist systems involved remain responsible for HOW the underlying work is performed unless a separate capability is independently justified.

A Consequence Case is native only when all of the following are materially present: a governed event fact, material change, closure requirement or Sontu-governed commitment/authority condition creates a cross-party or cross-authority consequence; the consequence cannot safely be treated as informational only; Sontu's product promise requires knowing whether the event-side obligation is settled; and simply observing an external specialist's state is insufficient. If an external authority already exposes the needed outcome and Sontu can safely read or route it without assuming resolution responsibility, Form C integration/intelligence remains the preferred null.

This primitive does not authorize or imply a generic task/project/workflow engine. Arbitrary to-dos, universal subtasks/checklists, Kanban/project dependencies, workload planning, time tracking, organization-wide assignment queues, generic collaboration threads, workflow builders, help-desk/SLA machinery, CRM stages, broad approval routing and specialist process replication remain outside the Form B nucleus. Timing, responsibility and escalation belong in a Consequence Case only when they materially affect the event coordination consequence.

Product-level host value is therefore framed more narrowly: preserve understandable authoritative event truth, identify consequential gaps created when that truth changes or remains unresolved, and determine whether those gaps have reached a policy-permitted terminal outcome without forcing the host to reconstruct state across disconnected systems and parties. This is an internal product hypothesis, not externally validated demand or willingness-to-pay evidence.

This reconciliation is conceptual only. It creates no schema, API, UI, automation, implementation scope, prototype authorization or N88-G3+ movement. External evidence debt remains unresolved and current execution remains internal-only under Sontu Governance.

N88-G2 FORM-C-FIRST OWNERSHIP RECONCILIATION — 2026-09-07

The strongest Form-C equivalence test further narrows the provisional Form-B product nucleus. Current controlling doctrine is FORM-C-FIRST / B-WHEN-OBLIGATION-REQUIRES.

Sontu should observe, reconcile, interpret and route dependable specialist/external authority by default. Multi-system or multi-party complexity alone does not justify native Sontu state. A consequence remains Form C when complete authoritative external facts plus a stable deterministic reconciliation rule can establish whether the event-side outcome is settled, pending under known authority, excepted, unknown or no longer applicable without Sontu creating an independent settlement obligation.

Bounded Form B is justified only when Sontu itself creates or explicitly accepts an event-side coordination obligation that must persist to governed terminal disposition and no dependable external authority already owns that exact obligation. Detection, convenience, integration breadth, a unified dashboard or the mere existence of cross-boundary coordination cannot create Sontu responsibility.

Accordingly, the irreducible candidate Form-B value is not broad ownership of event truth. It is ownership of selected Sontu-created/accepted coordination obligations and their settlement status where specialist systems may provide evidence/execution but cannot own the exact event-side obligation.

Consequence Cases should therefore be rare relative to event changes. Most changes should terminate through observation, information/routing or deterministic reconciliation. A native Consequence Case is warranted only after external authority and deterministic reconciliation prove insufficient at the level of the exact Sontu-created/accepted obligation.

Form C remains the mandatory null and wins whenever equivalent settlement confidence can be achieved with lower native state/responsibility burden. External evidence must eventually test whether representative valuable workflows actually contain recurring obligations that satisfy this narrower Form-B boundary.

This is product-semantic clarification only. It does not authorize implementation architecture, schema/API/UI, providers, prototype/build or N88-G3+ work.

N88-G2 FUTURE CAPABILITY NOTE — EVENT INTELLIGENCE / DATE-RISK ASSISTANCE — 2026-09-12

Status and boundary  
Event Intelligence is accepted as a canonical future capability direction, not current implementation scope, package/pricing authority or evidence that a specific warning can be made reliably today. It extends the existing Intelligence doctrine: reduce host work, detect conflicts and surface useful decisions without becoming authority over event truth.

Host scheduling assistance  
When a host selects or evaluates a date, time and location, Sontu may evaluate the surrounding event environment and surface decision-useful scheduling context before publication. The minimum useful form is a factual/basic conflict signal when dependable evidence indicates unusually significant nearby event activity or another material scheduling pressure.

Advanced Date Intelligence may later provide richer host decision support such as identified overlapping events, estimated audience/category overlap, temporal and geographic overlap, expected competition for attention, local venue/transport pressure where dependable evidence exists, comparison of alternative dates, and identification of potentially complementary events that may increase rather than reduce demand.

Risk/fit model  
Future analysis may consider factors such as date/time overlap, distance, event scale or expected attendance, audience/category similarity, price/positioning, venue/capacity context, historical local demand and relevant congestion signals. These inputs are candidate evidence dimensions, not a fixed scoring formula. Sontu must distinguish observed facts from estimates/inference and expose uncertainty/provenance appropriate to consequence.

Competition is not the only interpretation. A major nearby event may create audience, tourism, nightlife or after-event opportunity for a compatible host. Intelligence should therefore support conflict, neutral and complementary/opportunity interpretations rather than treating high local activity as automatically negative.

Commercial direction  
Basic high-confidence scheduling conflict awareness should not be intentionally withheld merely to force an upgrade when Sontu already possesses decision-relevant evidence. Richer comparative analysis, alternative-date evaluation, demand/competition context, forecasting and professional planning reports are legitimate candidate premium/professional Event Intelligence value. Exact free/premium boundaries, package names, quotas and pricing remain unvalidated and separately governed.

Architecture preservation requirement  
Current event architecture should preserve clean canonical date/time, timezone, location/venue, category/tags, capacity/scale and host/organization identity/provenance so future Event Intelligence can evaluate event context without redesigning the core event model. External event/calendar/listing, mobility/transport, venue and other specialist data should remain integrations where appropriate; Sontu need not own those source systems.

Intelligence may recommend, explain and compare. It must not silently change the host's date, block publication solely on a probabilistic competition score, invent external-event facts, or present uncertain forecasts as deterministic truth. The host retains authority to keep the selected date unless another independently governed constraint applies.

Implementation sequencing  
Do not add Event Intelligence to the current coded prototype merely because this capability is canonical. Implement only when the underlying event/date/location state, dependable external or first-party evidence, host workflow need and validation scope justify it. Early architecture should avoid blocking the feature; it does not need to prebuild the analytics engine.

N88-G2 FUTURE CAPABILITY NOTE — ORGANIZATION CONTINUITY & SUCCESSION — 2026-09-13

Status and terminology  
Sontu should preserve a canonical future Organization Continuity & Succession capability for durable organization entities. This is a future governance/trust capability, not current implementation scope and not legal estate-planning functionality. Avoid product terms such as “payable on death” or “transfer on death” where they could imply transfer of money, securities, corporate ownership, inheritance or other legal property rights.

Scope of Sontu authority  
Succession concerns control of the organization entity and its permissions/roles inside Sontu. Sontu does not determine legal ownership of a corporation, partnership, nonprofit, estate or other real-world entity and must not purport to override corporate records, shareholder agreements, wills, estates, executors, boards, courts, regulators or other legally controlling authority.

Continuity plan  
Where supported, the current authorized top-level organization controller may establish a continuity plan containing one or more nominated successors/fallback contacts, such as Primary Successor, Secondary Successor and an emergency/legal representative. Nomination records intent for Sontu-account continuity; nomination alone does not grant current top-level authority and does not automatically prove later legal authority.

Supported succession contexts may eventually include:  
• Planned handover or retirement.  
• Death of the current controller.  
• Incapacity.  
• Owner/controller departure.  
• Emergency account recovery or prolonged loss of access.  
• Verified legal/corporate authority change.

Verification and pending state  
A report of death, incapacity or authority change must never itself transfer control. It opens a governed Succession Case or equivalent high-consequence review state. While evidence is unresolved, Sontu must represent the state as pending/unknown rather than infer death or succession from inactivity, bounced email, social media, AI inference, lack of login activity or another weak signal.

Depending on organization type, jurisdiction and consequence, candidate evidence may include official death certificates or registry evidence, executor/estate documentation, corporate/director/officer records, board/shareholder resolutions, legal representative documentation, verified government/business registries, confirmations from already-authorized organization administrators and/or manual Sontu trust review. Exact evidence standards, source hierarchy, jurisdiction rules and review procedures remain deferred to later legal/trust/safety design.

Operational continuity during review  
Opening a Succession Case should protect consequential ownership/control actions without unnecessarily disabling ordinary event operations for existing authorized staff. Existing least-privilege roles may continue policy-permitted work while high-impact ownership changes, sensitive credential changes or other protected actions are restricted or receive additional review. Exact freeze/restriction behavior is consequence- and policy-dependent.

Resolution  
When succession is sufficiently verified, Sontu may assign the appropriate top Sontu organization role/control authority to the verified successor or legally authorized representative, rotate/revoke sensitive access where appropriate, notify relevant existing administrators and preserve an attributable immutable audit trail of the authority transition and evidence basis. A pre-nominated successor is preferred evidence of intended Sontu continuity but never automatically defeats superior verified legal/corporate authority.

Security principles  
• No single unauthenticated “report deceased” action can transfer organization control.  
• High-consequence succession should use stronger assurance and multi-source evidence proportional to risk.  
• Nominated successors must not receive hidden present-day privileges merely by being nominated.  
• Conflicting claims remain unresolved until governed evidence supports a terminal outcome.  
• Human/manual review is legitimate for high-value or disputed organizations.  
• Organization continuity must preserve least privilege, auditability, notification and recovery safeguards.

Architecture preservation requirement  
Future organization architecture must not assume that the account which originally created an organization remains its permanent controller forever. Organization identity must be durable and separable from any one person's account. Top-level Sontu organization authority, legal-entity evidence, organization membership/roles and individual user identity should remain distinct concepts so planned handover and verified succession can occur without recreating the organization or breaking its events/history.

Implementation sequencing  
Do not build death verification, succession workflows or legal-document processing into the current prototype merely because this capability is canonical. Current architecture should preserve durable organization identity, explicit role/authority relationships and auditable authority changes. Detailed succession UI, evidence ingestion, jurisdiction rules, legal review, dispute handling and automation are later evidence-earned work.

FOUNDER LOCK — SUCCESSOR DESIGNATION REQUIRED FOR ORGANIZATION ACTIVATION — 2026-09-13

The Organization Continuity & Succession capability is strengthened by the following founder decision: every newly created durable Sontu organization must designate at least one eligible successor before the organization can complete activation and receive ordinary durable organization authority.

This is a required continuity control, not an optional profile-completeness suggestion. The creator/controller may begin organization setup and save a draft before choosing a successor, but the organization remains SETUP INCOMPLETE / NOT FULLY ACTIVATED until at least one successor designation has been completed and accepted under the applicable verification rules.

At minimum:  
• One successor designation is required.  
• More than one successor is permitted and encouraged for resilient organizations.  
• Multiple successors may be ordered (for example Primary, Secondary, Tertiary) or later use another governed priority/decision model appropriate to the organization.  
• The current top-level controller cannot designate the same account as its own successor.  
• A successor designation does not grant current owner/controller powers merely by being nominated.  
• The nominated person should be notified and, before the designation becomes relied upon for activation, must accept/acknowledge the designation and satisfy the identity/account assurance appropriate to the current product stage.  
• A successor may later decline or withdraw; if that leaves the organization with zero valid successors, the organization enters a continuity-action-required state and the current controller must nominate a replacement. Exact restrictions/escalation for an already-active organization are deferred to policy, but the absence must remain visible and consequential rather than silently ignored.  
• Removing the final valid successor requires replacement in the same governed action or otherwise leaves the organization in a continuity-action-required state; Sontu should not present zero-successor status as healthy.

Mandatory designation does NOT mean automatic succession. On death, incapacity, disappearance, retirement/departure or another succession trigger, the previously defined Succession Case verification and superior legal/corporate authority rules remain controlling. A nominated successor is evidence of intended Sontu continuity, not proof that the triggering event occurred and not authority to override a verified legally controlling instrument.

UX implication  
Organization creation should explain the requirement plainly as continuity protection, e.g. “Choose at least one successor so your organization can continue if you can no longer manage it.” Avoid estate/banking terminology. The successor step should be a distinct consequential organization-governance step, not hidden inside optional profile fields.

Architecture implication  
Current/future organization schema must be capable of representing successor nominations independently from active organization memberships/roles, including nomination status, priority/order where applicable, nominator/controller, nominee immutable user identity, acceptance state, timestamps and audit history. Do not model successor as merely another current admin role.

Implementation scope remains governed separately. If organization creation is already being implemented in the current product slice, its domain model must not contradict this mandatory activation requirement; full death/incapacity verification workflow remains deferred.

## PROTOTYPE RECONCILIATION — PUBLIC AND GUEST PARTICIPATION

This implementation interpretation is subordinate to the existing product foundation and does not change stage gates, commercial packaging or identity semantics.

A public event may be viewable without an account. Participation eligibility is a separate host choice: Anyone, which permits a bounded guest RSVP, or Sontu users only, which requires authentication before commitment. Private-event access continues to follow its invitation and authorization rules.

Guest participation is event-scoped and does not create a second account class. A later verified Sontu account may claim a matching guest RSVP without changing the universal personal-account model. Host and participant remain contextual event relationships. No pricing, checkout, subscription or paywall behavior is authorized by this reconciliation.
